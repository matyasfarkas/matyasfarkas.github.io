    Codebase Guide (for AI agents and new developers)¶

    This document is a dense, accurate map of the Global Macroeconomic Analysis Projections and Scenarios (a global projection and scenario tool, built on an EM (Expectation–Maximization) Bayesian Global VAR engine) for an automated agent or a developer who needs to make a correct change quickly. It explains where things are, why they are shaped the way they are, and the conventions you must not break. Read it before editing compute or pipeline code.

    Companion docs: README.md (overview), USER_GUIDE.md (UI), fiscal-block-methodology.md (fiscal math), ADDING_A_COUNTRY.md (human runbook for data/model updates).

    1. What the app is¶

    A static, client-side web app: a Next.js (App Router) frontend that does all econometrics in the browser in TypeScript. There is no required backend for the core features — the pre-estimated models are static JSON under app/public/data/ and every Kalman filter / smoother / matrix op runs on the user's machine. A FastAPI backend exists only for computing DSGE IRFs from custom policy rules and is not needed for normal use. The same build also ships as a Tauri desktop app (Windows/macOS) that runs fully offline.

    Since 4.0.0 the data and the estimated model are separate from the tool. Everything under app/public/data/ is a data pack: the files plus one manifest.json that lists each file's SHA-256 and size and dates every economy. The tool reads every data file through that manifest (lib/data/dataManifest.ts), checks it before use, and takes all dates from it — nothing about the data is compiled in except the list of economies the UI knows. A new pack (a quarterly data shift or a re-estimated model) therefore needs no new app version: the web build serves whatever pack it was built with, and the desktop app reads an update pack dropped into its data folder. See §2a. The live pack is 2026Q2-reest-20261008b (Oct 2026 genuine-data re-estimation, data to 2026Q2).

    The economic content is a three-layer methodology:

    1. Conditioning — impose user paths on any BVAR variable; solve the conditional forecast with a Durbin–Koopman (DK) simulation smoother on the BVAR companion form.
    2. Counterfactual — overlay a DSGE-model policy counterfactual (MMB — Macroeconomic Model Data Base — IRFs + a policy rule, or the Barnichon–Mesters optimal-policy QP).
    3. Uncertainty — posterior-draw fan charts.

    On top of these sit three extensions: a fiscal block in 41 economies (derived debt/GDP), a 35-bloc GVAR layer with a fully endogenous US (cross-country spillovers across an endogenous US bloc + an EA aggregate + 33 Rest-of-World blocs), and a long-run anchor (a deterministic companion-drift counterfactual that glides a bloc's forecast to a user-set long-run target along its own estimated convergence profile — the reactive, no-re-estimation analogue of a Villani steady-state prior; driftSetter.ts, default transition shape).

    A fourth layer, Drivers, is experimental and sits strictly downstream of the other three: it reads the scenario path the app is already displaying and asks a chosen DSGE model from the MMB which sequence of that model's own structural shocks would reproduce it over the first twelve forecast quarters. It writes nothing back into the forecast. The claim is model-conditional — "through model M's lens, this is the mix of M's shocks that reproduces the path" — and it is validated by same-model recovery, never by any model-free statement about what caused the path. See §8c.

    🔴 TOPOLOGY CHANGE — the US is now an ENDOGENOUS coupled bloc, NOT the frozen anchor. The deployed US/spec.json carries n=40: its domestic + fiscal vars plus 3 ROW*_US trade-weighted stars (0-based cols 37–39, block:'row') plus the 4 global commons it determines. With a US row in weights_24bloc.json, configureGVARTopology sets US_ENDOGENOUS = true: the US now drives RoW AND receives RoW→US feedback through its own stars. The frozen-anchor code paths still exist (gated on !US_ENDOGENOUS) and stay byte-identical for legacy/US-less-stars data, but the live deployment runs the endogenous path. The closed form is solved on an augmented state (stars ++ US-global deltas, dim=2180, ρ(M)=0.971875 in the live artifact). See §5/§5a.

    The app ships 52 economies in one compiled registry (app/src/lib/data/countries.ts; Argentina, Israel and Russia were dropped in 2026). 35 of them are GVAR-coupled — the endogenous US bloc + an EA aggregate bloc + 33 RoW blocs listed in weights_24bloc.json (the filename is stale; it holds 35 blocs, US first, with a US weights row that activates the endogenous coupling). The other 17 are the euro-area members (DE FR IT ES NL AT BE FI GR IE LU PT SI SK EE LT LV): each has its own model (domestic + fiscal block + euro-area-wide external columns + two rest-of-euro-area aggregates, estimated one by one, outside the coupled GVAR), not in the coupled GVAR and with no weights row. The reason: the fully-disaggregated euro GVAR was non-convergent (ρ(M)=1.089>1); aggregating the euro area into one EA bloc restores stationarity (ρ(M)=0.726 at the time) — this is why EA is a single bloc and the members are separate.

    2a. The data pack — how the tool reads data (4.0.0)¶

    • One indirection. dataManifest.loadManifest() reads manifest.json (no-store), checks compatibility (schemaVersion major = 2, minToolVersion ≤ app version) and, for an update pack, that every reused file matches the app's built-in copy. Then fetchVerified(logical) / fetchJSON / fetchGzJSON look a file up in the manifest, read it, and check byte length and SHA-256 (for .gz, of the compressed bytes) before use. loader.ts and gvarLoader.ts read every data file this way. A failure is an error with the file's name, and the file is never used. Caveat: the callers only log it (page.tsx, gvarLoader.loadGVARModels via Promise.allSettled, loadGvarWeights falling back to the build-time weights), so after start-up a bad file shows nothing on screen and the global model silently leaves that economy out — see UPDATE_MANUAL.md §10, Known limits.
    • Where the bytes come from (getDataSource). Web: <base path>/data/. Desktop (Tauri): the pack built into the app, unless <appDataDir>/gmaps-data/manifest.json exists — then that folder (read with the Tauri fs plugin), with the same checks. An update pack in that folder may mark files inherit: true (= take the built-in copy). Rollback = delete that manifest.json and reload.
    • Dates come from the data. loadManifest calls dates.setPanelDates(manifest) before any bloc data is used. lastHistOf(country) throws if read earlier — there is no compiled fallback date. The pack's dating itself comes from each historical_levels.json firstQuarter + rows − 1 (stamp_calendar.mjs, checked by pack-verify).
    • DataPackGate (inside LoginGate) renders the app only after the manifest has loaded, so every component that reads dates during render sees them initialised; an incompatible pack is shown as one full-screen message. DataPackSection (Settings) shows the pack id, "data through", and its source (bundled / update / external), plus the desktop "Open data folder" and "Reload" buttons.
    • What is still compiled in: the economy list (countries.ts, the CountryCode union) and a build-time copy of the weights + 6 specs in gvarSolve.ts (module-load default topology, test default, fetch-failure fallback, and the candidate-bloc list GVAR_BLOC_CANDIDATES). So a pack can update existing economies but cannot add one.
    • Tools: pack-build.mjs --pack-id <id> stamps the manifest (packs are immutable by rule: never re-use an id for different content — the script does not enforce it); pack-verify.mjs --full checks every hash, the weights↔coupling link, the dating against the estimation panels, and that the pack does not need a newer app; pack-delta.mjs cuts an update pack against a recorded release (pipeline/released_packs/<version>.manifest.json). User and maintainer guide: docs/UPDATE_MANUAL.md; field reference: DATA_SCHEMA.md §1.1.

    3. The render/compute flow (one pass)¶

    ChartGrid is the hub. Per render it computes:

    • condForecast = useConditionalForecast(...) — single-country conditional forecast (mean + level deviation + scenario levels) via the DK smoother.
    • gvarFc = useGvarForecast(...) — for any active GVAR bloc (the endogenous US + EA + the 33 RoW blocs), the cross-country propagated forecast (solved in a Web Worker). null for a non-GVAR country (a euro member). Under the endogenous-US topology it returns a two-tier result: a fast mode:'direct' first-order preview on every pin edit, and the complete mode:'full' fixed point on the explicit "Solve full GVAR" button (solveFullToken) — see §5a/§8.
    • effective = (isGvar && gvarFc && !hasFiscalTarget) ? {...condForecast, ...gvarFc fields} : condForecast — the path actually drawn. This is the single source of truth for "the displayed scenario line".
    • fiscalBlock (the 41 economies with a fiscal block) — derived PB / debt-service / debt-to-GDP from effective.scenarioLevels by the accounting identity.
    • setDriversInput({ displayed, isolated, coupled, displayedIsCoupled, external, baselineDisplay, histDisplay }) — a publish into the store of the level-deviation paths the Drivers drawer reads (§8c). ChartGrid writes it in an effect and never subscribes to it, so the publish cannot re-render the grid; the same pattern as setChartExportData.

    Refs gvarBandRef and fiscalMeanRef snapshot effective and fiscalBlock so the band-computation effect (which fires only on Compute, deps [uncertaintyComputing]) reads fresh values without re-subscribing.

    3a. Per-chart render memoization (so one edit repaints ≈1 of ~35 panels)¶

    A single conditioning edit changes scenarios, re-running the monolithic charts useMemo → every chart object gets a fresh identity. Absent memoization, Plotly would repaint all ~35 panels for one dragged point. Two levers (in ChartGrid.tsx) collapse that to ≈1 panel:

    • reconcileCharts(next, prev, onRebuilt?) (ChartGrid.tsx:205) reuses the PRIOR render's chart object reference for any panel whose freshly-built content is deep-equal (chartDeepEqual, :173), keyed by chartVar.bvarIdx. It returns the prior array outright when every element kept its reference (stable outer identity → no [charts] effect churn). The data is byte-identical — this only preserves reference identity where the content did not move.
    • MemoDraggableChart = memo(DraggableChart) (:2523) skips the re-render entirely when a panel's chart reference and the grid's useCallback'd handler props are all ===.

    So a conditioning edit (or a GVAR spillover) repaints only the conditioned panel + any partner panels that actually moved. Pinned by chartgrid-render-memo.test.ts via the exported chartRebuildCounter / draggableChartRenderCounter instrumentation (test-only, ~zero production cost). This is the render optimization; the compute optimization (keeping the heavy GVAR solve off the drag path) is §5a/§8b.

    5. The GVAR engine (app/src/lib/compute/ + lib/data/gvarLoader.ts)¶

    35-bloc GVAR. The US is a fully endogenous coupled bloc (n=40; PZTEXP was dropped in the 2026-07 dedup as an exact duplicate of GLB_OIL): it carries its domestic + fiscal vars, the 4 global commons as its OWN endogenous variables (the US determines oil / US10Y / USBAA / USeq), AND 3 ROW*_US trade-weighted stars (0-based cols 37–39, block:'row') from a US trade-weights row — so the US drives RoW through the globals/its linked series AND receives RoW→US feedback through its own stars, iterating in the cross-country fixed point exactly like a RoW bloc. The other 34 blocs are an EA aggregate plus 33 Rest-of-World blocs (JP, UK, CA, CN, CH, KR, MX, AU, TR, SE, PL, NO, DK, IN, BR, ID, SA, ZA, TH, MY, CL, CO, CR, CZ, HU, IS, NZ, TW, HK, SG, RO, PE, PH — the blocs list of weights_24bloc.json; RU, AR and IL were dropped in 2026). EA and all 33 RoW blocs each carry two kinds of foreign variable:

    • 3 trade-weighted stars (block:'row'): ROWDEM/ROWINF/ROWFIN = trade-weighted partner real-GDP growth / inflation / short rate, renormalized over partners present each quarter.
    • 4 global commons (block:'global', the SAME 4 ids in every bloc, US-determined): GLB_OIL (WTI), GLB_USLR (US 10Y), GLB_USBAA (US BAA → credit spread), GLB_USEQ (US equity). All 4 globals are isFinancial:true in every bloc (verified across US/EA/JP/CN/…), so the COVID-as-missing window keeps them OBSERVED (not macro-masked / imputed) — a coherence fix that applies in particular to GLB_OIL and GLB_USEQ, which were previously mis-tagged: oil and US equity are market data and must condition the COVID imputation, not be holes in it.

    How the globals propagate (applyGlobalPins in gvarSolve.ts). Each RoW bloc PINS its 4 global columns to its own baseline + the US scenario DEVIATION of the matching global (matched by id, 1:1): pin = cBaseLvl[col] + (usScenLvl[usCol] − usBaseLvl[usCol]). So a shock to US oil / US financial conditions moves the SAME common delta into every RoW bloc, and each bloc's domestic vars respond via its own estimated coefficients. deriveBlocIdx exposes the global columns as IDX[c].glob (id → column); a bloc with no globals gets glob = {} and applyGlobalPins is a no-op (the legacy globals-free path stays byte-identical).

    Frozen-anchor vs endogenous-US treatment of the US global delta. In the frozen-anchor path (!US_ENDOGENOUS) the US is solved FIRST and frozen, so the US scenario deviation is a constant: the global pin is a US→RoW exogenous forcing that enters the per-bloc forcing/baseline d, NOT the RoW↔RoW coupling M (the globals are held fixed across the per-period M probes). Under the endogenous-US path (the live deployment), the US scenario deviation of each global is itself part of the fixed point (the US responds to RoW feedback), so the US-global delta becomes an augmented state variable and its coupling enters M via the buildLinearSystemEndo channels (2)+(3) — see §5a. Indirect effects (globals move a bloc's macro → its stars → other blocs) always flow through the existing star coupling M and are not duplicated.

    🔴 DESIGN DECISION — pin the US DELTA, not the US LEVEL (load-bearing). Each RoW bloc estimated its OWN baseline path for the globals (weakly-exogenous regressors), and those baseline LEVELS differ from the US's by tens of 100·log units on oil. Pinning the US level would inject that entire baseline gap as a spurious delta even at ZERO scenario (every country would jump the moment it was selected). Pinning the US delta on each bloc's own baseline gives exactly zero spillover at zero scenario AND an identical common shock under conditioning — mirroring how the star pins use baseRoW + partnerDelta, not the partner level. The first (wrong) implementation pinned the level; it was caught by the CN-deflation and zero-scenario tests. Verified on the real GVAR data: a US GLB_OIL pin yields an identical oil delta across all RoW blocs to ≤1e-9, and a zero scenario yields zero RoW spillover.

    The scenario deviation is a linear fixed point x = M·x + d (baseline is data-driven, computed once). The engine solves it in closed form as x = (I − M)⁻¹·d. Under the live endogenous-US topology the state is augmented (RoW+US stars ++ the US-global deltas), so dim = 2180 and ρ(M) = 0.971875 < 1 in the deployed artifact (pack 2026Q2-reest-20261008b; see §5a for the channel construction; the value moves with each refit — 0.957724 for the Sep 2026 model — and what is load-bearing is < 1; a pre-2026-07-17 artifact field read 0.935044 from a power-iteration estimator that missed the complex dominant pair — corrected by eigendecomposition). M and its inverse come from the precomputed coupling artifact (bvar/gvar/coupling_default.json.gz, read from the data pack via fetchGzJSON: hash-checked, then decompressed in-browser with DecompressionStream; no plain .json fallback) — building/inverting M at this scale is many minutes in-browser, so the artifact is mandatory for interactivity, not optional. The shipped artifact carries modelSig (35-bloc, US:40), pinStructure: '' (the empty/baseline structure), dim, rhoSpectral, M, AND the BLAS-computed invImM. The manifest records the weights the coupling was built from (gvar.coupling.inputs.weightsSha256); gvarLoader drops the artifact (and the solver recomputes) if that differs from the served weights' hash. Gauss–Seidel (solveGVAR, which now iterates the US too when endogenous) is kept as a cross-check; closed-form ≡ iterative to ~1e-6 over the full conditioning battery. (Historical note: the pre-endogenous frozen-anchor coupling had dim≈1920, ρ(M)≈0.726 — those figures no longer describe the deployed artifact.)

    Topology is self-configured, not hardcoded. configureGVARTopology(specs, weights) (in gvarSolve.ts) reads each deployed spec.json + the trade weights fetched from the data pack (weights_24bloc.json; the filename is stale — it lists all 35 blocs; the build-time copy is only the default/fallback) and, for every candidate bloc, derives its gdp/price/rate columns (deriveBlocIdx, mirroring the estimator's findcol prefix order), its RoW-star indices, and its global columns (IDX[c].glob). A RoW bloc is active iff its spec carries block:'row' vars AND it has a weights row. The US is endogenous iff its OWN spec carries the 3 ROW*_US stars AND weights_24bloc.json has a US row — this sets the module flag US_ENDOGENOUS. Two derived sets are mutated in place: - ROW_COUNTRIES = every bloc except the US (the weight-row + global-pin recipients; the US is the global SOURCE, never a global RECEIVER). - COUPLED_COUNTRIES = the blocs that iterate in the fixed point: ROW_COUNTRIES when the US is frozen, or ['US', ...ROW_COUNTRIES] (US first) when US_ENDOGENOUS.

    IDX, W, ROW_COUNTRIES, and COUPLED_COUNTRIES are mutated in place at load (importers hold live references); W is keyed for every COUPLED bloc (the US too, when endogenous), renormalised over the active panel. gvarLoader re-configures from whatever blocs are actually deployed. Never hardcode bloc indices or a bloc subset — read IDX/ROW_COUNTRIES/COUPLED_COUNTRIES at runtime.

    5·EM.s. Seasonal dummies for NSA-seasonal blocs (offline estimation contract)¶

    Some blocs carry not-seasonally-adjusted (NSA) series (NSA HICP/CPI, unemployment LR, house prices, India GOV, UK/KR SFA) whose within-year cycle, left unmodelled, is otherwise absorbed by a near-Nyquist companion root (an alternating-sign root ≈ −1) that produces a spurious sawtooth in forecast. The fix is a set of deterministic quarterly seasonal dummies baked into the estimation, so the seasonality is a bounded deterministic cycle instead of an explosive stochastic root.

    Which blocs (GVAR_DUMMY_BLOCS, pipeline/export_bvar_gvar24_loop.m). The script's default coupled set is 16 blocs — {CL, CN, CO, CR, EA, ID, IL, IN, IS, JP, KR, MX, NO, TR, UK, ZA}. The deployed Oct 2026 run passed that list plus HK and PE (left out by accident before), so with IL no longer estimated 17 coupled blocs carry dummies; the euro members' run set EURO_DUMMY_MEMBERS to all 17 members (pipeline/export_bvar_euro_redesign.m). 34 economies in all — the pack manifest lists them (blocs.<CC>.seasonalRows = 3). A bloc qualifies when the panel scan flags calendar-R² ≥ 0.40 with display-amplitude ≥ 2 on any NSA series, PLUS every even-interest bloc (below). Both env vars override the default.

    Mechanism. The three quarterly dummies D = [q==2, q==3, q==4] (Q1 is the base) enter each equation's regressor row x = [1, D, y_{t-1}, …, y_{t-p}]. The exported betahat layout is therefore [constant; γ_Q2; γ_Q3; γ_Q4; B_1; …; B_p] — k = 1 + nsr + n·lags rows with nsr = 3 (seasonalRows); legacy blocs keep nsr = 0 unchanged. The dummy coefficients carry a diffuse prior (variance Vc, mean 0, like the intercept) and are zeroed in the sum-of-coefficients (SOC) dummy columns. Implemented in BVAR/MFBVAR/Support/BVAR.m (optional D arg), BVAR/MFBVAR/GLPreplicationWeb/logMLMFVAR.m (D arg), and BVAR/MFBVAR/cgl_bvarV5.m (the 'qoy' quarter-of-year vararg → D; the DK simulation-smoother artificial path carries the seasonal term so the smoother stays exact, and the seasonal forecast simulation continues the q-of-year cycle). The two exporters thread a per-bloc qoy vector and ship the new fields: export_bvar_gvar24_loop.m / export_bvar_euro_redesign.m write spec.json (seasonalRows, and for seasonal blocs qoyNext) and companion_mean.json (seasonalRows).

    App side (app/src/lib/compute/kalman.ts). BVARParams gains { seasonalRows?, qoyNext? }. buildStateSpace reads the lag coefficients at row 1 + nsr (skipping the deterministic rows) and precomputes c2ByQ — 4 quarter-specific transition constants (the Q1-base c2 plus γ_Q2/γ_Q3/γ_Q4 on the top n rows). c2AtStep(ss, t) picks the constant for forecast step t via q = ((qoyNext−1+t) mod 4). Every betahat consumer is wired: gvarSolve.buildParams / makeCountryModel, useConditionalForecast, runGvarBandSolve (per-draw), driftSetter, the ChartGrid band paths, and the pipeline .mjs scripts.

    🔴 PHASE RULE (do not break). The app always derives qoyNext from its own date grid via dates.qoyNextOf(country) (the quarter after lastHistOf, wrapped 1..4), never the shipped estimation-grid qoyNext in spec.json — a within-year data shift moves the display origin past the estimation grid, so trusting the shipped value would mis-phase every seasonal constant. lastHistOf itself comes from the data-pack manifest (setPanelDates), which also cross-checks the manifest's declared qoyNext against this recomputation and stops the load on a mismatch. makeCountryModel sets params.qoyNext = qoyNextOverride ?? qoyNextOf(code) (the override is for the node pipeline scripts, whose forecast origin is not the app's; nowcastCompletion rebuilds seasonal blocs with the floor-row phase for the same reason).

    All nsr = 0 paths are byte-identical to before (buildStateSpace reads row j+1, c2 from row 0, builds no c2ByQ; buildParams sets seasonalRows only when > 0).

    Even-coupon EFFI (pipeline/build_fiscal22_columns.py) — why the even-interest blocs carry dummies. EVEN_INTEREST = {CL, CO, CR, ID, IL, MX, TR, ZA} are blocs whose interest payments follow an annual/semiannual coupon calendar (detected: a systematic within-year pattern — calendar-R² > 0.5 & CV > 0.25 on raw interest, or near-perfect quarterly alternation). even_distribute_years() replaces, within each complete calendar year, the 4 quarterly interest payments by their mean (the annual total is preserved exactly; a trailing partial year uses the trailing-4-quarter mean). EFFI = 400·evened_interest_t / debt_{t−1} then becomes the accrual borrowing cost. Primary expenditure keeps the raw interest (te − intr = true non-interest spending), and SFA (the exact debt-identity residual) absorbs the genuine cash-vs-accrual timing — which is why these blocs also carry seasonal dummies. The debt identity still closes exactly (~1e-14). Result: the EFFI sawtooth is removed (mean |q/q change| CL 4.82→0.11, MX 4.95→0.21, ZA 5.00→0.25) and the near-Nyquist companion root that drove it moves off −1 (ZA −0.973→−0.634, MX −0.953→−0.659, CL −0.965→−0.588).

    Superseded in the Oct 2026 data (decision D5). The rebuilt panels no longer even out the coupons: for MX, CL, CO, CR, ID, TR and ZA, EFFI is now interest over the last 4 quarters ÷ debt at t−4 (genuine and one-sided, to the latest quarter) — effi: "trailing4" in the source registry, computed by pipeline/sources/derived.py. These blocs keep their seasonal dummies. The paragraph above describes the earlier build_fiscal22_columns.py method.

    Result. NSA series now honestly show their seasonal cycle in-forecast as a bounded deterministic cycle (the dummies model the seasonality) instead of a spurious near-Nyquist explosive root; the residual SFA cycle is bounded (year-1 ≈ year-5 amplitude).

    5a. Endogenous-US augmented closed form + the affine-kernel perf path¶

    When US_ENDOGENOUS, the US both (i) receives partner spillovers through its own ROW*_US stars and (ii) drives every RoW bloc's globals (which the RoW blocs pin to own-base + the US-global DELTA). With the US frozen that delta was a constant in d; now it is part of the fixed point, so the compact state is AUGMENTED (buildLinearSystemEndo):

    x = [ star pin-delta s_{c,v,t}  for every COUPLED bloc c (US included), v∈{DEM,INF,FIN}, t ]
    ++ [ US global-column delta gΔ_{p,t}  for each US global column p, t ]

    with three coupling families assembled into M from the constant per-period smoother kernels: 1. star ← star — receiver c's star v at t ← partner j's linked-col response from j's star pin (vp,tp); D[v] = identity (rate) or 4·Δ (gdp/price). The US is BOTH partner and receiver. 2. gΔ ← US star — the US global col p at t = the US free-var response to its OWN star pins (a definition row). 3. star ← gΔ — a RoW partner j's domestic vars respond to its global pin (Kg[j][p]), feeding the stars of the receivers that have j as a partner (weight w_rj; US excluded — it has no global pins).

    d then carries only the exogenous own-pin contributions (each bloc's own scenario pins moving its linked series at zero partner/global delta) plus the US's own-pin global delta; the US-as-partner term is in M (1), the US-global term in M (2)+(3). solveGVARClosedFormEndo solves x = (I−M)⁻¹d — using the hydrated artifact inverse when present, otherwise an inverse-free Neumann fixed-point x ← d + Mx (the in-JS O(dim³) inverse at dim≈2060 was ~46 min — the deployed dim is 2180 — and is NEVER built live; the Neumann path converges because ρ(M) < 1, in a few hundred cheap matvecs at the earlier ρ≈0.92 and more at the deployed ρ≈0.97) — then reconstructs each bloc's full level with one final conditionalForecast.

    Affine-kernel perf (blocKernels + affineBlocKernels). A bloc's response kernels — K[v][tp] (star-pin IRFs) and Kg[p][tp] (global-pin IRFs) — depend ONLY on that bloc's params + its OWN pin STRUCTURE (which cells are pinned), not on partner data, the global topology, or pin VALUES. So: - All (3 stars + #globals)·H per-period kernels for a bloc come from one filter+smoother pass on the probe baseline plus cheap per-cell matvec recursions (affineBlocKernels in kalman.ts) instead of one full conditionalForecast per (var, tp) — numerically identical (<1e-9), ~10–20× faster on the n=40/H=20 US bloc (measured when it had lags=3; the deployed model has lags=4). - The kernels are cached (_blocKernelCache, keyed by modelSig + bloc + own-pin-cells). In the dominant flow (the user pins ONLY the US) all 34 other blocs keep an empty own-pin structure ⇒ their kernels are reused ⇒ only the US re-probes. prewarmGVARKernels/prewarmGVARKernelsChunk warm the empty-structure kernels off the critical path (in the worker right after load); prewarmGVARKernels also caches the empty-structure assembled M so the first US-pin solve reuses it.

    Two-tier UX (solveGVARDirect + the "Solve full GVAR" button). The full fixed point pays smoother reconstructions and an (I−M) solve. To stay reactive on a drag, solveGVARDirect returns a first-order preview: x_direct = d (the US scenario's one-hop spillover, no RoW↔RoW or RoW→US feedback) mapped to each bloc's level delta straight from the prewarmed kernels (pure matvecs, no Kalman pass, sub-50 ms) — it UNDER-states the response (omits multiplier feedback). runGvarSolve.ts routes mode:'direct' → solveGVARDirect (live preview on pin edits) and mode:'full' → solveGVARClosedForm (the complete fixed point, on the explicit button). The slow path is a structure-change direct solve (placing/moving a US pin re-probes the US bloc, several seconds): the hook (useGvarForecast.ts) defers it to drag-end so it fires once per gesture, shows a "computing…" badge, and the worker strips the ~95 MB coupling artifact (withoutCoupling) from direct-mode posts (solveGVARDirect never uses it). Value-only re-drags (same structure ⇒ kernel-cache hits) and full solves dispatch live. ChartGrid.tsx shows the mode badge ('DIRECT preview' amber / 'full solve' blue) and the ▶ Solve full GVAR button whenever the active result is a direct preview.

    6. Data-space conventions (CRITICAL — most bugs live here)¶

    • A variable's transformation is 'log' or 'lin' (in spec.json).
    • log variables are stored as 100·log(level). The chart displays q/q annualized growth = 4·Δ(100·log level). Historical growth in historical.json is already this 4·Δ form.
    • lin variables (rates, ratios, unemployment) are passed through as-is (level = display).
    • Conditioning is WYSIWYG: a directly-pinned quarter shows exactly baseline + your deviation.
    • Posterior draws are flat arrays with shape beta_shape=[k, nv, nDraws] (k=n·lags+1, nv=n) and sigma_shape=[n, n, nDraws]. Index: beta[draw*k*nv + j*k + i], sigma[draw*n*n + j*n + i]. These are Float64Array after loadCompanionDraws (converted once for clone/index speed).
    • GVAR RoW pins exchange paths in 100·log level space (avoids a differencing bug): for a log RoW var the pin delta is 4·Δ(level-gap), for a lin rate it is the level-gap.

    When in doubt, the canary tests (§11) encode the exact conventions — run them.

    6a. The per-variable prior convention (RW vs WN) — prior in spec.json¶

    Every variable in spec.json carries a prior field — 'RW' (random walk, the default) or 'WN' (white noise / stationary). It selects the prior mean on that variable's OWN first lag in the GLP/Minnesota prior:

    prior Own-first-lag prior mean Behaviour Used for
    'RW' (default) 1 the variable is a priori a random walk (persistent, drifts at the long end) every macro/financial level, all RoW stars, EFFI
    'WN' (stationary) 0 the variable is a priori white noise → its forecast mean-reverts to the in-sample mean the fiscal GDP-ratios FREV_GDP, FPEXP_GDP, SFA; and, in the deployed growth-rate model (BVAR_DIFF_GP=1), real GDP, the headline price and DEFL_<CC> — estimated as growth rates, so their growth mean-reverts

    The mechanism (verified — BVAR/MFBVAR/GLPreplicationWeb/bvarGLPmf.m). The Minnesota prior-mean matrix b is built with a diagonal of diagb over the own-first-lag block; WN columns get that diagonal entry zeroed:

    % bvarGLPmf.m, lines 192–195
b=zeros(k,n);
diagb=ones(n,1);
diagb(pos)=0;   % Set to zero the prior mean on the first own lag for variables selected in the vector pos
b(2:n+1,:)=diag(diagb);

    pos is the vector of WN column indices. It is the 3rd positional argument of the single-bloc estimator cgl_bvarV5.m (named stationary there; pos=stationary at line 19) and is threaded straight into the bvarGLPmf call ('pos', pos) and every downstream logMLVAR_* / BVAR call.

    Where it flows (spec.json → estimator pos → forecast). 1. The estimators read the per-variable prior from the spec and build the pos index set: - pipeline/export_bvar_gvar24_loop.m: statCols = find(Spec.Prior(keep)=="WN")' (on the kept domestic block — stars are appended AFTER and are always RW), passed as cgl_bvarV5(x, lags, Dc.statCols, …). - pipeline/export_bvar_euro_redesign.m (the 17 euro members): statCols = find(Prior=="WN")', plus the differenced GDP/price/deflator columns under BVAR_DIFF_GP (the older export_bvar_euro_fsap.m uses the same statCols rule). - They use a robust priorsfrom(vars) helper that tolerates MATLAB's jsondecode dropping a prior field that is present on only some variables (cell-array vs struct-array shapes); a missing/empty prior defaults to 'RW' (the historical behaviour) — so the WN prior is purely additive (a bloc with an empty pos is unchanged). 2. The estimator bakes the prior into the exported coefficients — the WN mean-reversion lives in the posterior betahat/sigmahat (and the draws) written to companion_mean.json / companion_draws.json. 3. The TypeScript runtime never reads .prior (grep: no .prior access anywhere in app/src). The forecast uses the estimated coefficients only — the prior has already done its work at estimation time. prior in the deployed spec.json is therefore estimation provenance / documentation, not a runtime switch. (Consequence: changing a prior requires a re-estimation + re-export, not just a spec edit.)

    Result (verified on the US bloc). Under the old all-RW prior the fiscal ratios drifted at the long end (US revenue stuck near ~19%); with the WN prior FREV_GDP mean-reverts toward its in-sample mean — the deployed US/baseline_levels.json shows FREV_GDP ≈ 18.06 at h=0 → ≈ 17.4 by h=8 → ≈ 17.9 at the long horizon, instead of drifting up. EFFI (the effective interest rate) deliberately stays RW (it is persistent). Committed 6f0161a / 22250be / e38673a. (The US numbers above are from that change; the deployed pack's values differ.) The fiscal prior assignment is consistent across all 41 fiscal economies (verified: FREV_GDP/FPEXP_GDP/SFA = WN, EFFI = RW in every shipped spec.json with a fiscal block).

    7. The fiscal block (fiscalAccounting.ts) — 41 economies¶

    Stock-flow-consistent, CBO/IMF-style. The BVAR estimates 4 fiscal drivers — FREV_GDP (revenue/GDP·100), FPEXP_GDP (primary-exp/GDP·100), EFFI (the effective interest rate = net interest / lagged gross debt ·100, annualised) and SFA (the stock-flow adjustment, % of GDP); reporting variables (debt service, debt/GDP, deficit, GFN (gross financing needs), snowball) are derived. The debtService (DSVC) parametrisation was reverted — the endogenous interest variable is back to EFFI, and SFA is now the new estimated BVAR variable.

    Stationary (WN) prior on the GDP-ratios (see §6a). The three GDP-ratio drivers FREV_GDP, FPEXP_GDP, SFA are estimated with the prior:'WN' stationary mean (own-first-lag prior mean = 0) so they mean-revert to their in-sample means instead of drifting at the long end (the old all-RW prior left US revenue stuck near ~19%; it now reverts toward ~17.4%). EFFI stays prior:'RW' — the effective rate is genuinely persistent. This is purely an estimation-prior choice baked into the exported coefficients; fiscalAccounting.ts is unchanged by it.

    Which economies: the 41 with a fiscal_meta.json — 24 GVAR blocs and all 17 euro members (the pack manifest lists them; see DATA_SCHEMA.md §9).

    • pb = revenue − primaryExp (primary balance, + = surplus).
    • SFA is a NEW estimated BVAR variable = the EXACT residual of the app's debt recursion — the deficit–debt discrepancy (observed dDebt − (deficit + interest − growth)), driven by the federal-flows-vs-gross-debt perimeter seam / intragovernmental holdings. It is computed so the recursion closes to machine precision; COVID quarters are set NaN (the COVID-as-missing Gibbs imputes them). The debt/GDP projection does NOT use the forecast SFA: computeFiscalBlock rolls debt forward with the constant structural SFA, sfaDefault (the historical mean, ex-COVID), because the forecast SFA column is pulled to extremes by the long-run anchors' cross-responses (fiscalAccounting.ts, comment above const sfaT).     • Recursion (per quarter): d_t = d_{t-1}·(1 + EFFI/400)/(1 + gNomQ/100) − pb/4 + sfaDefault/4, with pb = FREV − FPEXP and gNomQ = 100·log(realGDP)-diff + 100·log(deflator)-diff (q/q nominal, read off the level path; the deflator is DEFL_<CC> wherever the economy has one — 38 of 41 — else JGDP for the US and CPI for CN/NZ).     8. Uncertainty bands (two modes — know the difference)¶

    The band-computation effect lives in ChartGrid.tsx (deps [uncertaintyComputing], fires on Compute). Quick=50 draws, Full=200.

    • DEFAULT (model-specific density, fast, on by default). For every posterior draw, take the unconditional forecast (bvarForecastDraw, full forecast width) and parallel-shift it by the same mean scenario delta sourced from gvarBandRef.current.effective.forecasts (the GVAR-propagated path for any active GVAR bloc, else the single-country conditional). The band keeps full width (does not collapse when one point is pinned) and centres on the displayed line. The derived-fiscal charts (the 41 fiscal economies) get a matching parallel-shift band (per-draw unconditional computeFiscalBlock, shifted by mean scenario−baseline PB/debt via fiscalMeanRef).
    • EXPERIMENTAL (per-draw iterative GVAR density, opt-in). Gated behind the store flag experimentalFeatures (lower-left ExperimentalToggle). Re-solves the conditional cross-country system per draw (runGvarBandSolve). This is the conditional cloud — it pinches at pins (and collapses when lightly conditioned) and is slower. The request builder iterates the active GVAR bloc set (not a hardcoded subset), so every bloc's own-pins are carried; solveViewedScenLvl skips the cross-country sweep for a US-viewed bloc only when the US is frozen (!US_ENDOGENOUS) — under the endogenous-US topology the US depends on the fixed point like any bloc, so it goes through the full solve.

    Why two modes: the per-draw conditional re-solve over-determines the conditional mean when only a point or two is pinned, so it compresses too much; the default parallel-shift preserves the model's own forecast width while still centring on the scenario. The default is the right answer for almost everyone; the experimental mode is there for users who want the pinching behaviour.

    8a. Long-run anchor — driftSetter.ts¶

    A user can pin a long-run target for a variable. The anchor is a deterministic per-horizon display translation, not a re-estimation or a reweighting: computeDriftDeltaFull builds a level-space shift Sₕ·δc (from the drift cache) that moves the display mean and every quantile toward the target, so the terminal hits the target exactly while band widths stay invariant (a rigid translation at each horizon). Two orthogonal user toggles: solve mode perVariable/joint (joint chooses the δc's so every anchored variable hits its target simultaneously when the system is tame, else falls back per-target) and transition shape rigid/transition (default transition — the adjustment is phased in along the variable's own estimated convergence profile, so there is no origin jump; both shapes share the same exact terminal). Applied in ChartGrid; the GVAR cross-bloc spillover of the local anchor lives in gvarDriftSpillover.ts.

    The earlier after-estimation entropic-tilt PLR mechanism (KL-min importance reweighting of the posterior draws, formerly longRunTilt.ts) has been removed and superseded by this display translation, which is faster and does not degenerate the fan.

    8c. Drivers — the model-conditional scenario decomposition (EXPERIMENTAL)¶

    Everything above answers what the path looks like. The Drivers drawer answers a different question: which sequence of a chosen DSGE model's own structural shocks would have produced the path the app is currently showing? Given the scenario's level deviation from baseline, it solves for that shock sequence over the first twelve forecast quarters and draws the resulting contributions as a stacked chart in the main panel's units, with an explicit grey residual for the part the named shocks cannot reproduce. This is the NAWM-II-style "filter the path through the model" exercise, run on a path object rather than by inverting a recursion.

    State the limits before the mechanics, because they shape the code. The feature is experimental and badged as such in the UI. Its claim is model-conditional: it reports what mix of model M's shocks would have generated this path, not what caused it, and it is not model-free shock labelling. Its validation is same-model recovery — generate a path from a model's own known shock sequence, decompose it under that same model, compare the recovered contribution paths — so the numbers speak to the estimator, not to the model and not to the world. A different lens gives a different answer, and the lenses are not equally validated: pipeline/bench_simple_decomp.m ran exactly eight models (US_SW07, US_CMR14, EA_SW03, EA_SWW14, CA_LS07, HK_FP13, BRA_SAMBA08, UK_SM11) and never touched an FRB/US lens. Aggregating shocks into Monetary/Demand/Supply classes is licensed at one configuration (Remark 1). Do not widen any of this without a bench row behind it.

    Where it sits. Strictly downstream of §3, §5 and §5a, and strictly read-only with respect to them. The drawer consumes the deviations ChartGrid has already computed; nothing it does re-enters the forecast, the GVAR coupling, the fiscal recursion or the bands.

    Direction of dependencies — who may import whom. driversDecomp.ts is pure: its only import is ./matrix, and it may not grow a React, store or fetch dependency. loader.ts gains loadDriversIndex / loadDriversModelIRFs plus the DriversIndex and DriversModelMeta types; it imports nothing from the drawer. That placement is the whole reason the open flag lives in the store rather than in ChartGrid's local state — a ChartGrid → DriversDrawer → ChartGrid import cycle would otherwise be unavoidable (the rationale is recorded at useStore.ts:323). useStore.ts imports neither component.

    The engine. The object it estimates is a deconvolution. Write H = 12 for the horizon (DRIVERS_H), q for the number of watched observables, K for the number of named shocks, and let z be the scenario deviation expressed in the model's observable space. Then

    z_o(t) = Σ_k Σ_{τ ≤ t} R_{k,o}(t − τ) · ε_k(τ) + u_o(t), o = 1…q, t = 0…H−1

    where R_{k,o}(h) is model observable o's impulse response to shock k at horizon h, ε_k(τ) is the size of shock k arriving in quarter τ, and u is the residual. Stacking gives Θ·ε = z − u with Θ of dimension (q·H) × (K·H): rows are blocked by observable (row index o·H + t, the three locked common observables first, then any added natives in the order they were toggled), columns are blocked by shock (column index k·H + τ), and each (o, k) block is lower-triangular Toeplitz because a shock arriving at τ cannot move an observable before τ. The entry Θ[oH+t, kH+τ] is read out of the IRF file as irf[shock_k][irfField_o][t − τ + 1]; index 0 of every IRF array is the pre-impact zero, so indices 1…H carry h = 0…H−1, mirroring MATLAB's s.obs(2:H+1). The shipped arrays are length 21.

    The solver is displayed as

    decompose(irf, shocks, observables, H = DRIVERS_H) → DriversDecomposition

    where irf is a ModelIRFs (shock name → observable field → number[], the raw model file or a synthetic one built by buildClusterIRFs); shocks is the string[] of K named units in the model's fixed order; observables is the DecomposeObservable[] of q watched rows, each carrying key (display key), irfField (the field to read from the IRF record, usually the same string), path (number[] of length ≥ H, the observable's deviation) and an optional weight (the measurement-error row weight, 1/√(1+me), present only on added observables); and H is the horizon, 12. It returns a DriversDecomposition holding eps (a Float64Array of length K·H, shock-major: eps[k*H+τ]), contributions[k][o][t], fitted[o][t] = Σ_k contributions[k][o][t], residual[o][t] = z − fitted, the input z[o][t], the ridge lambda actually used, the numerical rank of Θ, rows = q·H, and regime, which is 'exact-fit' when rank ≥ rows and 'residual-able' otherwise.

    The estimate is the minimum-norm least-squares solution under an equal-response-energy prior: ε̂ = D⁻¹ · argmin ‖ε̃‖ over the minimisers of ‖W(ΘD⁻¹ε̃ − z)‖², where D holds the Euclidean norms of Θ's columns and W the row weights. Numerically the routine forms ΘN = ΘD⁻¹ (columns below 1e-12 keep a scale of 1 so they stay inert rather than being amplified), applies the row weights, LU-factors the ridge Gram (G + λI) once with λ = RIDGE_LAMBDA_SCALE · mean(diag G) = 1e-8 · mean(diag G), and runs REFINE_STEPS = 2 iterative-refinement sweeps against that same factorisation. Every iterate stays in range(Θᵀ), so the refined solution converges to the min-norm least-squares solution the MATLAB benches obtain from pinv. The column scaling matters economically, not just numerically: SW07's shocks differ by roughly an order of magnitude in stacked response energy (measured on the shipped US_SW07/SW.json, the three-observable H = 12 norms run from 1.28 for interest_ to 13.84 for epinf), and without the scaling the ℓ² penalty prices the small-response monetary shock out of its own attribution. In identified configurations the scaling is a pure reparameterisation; in underdetermined ones it is what takes SW07's mean off-class leakage at three observables from 32% to 5%. Contributions and the residual are computed through the raw, unweighted Θ and the un-normalised ε, so neither the column scaling nor the row weights ever touch the reported bars. thetaRank is a pivoted Cholesky on the smaller-side Gram with relative pivot tolerance 1e-12·max(diag); the shipped menu's two regimes sit about twenty orders of magnitude apart in conditioning, so the threshold is not delicate.

    Units — where this connects to §6. The input is the level deviation [t][j] in smoother level space (100·log for log variables, native units for lin), not display space. That choice is load-bearing twice over: the long-run anchor's δc drift translates baseline and scenario rigidly, so it cancels in the deviation by construction (§8a), and the observable maps are measured against the level space rather than assumed. The three locked common observables are built by commonObservablePaths:

    • output — the GDP level deviation (100·log) passed through as an identity. The column is resolved through resolveChartVars role output; on the US bloc that is GDPH.
    • inflationq — 4·(p_t − p_{t−1}) of the price-level deviation, with p₋₁ = 0 (the same convention the charts use). On the US bloc the price column is JGDP.
    • interest — the policy-rate deviation, already annualised, passed through as an identity with no division by 4. On the US bloc that is POLRATE.

    Those factors are read off the shipped SW07 file, which carries both the MMB common block and SW07's own observables, and are regression-pinned: the test suite checks on every shock and every horizon with a non-trivial response that inflationq/pinfobs and interest/robs are both 4.000 to better than 1e-9. Four further native observables (dc, dinve, dw, labobs for SW07; the CMR14 analogues) are available only on the US bloc, because only the US spec carries all five of the columns they need (CH, FNH, LXBC, JGDP, LANAGRA). Every other bloc runs at three observables. On the way out, obsDisplaySpec / toDisplayDev map each observable into the main panel's display space through a linear operator — a gain or a scaled first difference — which is exactly why the bars, the residual and the baseline re-sum to the scenario line to 1e-8.

    What the drawer's controls gate. Two rules carry the licence and are enforced in the interface, not merely documented:

    • The budget rule. At q watched observables the user may name at most q shocks. decompose throws on K > q, and the UI disables every un-named chip once the budget is reached. The budget is 3 + addedObs.length where the native mapping exists, and 3 otherwise.
    • The collinearity flag. Shock pairs whose unit-normalised stacked three-observable H = 12 response paths satisfy |cos| > 0.95 (index.collinearThreshold) are precomputed at build time and shipped in the index; the drawer warns whenever both members of a flagged pair are named, quoting the measured |cos|. The one-click "Use all" selection is greedy in the model's fixed shock order and skips any shock forming a flagged pair with one already picked (useAllShockSelection).

    Observables that are invertible linear transforms of one already watched (dy, pinfobs, robs for SW07; gdp_obs, inflation_obs, Re_obs for CMR14) are excluded from the addable list, because adding one would raise the budget by one while buying no new rank, making the identification the budget rule promises fictitious. That exclusion is pinned against the data, not against a curated list: a test requires each legitimate SW07 addable to buy exactly H = 12 new rank and each excluded transform to buy exactly zero, alone and all three together.

    When the decomposition recomputes, and what invalidates it. The whole thing is one synchronous useMemo on the main thread — there is no worker and no backend, because the largest system on the shipped menu is 84 × 84 (seven observables × twelve quarters). It re-runs when any of open, the observables array, the decompIrf unit pool, the named set or hasDeviation changes. Upstream of those, observables is rebuilt from path, the resolved common-observable column indices, the native availability flag, the added-observable list, the measurement-error slider and the spec ids; path itself is selected from driversInput by the source (scenario or external forecast) and the domestic/global mode. So every scenario edit, every GVAR solve, every external-forecast import and every drift change flows through setDriversInput and re-solves the decomposition — which is exactly why the memo opens with if (!open) return { d: null, error: null }. The drawer stays mounted in ScenarioBar and driversInput is republished on every drag tick, so without that guard a closed drawer would re-solve an 84 × 84 system per frame for a panel rendering nothing. Two further invalidations are worth knowing: changing the bloc or its spec re-hydrates the entire configuration (model, named set, observables, view) from the per-bloc localStorage key gmaps-drivers-model:<bloc>, and a shrinking budget clamps the named set — a bloc without the native columns drops the budget from 7 to 3, and the clamp fires whether or not the drawer is showing.

    Build time versus run time. Nothing about the lens menu is computed in the browser. The index generator app/scripts/build_drivers_index.mjs is run by hand — it is not part of next build — and at build time it determines the usable shock set per model (all three common observables present and a stacked H = 12 norm ≥ 1e-9), the dropped shocks and why, the collinear pairs, the FRB/US collinearity clusters, the validated default cluster naming, and the sha256 of every shipped file; it copies class_maps.json in verbatim. At run time the drawer fetches index.json once on first open and each model's IRF file once on selection, caches both in component state, and does only the deconvolution and the display mapping. The app never reads anything under pipeline/ at runtime — class_maps.json is the single source of truth for class membership and is amended there, not in the app. The payload cost is 36 KB for the index plus 215 KB for the default SW07 lens; either 54-shock FRB/US lens adds about 10.7 MB, which is why a failed IRF fetch is recorded per model and offers an explicit Retry rather than being swallowed. These files go over the wire as plain JSON — unlike companion_draws and the GVAR coupling artifact, there is no client-side decompression step.

    Remark 1 (the class-view licence has THREE coordinates). classViewLicensed(model, observableKeys, namedShocks) returns true only when the model is US_SW07, the watched observables contain all of {output, inflationq, interest, dc, dinve, dw, labobs}, and the named shocks contain all of {interest_, eb, fiscal_, eqs, ea, epinf, ew}. All three are gated because pipeline/bench_class_recovery.m held all three fixed: its passing cell is SW07 at q = 7 with K = 7, every usable column of that model's class map, where it measures 100% class-total recovery and 0% off-class leakage. Un-naming a single shock revokes the licence, and it must: the missing shock's energy is redistributed across the classes that remain, which is precisely what the off-class-leakage criterion measures. The third argument is required rather than optional so that a caller who forgets it gets a compile error instead of silently re-opening that hole. The standing guard asserts the two constants against literal bench coordinates and includes a negative case for each of the seven droppable shocks, so widening either constant turns the test red.

    Remark 2 (CMR14's "families" are a grouping, not a licensed class split). CMR14 ships a class map and the drawer renders it as Monetary/Demand/Supply/Financial families, but the bench refused it: under the shipped solver it recovers those class totals in 78% of test instances against its 90% bar. The drawer discloses that number verbatim on screen. Never present the families as classes, and never extend classViewLicensed to reach them.

    Remark 3 (FRB/US clusters are chained, not mutually parallel). The two 54-shock FRB/US lenses group their shocks into connected components of the |cos| > 0.95 graph, labelled by the largest member's equation name. Collinearity is not transitive, so two members of the same component can sit well below 0.95 against each other; they are chained through collinear links. The composite column clusterCompositeIRF builds is therefore the genuine first principal component of the member set (200 power iterations, seeded from the largest-norm member, sign fixed by a positive projection on it), not a proxy for an already-parallel bundle. Naming a cluster names one column, so the budget counts clusters, not members. Write it this way; do not write "pairwise near-parallel".

    Remark 4 (a full-rank Θ is not evidence a naming is usable). Most cluster triples pass the rank test while being badly conditioned. The build-time scan checks every triple through the shipped solver against the 1e-6 same-model-recovery criterion and ships only the winner as defaultNamed: 123 of 1,771 triples pass for US_FRB22 and 122 of 1,330 for US_FRB22_var. The drawer warns whenever the user leaves that default. Conditioning is what matters here, and rank does not imply it.

    Four display-side facts belong with the drawer rather than here, and are set out with their reasoning in MODULES.md Remarks 5–8. In short: when rank ≥ rows — almost every shipped configuration, including the US default at 84/84 — the residual is identically zero by construction and is evidence of nothing; at K = q the measurement-error slider cannot move the solution, because scaling a square system's rows cancels, and it is disabled there; the "Deviation from baseline" view auto-follows the main display but always draws the panel's rate deviation, whereas the panels' "% vs base" mode defaults to a level sub-mode, so the two can be in different units; and the shares strip is a norm share of contribution paths, not a forecast-error variance decomposition, so it can never show two contributions offsetting each other. Do not describe any of these four the other way round in a caption, a tooltip or a commit message.

    13. Conventions to respect (a checklist before you commit)¶

    1. Don't hardcode variable indices. Read n from companion_mean.json, fiscal indices from fiscal_meta.json, GVAR indices from IDX.
    2. Respect the data space. A stray ×4 or /100 between level and growth space will diverge forecasts silently — the canary tests catch it.
    3. The GVAR bloc set is data-driven (35 blocs: endogenous US + EA + 33 RoW), not a hardcoded list. Never hardcode a subset like ['US','EA','JP'] — read ROW_COUNTRIES / COUPLED_COUNTRIES / IDX (live, set by configureGVARTopology) or iterate the active candidates from gvarLoader.ts. Note the US is now in the fixed point (COUPLED_COUNTRIES, gated by US_ENDOGENOUS): US pins are NOT free — they change the US smoother and thus M, so they enter the coupling-cache key and the pin-structure signature. A leftover pilot subset loop in the band request builder once silently dropped some blocs' own-pins (band on baseline while the line followed the propagated path); that class of regression is invisible to tsc and only shows on the dropped blocs.
    4. gvarPins persists across setCountry — by design.
    5. Exact MATLAB replication when porting an estimator — no shortcuts; flag and ask if unsure.
    6. The green gate is mandatory before deploy — and it is two halves (npm test + npm run test:heavy), not one vitest run. See §11.
    7. Never widen a Drivers licence without a bench row behind it. classViewLicensed gates on three coordinates — model, watched observables, named shocks (§8c Remark 1) — and each matches a configuration bench_class_recovery.m actually ran. The same discipline applies to the addable-observable exclusions, the |cos| > 0.95 flag and the shipped defaultNamed cluster triple. If a change makes a reading available in a configuration no bench covers, it is a licence widening even when nothing looks broken on screen, and the drivers tests are written to go red on it.
    8. Drivers is read-only with respect to the forecast. driversInput flows ChartGrid → store → drawer and stops there. Do not let the drawer write scenario state, and do not let ChartGrid import it (§8c).
    9. Read data only through the pack. Never fetch() a data file directly or import one into app code for runtime use — go through dataManifest.ts (fetchJSON/fetchGzJSON), so it is hash-checked and served from the right source (web or desktop data folder). Never compile in a date: use lastHistOf / qoyNextOf / offsetLabel (set from the manifest). Never edit a shipped data file by hand, and never regenerate an existing pack id in place — re-run the step that produces the file, then pack-build --pack-id <new id>.

    13a. Known issues & limitations (flagged-for-fix, NOT yet fixed)¶

    These are flagged-but-unfixed at the current deployment — document them honestly; do not treat the affected output as verified. The module-reference MODULES.md § Known issues carries the file:line detail; the short forms:

    1. CN fiscal debt — inflation double-count (RESOLVED 2026-06). The CN debt roll-forward used to read Δ(GDP) + Δ(deflator) against an already-NOMINAL GDP_CN, double-counting inflation. The surgical CN-only re-estimate replaced GDP_CN with real GDP (spec.json var 0 = "CN Real GDP …"), so the growth term is now the correct real-GDP + price nominal growth, as for the other economies. (CN's price column in the fiscal block is CPI_CN.)
    2. [OBSOLETE — longRunTilt.ts removed; superseded by the driftSetter.ts anchor, §8a]. The former entropic tilt did not filter non-finite moments: an unstable draw's non-finite long-run moment NaN-poisoned the softmax weights and silently emptied the anchor band. The driftSetter.ts display translation does no per-draw reweighting and is not subject to this failure mode.
    3. Only a console-level ρ(M) < 1 divergence guard on the live closed-form solve. When the endogenous Neumann iteration does not converge, solveGVARClosedFormEndo computes ρ(M) and runGvarSolve treats ρ ≥ 1 (or a non-finite residual) as DIVERGED: it logs a console warning and does not cache the result (gvarSolve.ts ~1801–1808, runGvarSolve.ts ~269). There is still no on-screen warning, so a refit with ρ(M) ≥ 1 would show a wrong path to the user. ρ is shipped in the artifact (0.971875 in the deployed pack) and must be checked when the coupling is rebuilt (§12a step 4).
    4. Conditional band uses the FILTERED, not DK-smoothed, covariance. conditionalForecast returns the smoothed MEAN but the FILTERED variance, so the band is overstated for quarters that precede a future pin (the smoother would tighten them). Mean correct; band conservative. (kalman.ts:405.)
    5. Positional meta indices (STALE-POSITIONAL-INDEX) — mitigated, not removed. fiscal_meta.json and external_meta.json still store positional column indices, which go stale on any variable-order change (the EA/UK debt-explosion cause; the Oct 2026 external fx mis-pointing). port_gvar_exports.py now regenerates both by variable id; blocs copied raw need node pipeline/fix_fiscal_meta_indices.mjs and node pipeline/fix_external_meta_indices.mjs. fiscal-meta-indices.test.ts and data/meta-column-indices.test.ts guard them. (§7.)
    6. The Drivers caveat over-claims for US_FRB08. For any lens outside the eight models bench_simple_decomp.m ran, the drawer's bottom caveat falls back to "what backs it is a build-time check that the shipped default naming recovers a known shock sequence to 1e-6". That build-time scan runs only for clustered models, so it exists for the two 54-shock FRB/US lenses and not for US_FRB08, which is in the menu with two shocks, no bench row and no scan. The sentence is therefore true for two of the three lenses it is shown on. Do not repeat the build-time-check claim for US_FRB08 in any document until either the scan covers it or the caveat splits again. (DriversDrawer.tsx, the BENCH_VALIDATED_MODELS fallback branch; §8c.)
    7. Three numbers in the Drivers source comments do not reproduce. The SW07 column norms quoted as "0.41 vs 3.55" (driversDecomp.ts, bench_class_recovery.m), the CMR14 collinear-pair error range "1.7e-3–9.4e-3", and the FRB22 top-three-by-size failure "1.4e-1" could not be reproduced from the shipped files under an independent solver mirror; they most likely predate the IRF regeneration. In each case the qualitative point is confirmed and the mechanism is real — the norms do differ by about an order of magnitude, a flagged pair can push the recovery error far past 1e-6, and the size-ranked triple does fail — but the three numbers must not be quoted in documentation until the comments are refreshed.

    The two cores:

    1. Out-of-sample forecast horse-race (Part 1). Recursive expanding-window, origins 2010Q1–2024Q4 (drop the 2020 COVID origins for the headline), leak-free ROLLING as-of-t0 trade weights (rebuilt from IMTS bilateral trade ≤ t0 — using the shipped 2021–2023 weights at an early origin would inject future trade structure), targets {real GDP growth, inflation, short rate} for US/EA/JP/UK/CA/CN, horizons h ∈ {1,2,4,8}. COVID-as-missing is re-applied in-sample at every origin whose window spans 2020Q2–Q4.

    2. Endogenous-US spillover analysis (Part 2). The endogenous-vs-frozen conditional-scenario contrast that this repo's gvarSolve.ts already computes is Tier A (the headline, zero new code: solveGVARClosedFormEndo vs the frozen path). GIRF / FEVD / Diebold–Yilmaz connectedness is Tier B — new code in the eval repo (constructible from the exported betahat/Σ + the coupling M), not a call into the shipped solver. The shipped solver computes conditional-mean scenario deltas, NOT GIRFs/FEVD — do not relabel a multi-period rate pin a "shock" or a "GIRF."

    Scoring: CRPS (primary density score) + parametric log-score + PIT/coverage; significance via Giacomini–White (headline, valid under nesting + the expanding scheme), Clark–West (nested point), Diebold–Mariano (non-nested), with Romano–Wolf + Model Confidence Set for multiplicity.

    Headline result (first full pass — 56 origins, 9 models; from results/tables.{txt,json}). AR(p) and the DFM have the lowest point CRPS, BUT the 90% Model Confidence Set tells the publishable story: emgvar_endo is IN the INFLATION MCS at every horizon (h=1,2,4,8) and IN the SHORT-RATE MCS at h=1,2,4 — statistically indistinguishable from the best on the nominal block — while it is OUT of the GDP-GROWTH MCS at h=1 and h=8. emgvar_endo ⪰ emgvar_frozen across the MCS (the endogenous-US design earns its keep — e.g. at RATE h=1 and GROWTH h=4 the endogenous bloc is in the set and the frozen one is removed). The EM-Bayesian treatment decisively beats the textbook OLS classical GVAR: cgvar_a is removed from most MCS sets (GROWTH h=1/4/8, INFL h=4/8, RATE h=8) and carries CRPS/RW up to ~2.5. Best inflation h=1 is emgvar_endo (relRMSE 0.799, CRPS/RW 0.814).

    Honest caveats (must state, verified in the tables). - Draw-based densities are OVER-CONFIDENT. PIT cov90 for emgvar_endo runs ~0.73–0.83 (vs the 0.90 target); the frozen variant is similar. The bands are too tight at the draw counts used. - The parametric log-score column is numerically broken on the under-covered clouds (the LPS(G) entries blow up to ~1e14+). CRPS and the MCS are the robust primaries; treat LPS(G) as unusable.

    Tier-A spillover (eval/tier_a_scenario.mjs, results/tierA/us_rate_100bp.json). A US +100 bp conditional projection shows non-trivial endogenous-only cross-country feedback that the frozen anchor structurally omits (the file's own meta.note: the endo−frozen gap is the RoW→US feedback the frozen anchor cannot represent). BUT the magnitudes are large and sign-flipping across horizons (e.g. the frozen-anchor US/UK growth paths swing to −4.4 / −3.1 at h=20), and it is a multi-period conditional projection, NOT a causal IRF (the file labels itself exactly that). The magnitudes need a validation pass before being headlined — do not over-claim a causal interpretation.
