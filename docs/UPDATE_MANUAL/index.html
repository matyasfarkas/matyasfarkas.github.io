    GMAPS 4.0 — Update Manual¶

    How to keep GMAPS current: data updates, model updates, and new app versions. For two readers: users of the desktop app (sections 1–3) and the maintainer who produces updates (sections 4–9). Section 10 is a reference.

    Applies to GMAPS 4.0.0 and later. Last revised 2026-10-08. The websites run data pack 2026Q2-reest-20261008b (data through 2026Q2, the genuine-data model update of October 2026); the 4.0.0 desktop installer carries 2026Q1-20261006 (section 7.4).

    1. What changed in 4.0, in one page¶

    The data and the model are now separate from the app. Everything GMAPS shows (histories, forecasts, estimated models, uncertainty draws, trade weights) lives in a data pack: a folder of files plus one manifest.json that lists every file with its SHA-256 fingerprint and size. The app checks every file against that list before using it, and refuses a damaged or mismatched file. A problem with the pack as a whole (wrong version, an update made for another release, an unreadable manifest) stops the app with a full-screen message. A single damaged file found later is refused too, but today its message goes only to the browser console (see "Known limits" in section 10).

    That separation means:

    • New data does not need a new app. The maintainer sends an update pack (a small zip); users unzip it into a folder and press Reload.
    • A model update does not need a new app either, as long as the variables stay the same.
    • The dates come from the data itself. Each country's history file records the quarter of its first row (firstQuarter); the last quarter is always first quarter + number of rows − 1. There is no date setting that can drift out of step with the data.

    Why the last point matters (what went wrong in September 2026). Two model updates (22 and 23 September) replaced each country's data with fresh model exports. A model export ends at the estimation end, 2025Q4. The July data shift had added 2026Q1, and that row was silently lost. But a separate date setting still said "2026Q1". For about two weeks, the US, the euro area, Japan, the UK and 31 other economies were shown one quarter late, the 15 seasonal economies had their quarterly pattern applied one quarter off, and the published 2026Q1 data were missing. Nothing failed, because the only check that compared rows with dates ran after a data shift, never after a model update.

    4.0 fixes the cause, not just the symptom:

    • the date is computed from the data (no label to forget);
    • after every model update one command dates the new exports from the estimation panels and re-applies the data shift (npm run data:model-update -- --then-shift);
    • an offline calendar check compares the dated rows with the estimation panels the models were fitted on. It runs on every build and refuses to ship a mis-dated pack.

    2. Installing GMAPS 4.0.0¶

    Windows (x64)¶

    1. Get GMAPS_4.0.0_x64-setup.exe (536 MB; or the no-install GMAPS_4.0.0_x64-portable.exe, 530 MB) from the release page, and compare its SHA-256 with SHA256SUMS.txt (PowerShell: Get-FileHash .\GMAPS_4.0.0_x64-setup.exe). The data built into 4.0.0 run to 2026Q1 (data pack 2026Q1-20261006). The websites already show the October 2026 model update (data to 2026Q2); see section 7.4 for how it reaches the desktop app.
    2. Double-click it. Windows SmartScreen may warn that the app is unrecognised (it is not code-signed). Click More info → Run anyway.
    3. GMAPS needs Microsoft Edge WebView2, which is part of Windows 10/11. On an older or stripped-down machine without it, install the "Evergreen WebView2 Runtime" from Microsoft.

    Windows on a Mac (Parallels/UTM on Apple silicon). That Windows is the ARM edition. It runs the x64 app through Windows' built-in x64 emulation. That works, but it is slower than a native build. A native ARM64 Windows build can be made on request.

    macOS¶

    Build it on a Mac from the repository (cd app && npm install && npm run tauri build), or use a .dmg if one is provided. The app is unsigned: the first time, right-click → Open.

    Where the app keeps its data folder¶

    System Data folder (created by Open data folder)
    Windows C:\Users\<you>\AppData\Roaming\io.github.matyasfarkas.gmaps\gmaps-data
    macOS ~/Library/Application Support/io.github.matyasfarkas.gmaps/gmaps-data
    Linux ~/.local/share/io.github.matyasfarkas.gmaps/gmaps-data

    You never need to type these: Settings → Data pack → Open data folder creates and opens it.

    3. Updating the data on your computer (users)¶

    3.1 See which data you have¶

    Open Settings (bottom left) → Data pack. It shows the pack name, how recent the data are ("data through 2026Q1"), and where they come from:

    • bundled with the app: the data that came with your installation;
    • update pack (data folder): an update you installed. The line also says how many files came from the update and how many from the built-in data;
    • external pack (data folder): a complete pack you installed.

    3.2 Install an update pack¶

    You receive a file such as 2026Q2-20261115_for_4.0.0.zip. The part after for_ is the app version it is made for.

    1. Settings → Data pack → Open data folder.
    2. Extract the contents of the zip into that folder, so that manifest.json sits directly in it (not in a sub-folder). On Windows, "Extract All" proposes a new sub-folder named after the zip. Either change the destination to the data folder itself, or move the extracted files up one level afterwards. If an older update is already there, let the new files replace the old ones.
    3. Press Reload (in the same panel). The Data pack line should now show the new pack and the new "data through" quarter.

    The app checks the whole update before showing anything: - every file it ships, and every file it reuses from your built-in data, must match its fingerprint; - an update made for a different app version is refused, with a message that names the version it needs.

    3.3 Go back to the built-in data¶

    Delete or rename manifest.json in the data folder, then press Reload. Nothing else is needed; the other files there are ignored.

    3.4 Messages and what to do¶

    What you see What it means What to do
    "This update pack (…) was built for the data pack X, but the data built into this app is pack Y" The update is for a different app version Ask for the update for your version, or a full pack
    "… could not be read from the data folder — the pack copied there looks incomplete" A file of the update is missing Extract the zip again, completely, into the data folder itself
    "… sha256 mismatch …" (today in the browser console only; see section 10, Known limits) A file was changed or damaged Extract again; if it persists, ask for a new pack
    "This data pack requires the tool to be at least vX" The data need a newer app Install the newer app version

    In every case you can go back to the built-in data (3.3).

    4. The ideas behind updates (maintainer)¶

    Term Meaning
    Data pack app/public/data/: all data files + manifest.json (fingerprint, size, and the dating of every country). The web build serves it; the desktop app has it built in.
    Calendar firstQuarter in each bvar/<C>/historical_levels.json. Last quarter = firstQuarter + rows − 1. The only source of dates.
    Panel quarter The common last quarter of the 35 coupled GVAR economies (they share one row grid). The 17 euro members follow it.
    Data shift Within the year: add the newly published quarter (US observed; other published values pinned; the rest nowcast through the model and shown in amber). The estimated model is frozen.
    Model update Once a year: re-estimate (MATLAB) and re-export. Changes the model fingerprint.
    Update pack Only the files that changed against the pack built into a released app version, plus a full manifest. One per recorded release.
    Release record pipeline/released_packs/<version>.manifest.json: the manifest of the pack built into that app version. Needed to cut update packs for it.
    Model fingerprint Hash of all GVAR companion_mean.json files. Unchanged by a data shift, changed by a model update. Archived vintages carry it, so the /monitor page knows whether a comparison is a pure data change.

    Golden rules

    1. Never edit dates by hand. There is nothing to edit; the data carry their own calendar.
    2. After every model export, date and verify it before anything ships (section 7). The calendar check must pass.
    3. Never hand-edit a shipped data file to "fix" a value. Re-run the step that produces it.
    4. Pushing to main deploys the websites. Commit and push are always a deliberate human step; no script does them.
    5. Never fill a missing value. A quarter that is not published stays missing: the model draws it, and the app shows it in amber as a model estimate. The data list every such cell (estimation_mask.json, nowcast provenance, coverage flags).
    6. Never regenerate a pack under an existing pack id. Any change after pack-build gets a new id; an old id with new contents would turn every cached copy into a fingerprint error.

    5. Monthly: is an update due?¶

    cd app
npm run data:check

    It asks the release calendars (FRED, OECD via DBnomics) for the latest quarter of a small set of sentinel series (US, euro area, Japan, Korea, China GDP; the US 10-year yield) and compares it with the panel quarter.

    Exit Meaning Next step
    0 Nothing new for every sentinel yet Nothing
    10 A new quarter is published for every sentinel: a data shift is available Section 6
    11 A full new calendar year is published beyond the model's estimation end: a model update is due Section 7

    A GitHub Action (.github/workflows/data-check.yml) runs this on the 5th of every month and fails on purpose (so GitHub emails the repository owner) when 10 or 11 comes back. It never changes data.

    6. Quarterly: the data shift¶

    6.1 One command¶

    cd app
npm run data:shift -- --asof 2026Q2            # dry run: every gate, nothing written
npm run data:shift -- --asof 2026Q2 --commit   # the real run

    Or let the scheduler do it: npm run data:auto checks and, if a shift is due, runs it with --commit (exit 0 nothing due, 10 shift done, 11 model update due, 1 error). It never commits or pushes. Example crontab line (6:00 on the 5th of each month):

    0 6 5 * *  cd /path/to/repo/app && npm run data:auto >> ~/gmaps-auto.log 2>&1

    6.2 What the shift does, step by step¶

    # Step Writes
    — Pre-flight: the at-rest dating is coherent (every history has a calendar; coverage + pack manifest agree). Stops otherwise. nothing
    0 Archive the current data as a vintage (pipeline/vintages/<quarter>_shipped[_<model>]) archive
    1 Counterfactual: the old data completed to the new quarter with no new information (the /monitor baseline) archive
    2 US: append the observed quarter from FRED (gated; revisions accepted and logged) US history
    2.5 Realized pins: every other published value for the new quarter (FRED mirrors of Eurostat, ECB, BoE, BoJ …), each gated against the shipped overlap pipeline/realized_pins_<q>.json
    3 Cross-economy nowcast: one coupled model solve fills every remaining gap (flagged model-implied → amber in the charts) staging
    4 Publish staging into app/public/data histories, forecasts
    5 Euro members follow the euro area (skipped for a member already at the quarter) member histories
    6 Re-simulate the uncertainty bands from the posterior draws (seeded) bands
    7 Coverage manifest (dates from the data; the expected quarter is asserted) coverage_manifest.json
    8 Release-impact record for /monitor release_impact.json
    9 Vintage-comparison artifacts for /monitor vintages/
    10 Re-stamp the data pack (manifest.json, pack id <quarter>-<yyyymmdd>) manifest.json
    11 Verification gate: dating coherent everywhere, every economy on the new quarter, no empty last-row cells, nowcast converged, every file re-hashed, calendar check nothing — stops on any problem
    12 One update pack per recorded app release → packs/<pack>_for_<version>.zip packs/

    6.3 After the run (deliberate)¶

    1. npm test — the full test suite.
    2. npm run build — its prebuild re-verifies the whole pack (pack-verify --full).
    3. Look at /monitor and a few charts: the history should end at the new quarter, the first forecast quarter should be the one after it, and amber dashed tails mark model-implied values.
    4. git add app/public/data pipeline/vintages pipeline/realized_pins_<q>.json && git commit
    5. When you decide to update the websites: push to main (this deploys).
    6. Send the update pack(s) from packs/ to desktop users (section 3.2). A quarterly data shift changes few files: the 2025Q4 → 2026Q1 shift (Oct 2026) produced an update pack of 297 files, 3.1 MB zipped.

    6.4 If it stops half-way¶

    Every step is safe to repeat. Re-run the same --commit command; finished work is skipped or harmlessly redone. To undo a run completely: git checkout -- app/public/data (and remove the new pipeline/vintages/* folders) — there is no date to restore.

    7. Yearly: the model update (re-estimation)¶

    When data:check returns 11 (normally in Q2, once the previous year is fully published):

    cd app
npm run data:q1prep -- --year 2026     # confirms the year is published; prints the runbook

    The October 2026 update is the worked example. The scripts it ran are in docs/reest-2026/runs/ (with a README giving the order), the method decisions in docs/reest-2026/PLAN.md, and the review in docs/reest-2026/REVIEW.md. Each MATLAB setting is explained in docs/REESTIMATING_MODELS.md.

    7.1 Data¶

    1. Rebuild every economy's panel from its source registry (pipeline/sources/registry/), using genuine data only, to the latest published quarter. Unpublished cells stay missing (golden rule 5).
    2. Rebuild what is derived from the data: the fiscal stock-flow adjustment and the euro-member panels (docs/reest-2026/RECIPE_live_model.md §3, step 0).

    7.2 Estimation (MATLAB)¶

    1. The 35 coupled economies: pipeline/export_bvar_gvar24_loop.m with BVAR_DIFF_GP=1 US_ENDOGENOUS=1 NDRAWS=1000 MAXIT=30 BVAR_SEED=1 GVAR_FIXHYPER=1 GVAR_NOFILL=1 (runs/run_gvar35b.sh). It iterates until the foreign ("star") variables stop changing. In 2026 it converged at sweep 6, after about 1 h 40 min on a 4-core machine.
    2. GVAR_NOFILL=1: missing cells at the start, in the middle and at the end stay missing, and the sampler draws them. The export lists them in estimation_mask.json.
    3. GVAR_FIXHYPER=1 with BVAR_SEED: every sweep uses the same random numbers. Without this, sweeps are not comparable and the loop does not converge.
    4. The 17 euro members: pipeline/export_bvar_euro_redesign.m for each member, with BVAR_DIFF_GP=1 GVAR_NOFILL=1 CGL_FIXED_COMPANION=1 (runs/run_members.sh). A re-run gives identical results.

    7.3 Into the data pack (run in app/ unless shown otherwise)¶

    1. Port. Copy the 35 GVAR exports raw, including estimation_mask.json. Port the members with pipeline/port_gvar_exports.py. Then run node pipeline/fix_fiscal_meta_indices.mjs and node pipeline/fix_external_meta_indices.mjs. They re-find the fiscal and external column positions by variable name. In 2026, adding a deflator column moved them (runs/port_to_app.sh).
    2. Date. Run node scripts/stamp_calendar.mjs, then npx vite-node scripts/build_coverage_manifest.mjs --panel-quarter <Q>.
    3. Coupling. Run npx vite-node scripts/precompute_gvar_coupling.mjs. ρ(M) must be below 1 (2026: 0.9719).
    4. Ragged edge. Run npx vite-node scripts/nowcast_complete.mjs --write --baselines --out <dir>, check that it converged, and publish the coupled economies from <dir> (runs/stageA.sh).
    5. Members and debt. Run apply_member_completion.mjs, then roll_d0_forward.mjs. The second rolls debt starting points forward to the panel quarter and keeps the published value as d0_observed.
    6. Forecasts, bands, draws. Run regen_gr_baselines_via_loader.mjs and regen_gvar_bands.mjs, then node scripts/gzip_companion_draws.mjs.
    7. Pack.
      • Run build_coverage_manifest.mjs --panel-quarter <Q> and vintages_publish.mjs.
      • Stamp the pack under a new id: node scripts/pack-build.mjs --pack-id <Q>-reest-<yyyymmdd>.
      • Verify: node scripts/verify_cutoffs.mjs --allow-ragged --dating-only, then npx vite-node scripts/pack-verify.mjs --full (runs/stageB.sh).
    8. Review. Run npm test and npm run build. Compare old and new (docs/reest-2026/compare_old_new.py). Open the built site in a browser. Commit; push only when you decide to.

    The steps above apply when the panels already end at the latest published quarter, as in 2026: the model is fitted to the latest data. If the exports end earlier (a model estimated to a year end), run npm run data:model-update -- --then-shift instead of steps 6 and 8, after step 7. It dates each export from its estimation panel; a country it cannot place stops the run, and nothing is guessed. It then re-stamps and verifies the pack, and shifts the panel to the latest published quarter.

    7.4 Getting a model update to desktop users¶

    A model update changes most files (every model and every band file), so its update pack is large: hundreds of MB, mostly the uncertainty draws. Also check whether the new data rely on app code newer than the installed version.

    The October 2026 pack relies on two display changes made after 4.0.0: every effective exchange rate is shown as an index level, and interior model-estimated quarters get amber marks. The 4.0.0 app accepts the pack (minToolVersion is 4.0.0), but it would show those two things the old way. A new app version (section 8) is the clean route. If you send an update pack instead, tell users about that difference.

    Status on 2026-10-08: neither has been done. Desktop users have 2026Q1-20261006.

    8. Releasing a new app version¶

    1. Set the version in app/package.json, app/src-tauri/tauri.conf.json and app/src-tauri/Cargo.toml (all three the same). If the data now need a feature of this version, raise MIN_TOOL_VERSION in app/scripts/pack-build.mjs and re-run it (pack-verify check [4] guarantees a pack never requires a newer app than the one it ships with).
    2. Make sure app/public/data is final and verified: npm run data:verify.
    3. Record the release (needed so future data shifts can cut update packs for it): node scripts/pack-record-release.mjs --version 4.0.0 → commit pipeline/released_packs/4.0.0.manifest.json.
    4. Build:
    5. Web: npm run build (the website deploy does this in CI on push to main).
    6. Windows x64 (cross-compiled on the Linux workstation): see app/src-tauri/README.md ("Windows x64 — cross-compiled from Linux"): npm run build:tauri, then XWIN_ACCEPT_LICENSE=1 npx tauri build --runner cargo-xwin --target x86_64-pc-windows-msvc --bundles nsis, then run makensis on the generated script with NSISDIR set (Tauri's own Linux NSIS step ignores it).
    7. macOS: on a Mac, npm run tauri build.
    8. Publish the installers (GitHub Release on the private repository) with their SHA-256 checksums.

    9. When something fails¶

    Message Cause Fix
    pre-flight FAILED — fix the at-rest dating first The coverage or pack manifest disagree with the data's calendars (e.g. files were replaced without re-stamping) npm run data:model-update
    … history has no calendar (stamp it …) A freshly exported history without firstQuarter npm run data:model-update
    cannot place its history on the calendar No history row equals the country's estimation panel at its last quarter: the export and the panel do not belong together Check that the export is from that panel; only with independent evidence: node scripts/stamp_calendar.mjs --first <Q> --blocs <C>
    MISDATED — the row dated X equals the panel at Y The calendar is wrong for that country Find out why (wrong firstQuarter?) and fix; never ship
    the coupled GVAR blocs do not share one last quarter Some coupled economies were shifted and others not Re-run the shift, or the model update
    coverage_manifest.json says … but the data end … The coverage manifest is stale npx vite-node scripts/build_coverage_manifest.mjs (or data:model-update)
    pack-verify … sha256 mismatch / listed but missing on disk A data file changed after the pack was stamped, or is missing Re-run node scripts/pack-build.mjs after the intended change; restore an unintended one
    pack needs tool ≥ X but this tool is Y MIN_TOOL_VERSION is above the app version Lower it, or release the newer app
    The web build fails in prebuild pack-verify --full found a mismatch (the deploy refuses to ship data the app would refuse) As above

    10. Reference¶

    Commands (run in app/)¶

    Command What it does
    npm run data:check Is a shift (10) or a model update (11) due?
    npm run data:shift -- --asof <Q> [--commit] The quarterly data shift (dry run without --commit)
    npm run data:auto Unattended: run a due shift (--commit); exit 0/10/11/1
    npm run data:model-update [-- --then-shift] After a re-export: date, re-stamp, verify (then shift)
    npm run data:q1prep -- --year <YYYY> Re-estimation readiness + runbook
    npm run data:verify verify_cutoffs + pack-verify --full
    node scripts/stamp_calendar.mjs --check Every country's calendar + calendar-check verdict
    npm run pack:build Re-stamp manifest.json
    npm run pack:verify -- [--full] [--dir <update> --bundled <built-in>] Verify a full or an update pack
    npm run pack:delta -- --base <manifest> --out <dir> --zip Cut an update pack by hand
    npm run pack:record-release -- --version <x.y.z> Record a released app's built-in pack

    What the checks guarantee¶

    • pack-verify --full (also in every web build): every listed file exists, has its recorded size and SHA-256; no unused plain twin of a .gz is listed; the GVAR weights match the coupling they were made with; the pack does not require a newer app than its own; the dating in the manifest equals each history's calendar; the calendar check confirms the dating against the estimation panels.
    • verify_cutoffs (end of every shift): every history has a calendar; all economies end at the panel quarter; the coverage and pack manifests agree with the calendars; no empty cells in the last row; the nowcast converged.
    • In the app: the data are refused with a full-screen message if the pack is incompatible, an update was cut for a different version, or any file fails its fingerprint.

    Files¶

    File Role
    app/public/data/manifest.json The pack: version fields, panel quarter, per-country dating, every file's fingerprint
    app/public/data/coverage_manifest.json Per-variable coverage, sources, flags (drives the Data & coverage page and the amber tails)
    app/public/data/bvar/<C>/historical_levels.json History (100·log for log variables) + firstQuarter
    app/scripts/lib/calendar.mjs Calendar arithmetic + the calendar check
    pipeline/vintages/ Archived vintages for /monitor (each with vintage_meta.json: origin, kind, model fingerprint)
    pipeline/released_packs/ Built-in manifests of released app versions
    packs/ (not in git) Update packs to send

    Known limits¶

    • The list of countries is still compiled into the app: a pack can update existing countries but not add one.
    • Files are fingerprinted one by one; the manifest itself is not yet signed (the format leaves room for it).
    • There is no "import zip" button: users extract the zip into the data folder.
    • The app still contains a build-time copy of the trade weights and of six economies' model descriptions (gvarSolve.ts). They are start-up defaults only. Once the pack loads, the app uses the pack's own, fingerprinted weights, and the list of countries comes from the compiled roster (first point above).
    • A file that fails its fingerprint check (or fails to download) after start-up is refused, but the message goes only to the browser console:
    • the single-country view keeps showing what it had;
    • the global model leaves that country out of the coupled system;
    • a weights file that fails is replaced by the build-time copy.

    pack-verify --full runs on every web build, so a damaged file cannot ship. What remains is a file damaged in transit or on a desktop disk. The fix is to show the message on screen and stop, as the start-up checks do (open, October 2026). - A within-year shift re-syncs only the previous quarter to the latest source vintage. After a large source revision, the quarter before keeps the older vintage, so the growth rate across that seam mixes vintages. (Example, now resolved: after the US annual revision of Sep 2026, US 2025Q4 GDP growth showed 1.6% annualised against 0.2% on current data. The October 2026 rebuild took every series from its current vintage, and the data now show 0.2%.) - Resolved in October 2026: the euro members had run an older model generation. They were re-estimated with the rest, in growth rates.
