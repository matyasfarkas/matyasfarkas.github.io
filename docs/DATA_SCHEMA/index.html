    Data Contracts & JSON Schemas¶

    This page is the reference for every JSON contract the app reads from app/public/data/bvar/ — and, since the experimental Drivers panel shipped, from app/public/data/dsge/census/ as well (§13). It is the authority for what each file contains, the exact field names, the array shapes, and the conventions (variable ids, block tags, transformations, the 6-significant-figure compaction). It complements — and does not duplicate — the prose in the companion docs:

    • ARCHITECTURE_FOR_AI.md — how the compute engine uses these files (§4–§10).
    • README.md / USER_GUIDE.md — overview & UI.
    • fiscal-block-methodology.md — the math behind fiscal_meta.json.
    • drivers-decomposition.md — the math and the licence behind the Drivers payload (§13).
    • ADDING_A_COUNTRY.md / REESTIMATING_MODELS.md — how the files are produced.

    If a fact here disagrees with the code, the code wins — these contracts are verified against the live files (app/public/data/bvar/US, …/EA, …/DE, …/CN, …/gvar) but the data is re-ported on every re-estimation. Values quoted below are from data pack 2026Q2-reest-20261008b (Oct 2026 genuine-data re-estimation, panel ending 2026Q2) unless labelled as history.

    Since 4.0.0 every file on this page belongs to a data pack (§1.1): the app reads it only through the pack's manifest.json, which lists each file with its SHA-256 and size. The data and the estimated model are therefore separate from the tool — a new pack updates them without a new app version.

    1. Where the files live¶

    Each economy is one directory app/public/data/bvar/<CC>/ keyed by ISO-2-ish country code (US, EA, JP, …; EA = euro-area aggregate). The cross-country GVAR coupling lives in app/public/data/bvar/gvar/.

    app/public/data/
  manifest.json                      THE PACK: every file's path + sha256 + bytes, dating per economy (§1.1)
  coverage_manifest.json             per-variable sources, coverage, flags, model-implied quarters
  nowcast_provenance.json            which history cells the coupled nowcast supplied (model-implied)
  default_anchors.json, cookbook/, dsge/, vintages/, weo_forecasts.json, …   (also in the pack)
  bvar/
    US/   EA/   JP/  …               one directory per economy (52: 35 coupled GVAR blocs + 17 euro members)
      spec.json                      variable manifest (ids, blocks, transforms)
      companion_mean.json            posterior-mean VAR (betahat, sigmahat)
      companion_draws.json.gz        flat posterior draws, gzipped (lazy-loaded, large); the plain
                                     .json is a local by-product, not in git and not in the pack
      baseline.json                  baseline fan in DISPLAY/GROWTH space
      baseline_levels.json           baseline fan in LEVEL space
      historical.json                last 40q in DISPLAY/GROWTH space
      historical_levels.json         last 40q in LEVEL space + firstQuarter (the calendar, §7)
      transformations.json           per-variable 'log'|'lin' list
      estimation_mask.json           history cells the estimator drew as missing data (§7.1)
      fiscal_meta.json               the 41 economies with a fiscal block (§9)
      external_meta.json             the 47 economies with the external-accounts satellite (§9.1)
    gvar/
      weights_24bloc.json            35-bloc trade-weight matrix + topology source (§10)
      coupling_default.json.gz       gzipped precomputed (I−M)⁻¹ coupling artifact (§11)

    Loader (app/src/lib/data/loader.ts). Every read goes through the pack: loadJSON(path) is dataManifest.fetchJSON(path), which looks the file up in manifest.json, fetches it, and checks its byte length and SHA-256 before parsing (a mismatch is an error, the file is never used, and the error is shown on screen by DataErrorBanner). Optional files go through fetchJSONIfInPack: a file the pack does not list is absent (null, a NotInPackError underneath); a listed file that fails is an error and fails the load. loadBVARData(country) fetches spec/companion_mean/baseline/historical eagerly, then optionally baseline_levels/historical_levels/fiscal_meta/external_meta (a missing file → null, normal for economies without a fiscal block or external satellite). companion_draws.json.gz is loaded lazily by loadCompanionDraws(country) only when Compute is clicked (it is the largest file — tens of MB): the compressed bytes are hash-checked, gunzipped with the browser's DecompressionStream, and the flat arrays converted once to Float64Array for fast indexing and zero-copy structured-clone into the band worker.

    1.1 manifest.json — the data pack¶

    Written by app/scripts/pack-build.mjs, checked by app/scripts/pack-verify.mjs (every web build runs pack-verify --full in prebuild), read at runtime by app/src/lib/data/dataManifest.ts. The manifest itself is the root of trust: it is fetched without caching and not hash-checked (a detached signature is a planned upgrade; today the format only leaves room for it).

    Field Type Meaning
    schemaVersion string "major.minor" contract version ("2.0"). The tool refuses a different major, or a minor below the one it needs
    minToolVersion string oldest app version that may read this pack ("4.0.0"); an older app shows a full-screen block
    packId string the pack's name, e.g. "2026Q2-reest-20261008b". Packs are immutable: a changed pack gets a new id
    previousPackId string | null the pack it was cut from, if any
    generatedAt, generatedBy string build time and builder
    panel.lastHistQuarter "YYYYQn" the common last historical quarter of the coupled panel ("2026Q2")
    blocs.<CC> object per economy: lastHistQuarter, qoyNext (seasonal phase of the first forecast quarter, null if no dummies), qoyNextEstimation, seasonalRows, shiftQuarters (quarters added after estimation; 0 in this pack), estimationEnd
    gvar.weights {path, sha256, bytes} the trade-weights file the coupled solve uses
    gvar.coupling {path, sha256, bytes, inputs:{weightsSha256, companionSig}} the coupling artifact and the weights it was built from (pack-verify requires inputs.weightsSha256 = gvar.weights.sha256; the app ignores a mismatched coupling)
    files.<logical> {path, sha256, bytes, inherit?} every file of the pack (1,997 in this pack). For .gz files the hash is of the compressed bytes. inherit: true appears only in an update pack: the file is taken from the app's built-in pack, and only if that copy has the same hash and size
    delta object, optional update packs only: the built-in pack they were cut against (basePackId) and how many files they ship / reuse

    Where the bytes come from. On the web, from <base path>/data/. In the desktop app, from the pack built into the app — unless the user's data folder (<appDataDir>/gmaps-data, opened by Settings → Data pack → Open data folder) contains a manifest.json, in which case that folder is used, with the same checks. Rollback = delete that manifest.json. Full user and maintainer guide: UPDATE_MANUAL.md.

    Dating. When the manifest loads, dates.setPanelDates(manifest) sets each economy's last historical quarter from blocs.<CC>.lastHistQuarter (§7) and checks each seasonal economy's qoyNext against the tool's own recomputation — a mismatch stops the load. There is no compiled date in the tool.

    2. Cross-cutting conventions¶

    2.1 The data space (log / lin)¶

    Every variable has a transformation:

    transformation stored as chart display
    "log" 100·log(level) q/q annualised growth = 4·Δ(100·log level)
    "lin" the level itself (rates, ratios, %-of-GDP, sentiment indices) the level as-is
    • *.json files in display/growth space (baseline.json, historical.json) carry the already-differenced 4·Δ(100·log level) for log vars and the level for lin vars.
    • *_levels.json files carry 100·log(level) for log vars and the level for lin vars (this is the "level space" that feeds the fiscal recursion, the GVAR solver, and the level-display fans).

    This is the single most bug-prone convention in the codebase — a stray ×4 or /100 between the two spaces diverges forecasts silently. The canary test scenario-scale-convention.test.ts pins it.

    2.2 The 6-significant-figure compaction¶

    Precision depends on how a bloc's files reach the app. In the deployed pack the 35 coupled GVAR blocs are copied raw from the estimator's export, at full double precision (docs/reest-2026/runs/port_to_app.sh step 1; e.g. US betahat[0][0] = 3.6855229634904627). The 17 euro members go through pipeline/port_gvar_exports.py, and those eight per-bloc files are rounded to 6 significant figures and serialised as compact JSON (separators=(",",":"), no whitespace) by pipeline/port_gvar_exports.py (sig6 → float(f"{x:.6g}"), recursing through lists/dicts via compact). The compacted set is exactly the FILES list in that script: spec.json, companion_mean.json, companion_draws.json, historical.json, historical_levels.json, baseline.json, baseline_levels.json, transformations.json. Integers, None, strings, booleans, and ±inf/NaN pass through (0/±inf/NaN map to 0/themselves). So in a member's files expect values like 4.16884, -5.50528 (AT) — never full double precision. Do not assume either precision when validating; read the file.

    coupling_default.json.gz is also 6-sigfig: its builder (app/scripts/precompute_gvar_coupling.mjs) rounds M/invImM/rhoSpectral with round6 = x => Number(x.toPrecision(6)) before gzip.

    Two more files are NOT 6-sigfig — they are written full precision by their own builders and are not in port_gvar_exports.py's FILES:

    • fiscal_meta.json — built with the panel by pipeline/sources/build_panel.py (derived.fiscal4; pipeline/country_rawdata/fiscal_meta_<CC>.json, members in pipeline/euro_redesign_staging/<CC>/), then d0 is rolled to the panel end by app/scripts/roll_d0_forward.mjs; d0 is full double precision, sfaDefault has 3 decimals.
    • weights_24bloc.json — all 35 receiver rows carry full double precision.

    Do not assume 6-sigfig when validating these two files.

    2.3 Variable ids, blocks, isFinancial¶

    Variable ids are stable string keys (e.g. GDPH, POLRATE, HICP_EA, GLB_OIL, ROWDEM_US). Suffixes encode role:

    • GLB_* — a global common (the 4 US-determined commons, ids GLB_OIL/GLB_USLR/GLB_USBAA/GLB_USEQ). These ids are shared across the 35 GVAR blocs (US, EA, JP, …). The 17 euro members carry no global columns.
    • ROW{DEM,INF,FIN}_<CC> — a GVAR bloc's 3 trade-weighted stars.
    • ROWEA_{GDP,HICP}_<CC> — a euro member's 2 rest-of-euro-area aggregates (block:'row').
    • _<CC> on a domestic var (GDP_EA, RATE_DE) — the country's own series.

    Each variable also carries a block tag that drives the GVAR/fiscal topology (read at runtime by configureGVARTopology / deriveBlocIdx in gvarSolve.ts — never hardcode indices):

    block meaning where it appears
    domestic the bloc's own endogenous macro/financial vars every model
    fiscal the 4 fiscal drivers {FREV_GDP, FPEXP_GDP, EFFI, SFA} the 41 economies with a fiscal block (24 GVAR blocs + all 17 euro members)
    row GVAR: the 3 trade-weighted stars ROW{DEM,INF,FIN}_<CC>; euro member: the 2 rest-of-euro-area aggregates ROWEA_{GDP,HICP}_<CC> all 35 GVAR blocs (incl. endogenous US) and all 17 members
    global the 4 US-determined commons (oil, US 10y, US Baa, US equity) the 35 GVAR blocs (as GLB_*)
    external euro-area-shared regressors (e.g. for AT: POLRATE_AT, EACORP, RATE_AT, YIELD10_DE) the 17 euro members

    History: until the euro-member redesign the members were "FSAP standalones" with global columns under US ids (WTI_US, …) and a us block. No shipped spec uses those any more.

    A bloc is GVAR-active iff its spec.json carries the 3 block:'row' stars and it has a row in weights_24bloc.json (euro members have neither). The US is endogenous iff its spec carries the 3 ROW*_US stars and the weights file has a US row — this sets the module flag US_ENDOGENOUS. See ARCHITECTURE_FOR_AI.md §5/§5a.

    isFinancial (boolean) flags financial variables (rates, spreads, FX, equity, house prices, leverage, oil). It drives display units and the COVID treatment (financials are kept observed through 2020Q2–Q4 while macro vars are masked).

    2.4 Exchange rates — one direction everywhere (rise = appreciation)¶

    Every exchange-rate variable in the published data — NEER_<CC> in each economy, the US FXTWM, and China's real index REER_CN — is an effective exchange-rate index of the domestic currency: a rise is an appreciation, a fall is a depreciation, in every economy. Sources: BIS broad nominal index (WS_EER), IMF (EER; AU, CL, CR, NZ) and Eurostat (ert_eff_ic_q, 42 partners; the euro-area members) — all quote the index this way; the direction was verified on the data (see pipeline/sources/registry/README.md, Conventions). Until the 2026 re-estimation, NEER_CA and NEER_EA were in fact bilateral rates against the US dollar (domestic currency per dollar: a rise was a depreciation); data packs from the 2026 re-estimation on use the harmonised direction for every economy. In log space a 1-unit move is a 1% appreciation (positive) or depreciation (negative).

    3. spec.json — the variable manifest¶

    The authoritative list of variables in fixed column order. The engine reads n and the per-variable metadata; it is index-agnostic otherwise (resolves fiscal/GVAR columns by id, not position).

    Field Type Shape Meaning
    n int scalar number of endogenous variables (= length of variables)
    variables array [n] one entry per variable, in column order
    variables[i].id string stable variable key (column identity)
    variables[i].name string human-readable label (for the UI dropdown)
    variables[i].transformation "log"|"lin" data-space (§2.1)
    variables[i].isFinancial bool financial-var flag (§2.3)
    variables[i].prior "RW"|"WN" prior-mean family on the own first lag (§3.1): "RW" = random walk (own-lag prior mean 1, the default); "WN" = stationary white-noise (own-lag prior mean 0 → mean-reverting). In the deployed growth-rate model "WN" marks real GDP, the headline price and the GDP deflator (estimated as growth rates) and the three fiscal GDP-ratios (FREV_GDP,FPEXP_GDP,SFA); everything else is "RW"
    variables[i].block string topology tag (§2.3)
    seasonalRows int scalar optional, top level (not per variable): 0 (legacy/default, absent) or 3 — the number of quarterly seasonal-dummy rows the estimator inserted into betahat for an NSA-seasonal bloc (§3.3).
    qoyNext int scalar optional, top level: quarter-of-year (1..4) of the first forecast row on the estimation grid. Present only when seasonalRows>0. The app ignores this value and recomputes the phase from its own date grid — see §3.3.

    Example (US, n=40, abridged — first/price/fiscal/global/star columns — a non-contiguous selection; the shown entries are NOT columns 0…11):

    {
  "n": 40,
  "seasonalRows": 0,
  "variables": [
    {"id":"GDPH","name":"Real Gross Domestic Product","transformation":"log","isFinancial":false,"prior":"WN","block":"domestic"},
    {"id":"JGDP","name":"Gross Domestic Product: Chain Price Index","transformation":"log","isFinancial":false,"prior":"WN","block":"domestic"},
    {"id":"GLB_USLR","name":"US 10Y Treasury yield (%)","transformation":"lin","isFinancial":true,"prior":"RW","block":"global"},
    {"id":"FREV_GDP","name":"Federal Receipts (% of GDP)","transformation":"lin","isFinancial":false,"prior":"WN","block":"fiscal"},
    {"id":"FPEXP_GDP","name":"Federal Primary Expenditure (% of GDP)","transformation":"lin","isFinancial":false,"prior":"WN","block":"fiscal"},
    {"id":"EFFI","name":"Federal Effective Interest Rate (% p.a.)","transformation":"lin","isFinancial":true,"prior":"RW","block":"fiscal"},
    {"id":"SFA","name":"Stock-Flow Adjustment (% of GDP)","transformation":"lin","isFinancial":false,"prior":"WN","block":"fiscal"},
    {"id":"GLB_OIL","name":"WTI crude oil, WTISPLC q-avg ($/bbl)","transformation":"log","isFinancial":true,"prior":"RW","block":"global"},

    The US carries the 4 globals as its own endogenous vars (cols where block:'global') plus its 3 ROW*_US stars (cols 37–39, block:'row') — this is what makes the US endogenous. A RoW bloc (EA, n=26) also carries the globals as its own columns; the coupled solve ties every bloc's copy to the single US-determined path. A euro member (DE, n=23) carries no globals and no trade-weighted stars: its foreign side is the external euro-area columns (POLRATE_DE, EACORP, RATE_DE) and the two rest-of-euro-area aggregates (ROWEA_GDP_DE, ROWEA_HICP_DE, block:'row').

    3.1 The prior field — "RW" (default) vs "WN" (stationary fiscal ratios)¶

    variables[i].prior selects the prior mean on each variable's own first lag in the GLP/Minnesota prior. It takes exactly two values:

    prior own-first-lag prior mean implied behaviour who carries it
    "RW" 1 (random walk — the historical default) the series can drift at the long end (a unit-root prior centre) every other variable
    "WN" 0 (white noise — stationary) the series mean-reverts to its in-sample mean FREV_GDP, FPEXP_GDP, SFA (all 41 fiscal economies); and, in the deployed growth-rate model (BVAR_DIFF_GP=1), real GDP, the headline price (CPI/HICP; JGDP for the US) and DEFL_<CC> — these are estimated as quarterly growth rates, so it is their growth that mean-reverts

    Growth-rate (DIFF_GP) columns. Under BVAR_DIFF_GP=1 (both deployed estimators, Oct 2026) the estimator first-differences real GDP and the price series to 4·Δ(100·log) and leaves every other column in levels. It exports the equivalent level VAR (one more lag — hence lags = 4 in the shipped files), so transformation stays "log" and the app's level-space engine is unchanged. The "WN" tag on those columns refers to the differenced series.

    Why this exists. Under a pure "RW" prior the fiscal GDP-ratios (revenue, primary expenditure, stock-flow adjustment) inherited a unit-root centre and drifted over the 20-quarter projection — e.g. US federal receipts stuck at ~19% of GDP instead of reverting to their ~17.4% in-sample mean. Switching them to "WN" centres the own-lag prior at 0 so the ratios mean-revert to their sample means at the long horizon, which is the economically correct stationary behaviour for a bounded share-of-GDP. EFFI (the effective interest rate) stays "RW" — it is a slow-moving level, not a bounded ratio. This change is committed (6f0161a/22250be/e38673a); at the time it was a no-op (byte-identical export) for the blocs without a fiscal block.

    The mechanism (verified end-to-end in the estimator).

    1. Spec → pos. The MATLAB estimators read the per-variable prior string out of spec.json and build the index vector of stationary columns:
    2. pipeline/export_bvar_gvar24_loop.m (statCols=find(Spec.Prior(keep)=="WN")', on the kept domestic block; stars are appended after and are always "RW").
    3. pipeline/export_bvar_euro_redesign.m (the 17 euro members; statCols = find(Prior=="WN")', plus the differenced GDP/price/deflator columns under BVAR_DIFF_GP). The older export_bvar_euro_fsap.m uses the same rule. Both resolve via a robust priorsfrom(...) helper (handles MATLAB's jsondecode dropping a prior field that is present on only some variables; absent → all-"RW").
    4. pos → cgl_bvarV5. statCols is threaded as the 3rd positional argument (stationary) of BVAR/MFBVAR/cgl_bvarV5.m, where pos=stationary (line 19) and passed on as 'pos',pos to bvarGLPmf.
    5. pos → prior mean = 0. In BVAR/MFBVAR/GLPreplicationWeb/bvarGLPmf.m the own-first-lag prior block is built from diagb: 
      diagb=ones(n,1);
diagb(pos)=0;            % zero the own-first-lag prior mean for the WN columns
b(2:n+1,:)=diag(diagb);  % default columns keep prior mean 1 (random walk)
      So a "WN" column gets own-lag prior mean 0 (stationary); every other column keeps 1 (the random-walk centre). A bloc with no "WN" column has pos=[], so diagb=ones(...) unchanged → identical to the historical default.
    6. Round-trip. On export each estimator re-stamps the per-variable prior back into spec.json from statCols (if any(statCols==i), v.prior='WN'; else v.prior='RW'), so the shipped spec always reflects the prior actually used.

    Deployed prior assignment for the fiscal block (verified in the live specs — identical in all 41 fiscal economies):

    Variable block prior rationale
    FREV_GDP (revenue % GDP) fiscal "WN" bounded ratio → mean-revert
    FPEXP_GDP (primary expenditure % GDP) fiscal "WN" bounded ratio → mean-revert
    SFA (stock-flow adjustment % GDP) fiscal "WN" bounded ratio → mean-revert
    EFFI (effective interest rate % p.a.) fiscal "RW" slow-moving level, not a bounded share
    everything else (macro, financial, stars, globals) any "RW" random-walk default

    3.2 The isFinancial flag — coherence audit¶

    isFinancial (§2.3) gates two things: the chart display units and the COVID treatment — financial variables are kept observed through the 2020Q2–Q4 data-augmentation window, while macro variables (and the two macro stars ROWDEM/ROWINF) are masked and DK-completed (Durbin–Koopman simulation smoother). A miscoded flag therefore changes both the picture and the estimate.

    Two coherence fixes are baked into the deployed specs (verified across all blocs):

    • GLB_USEQ (US equity) and GLB_OIL (oil) are isFinancial:true everywhere. Both are market-priced and continued trading through 2020 — keeping them observed (not imputed) through the COVID window is the correct treatment. (The earlier GLB_OIL:isFinancial=false was incoherent and has been corrected.)
    • Canada's IP_CA is a log-LEVEL. It is now transformation:"log", isFinancial:false, block:"domestic" — a proper 100·log(level) series (its q/q annualised growth is the 4·Δ display form), not a level-vs-growth mismatch.     3.3 The seasonalRows / qoyNext fields — quarterly seasonal dummies (NSA blocs)¶

    Blocs with not-seasonally-adjusted (NSA) series (NSA HICP/CPI, unemployment LR, house prices, India GOV, UK/KR SFA, and every even-interest bloc) are estimated with deterministic quarterly seasonal dummies so the within-year cycle is a bounded deterministic term rather than a spurious near-Nyquist companion root. Two top-level fields record this on the shipped bloc files:

    File · field Values Meaning
    spec.json.seasonalRows 0 (absent/legacy) or 3 number of quarterly-dummy rows the estimator added
    spec.json.qoyNext 1..4 (present only when seasonalRows>0) quarter-of-year of the first forecast row on the estimation grid (mod(qlast,4)+1)
    companion_mean.json.seasonalRows 0 (absent/legacy) or 3 the SAME count, so betahat can be sliced (§4)

    Which blocs carry seasonalRows=3 (set by pipeline/export_bvar_gvar24_loop.m GVAR_DUMMY_BLOCS + pipeline/export_bvar_euro_redesign.m EURO_DUMMY_MEMBERS; the Oct 2026 runs are in docs/reest-2026/runs/): in pack 2026Q2-reest-20261008b, 34 economies — the 17 coupled blocs {CL, CN, CO, CR, EA, HK, ID, IN, IS, JP, KR, MX, NO, PE, TR, UK, ZA} and all 17 euro members. The manifest lists them (blocs.<CC>.seasonalRows). Every other bloc ships seasonalRows=0 (or omits it) and uses the layout without dummy rows.

    Effect on the betahat row layout (§4). A seasonal bloc's betahat has k = 1 + seasonalRows + n·lags rows: row 0 = constant, rows 1..3 = the γ_Q2/γ_Q3/γ_Q4 quarterly-dummy coefficients (Q1 base), rows 4..k−1 = the lags blocks of n lag coefficients. The dummy rows are inserted between the constant and the lags — a consumer that assumes lag coefficients start at row 1 would read the wrong columns, which is why seasonalRows is shipped alongside betahat. For a legacy bloc (seasonalRows=0) the layout is the historical k = 1 + n·lags with lags at row 1.

    The app RECOMPUTES qoyNext; it does NOT trust the one in spec.json. A within-year data shift moves the app's display origin past the estimation grid (by shiftQuarters in the manifest), so after a shift spec.json.qoyNext is behind what the forecast needs. The runtime always derives the phase from its own date grid via dates.qoyNextOf(country) (quarter after lastHistOf, wrapped 1..4; lastHistOf comes from the pack manifest) and feeds it to BVARParams.qoyNext. When the manifest loads, setPanelDates also compares that value with the manifest's declared blocs.<CC>.qoyNext and stops the load on a mismatch. In pack 2026Q2-reest-20261008b no quarter was shifted (shiftQuarters = 0), so all three agree. See ARCHITECTURE_FOR_AI.md §5·EM.s and MODULES.md (kalman.ts).

    12. Validating a freshly ported bloc¶

    A quick sanity pass when adding or re-porting a bloc (paths absolute under app/public/data/bvar/<CC>/):

    1. spec.n === companion_mean.n === companion_draws.n, and length(spec.variables) === n.
    2. companion_mean.betahat is [1 + seasonalRows + n·lags][n]; sigmahat is [n][n] (seasonalRows = companion_mean.seasonalRows else spec.seasonalRows else 0; §3.3).
    3. companion_draws.beta_shape === [1 + seasonalRows + n·lags, n, n_draws] (same seasonalRows, inferred from beta_shape[0] on the draws side); sigma_shape === [n, n, n_draws]; length(beta) === product(beta_shape); length(sigma) === product(sigma_shape).
    4. baseline.mean and baseline_levels.mean are [horizon][n] with all of q05/q16/q84/q95 present (q50 optional).
    5. historical.data and historical_levels.data are [n_periods][n].
    6. transformations.transformations has length n and matches spec.variables[i].transformation.
    7. A fiscal bloc additionally ships fiscal_meta.json with all six idx keys in range [0, n) AND each idx resolving to the correct variable id (idx.revenue → FREV_GDP, etc.); likewise external_meta.json (idx = idxIds). For blocs copied raw (not through port_gvar_exports.py), run node pipeline/fix_fiscal_meta_indices.mjs and node pipeline/fix_external_meta_indices.mjs (the STALE-POSITIONAL-INDEX gotcha, §9).
    8. After porting, regenerate coupling_default.json.gz (§11) so modelSig matches.
    9. Re-stamp and verify the pack: node scripts/pack-build.mjs --pack-id <new id> then npx vite-node scripts/pack-verify.mjs --full (the pack is immutable — a changed pack gets a new id).

    Then run the green gate (npx tsc --noEmit && npm test && npm run test:heavy) — the canary tests (gvar-coupling-artifact, gvar-convergence, gvar-derived-topology, scenario-scale-convention, fiscalAccounting) encode the contracts above.

    13. The Drivers payload — app/public/data/dsge/census/ (experimental)¶

    The Drivers drawer answers one question about a path the app is already showing: which sequence of a chosen DSGE model's own structural shocks would have produced it? It reads that model's impulse responses out of the files documented here, solves for the shock sequence over the first twelve forecast quarters, and draws the contributions as a stacked chart in the main panel's units, with an explicit residual for the part the named shocks cannot reproduce. The models come from the Macroeconomic Model Base (MMB), the public archive of estimated and calibrated macro models.

    Two things about the claim, stated here rather than at the end. The feature is experimental, and its reading is model-conditional: it reports the mix of model M's shocks that reproduces the path, not what caused the path, and it is not model-free shock labelling. Its validation is same-model recovery — generate a path from a model's own known shock sequence, decompose it under that same model, and check the contribution paths come back — which speaks to the estimator, not to the model and not to the world. The two benches that establish it, pipeline/bench_simple_decomp.m and pipeline/bench_class_recovery.m, travel with the code, and their transcripts are docs/paper/simple_decomp_results.txt and docs/paper/class_recovery_results.txt.

    13.3 index.shockClasses — the embedded shock-class map¶

    pipeline/_shockbench/class_maps.json is the single source of truth for which of a model's shocks belong to which economic class.     Remark 2 (The class view is licensed on three coordinates, not one). A class map existing in this file does not mean the app will aggregate by it. classViewLicensed(model, observableKeys, namedShocks) returns true only when the model is US_SW07, the watched observables contain all seven of {output, inflationq, interest, dc, dinve, dw, labobs}, and the named shocks contain all seven of {interest_, eb, fiscal_, eqs, ea, epinf, ew}. That is the one cell of bench_class_recovery.m that passes both of its pre-stated criteria under the shipped solver, and the bench held all three coordinates fixed: it ran that observable set with K = 7, every usable column of SW07's class map. Un-naming a single class member revokes the licence, because the missing shock's energy is redistributed over the classes that remain — which is exactly what the bench's off-class-leakage criterion measures. The third argument is required, not optional, so a caller who forgets it gets a compile error rather than a silently re-opened hole. Everywhere else the Classes toggle is greyed with its reason shown.

    Remark 3 (CMR14's "families" are not a licensed class split). The drawer shows CMR14's own class map as an organising grouping of its shocks, labelled "Monetary family", "Demand family" and so on, and discloses the number the bench refused it on: bench_class_recovery.m recovers those class totals in 78% of test instances against its 90% bar. Present them as a grouping, never as classes. The point applies more sharply to censusGeneric, which has no consumer in the app at all.

    13.4 clusters and defaultNamed — the FRB/US lenses¶

    The two 54-shock FRB/US entries carry two extra fields, because their individual _aerr equation-residual shocks are not separable in the three common observables: 109 of the 1,431 shock pairs exceed |cos| = 0.95 for US_FRB22, 117 for the VAR-expectations variant. Rather than offer a naming the response space cannot support, the builder groups the shocks by the structure that space actually has.

    A cluster is a connected component of the |cos| > 0.95 collinearity graph, computed by union-find over the same collinearPairs list the index ships, and labelled by its largest member — largest stacked three-observable, twelve-quarter response norm, with the label taken as the mnemonic minus its _aerr suffix. Clusters are ordered by size descending, then id ascending, and a singleton is labelled by its member's mnemonic rather than as a cluster.

    Field Type Meaning
    clusters[i].id string equation name of the largest member, e.g. "hqlfpr", "eco_l"
    clusters[i].label string "<id> cluster (<n> shocks)", or the bare member mnemonic for a singleton
    clusters[i].members string[] the component's shock names
    defaultNamed string[] cluster ids the drawer names by default

    US_FRB22 has 23 clusters over its 54 shocks: hqlfpr (17 members — the financial/housing blob, which contains fiscal_, so the fiscal shock is not separately nameable in cluster mode), eco_l (10, the spending block), lww_l (4, wages/labour force/ECI), fpxrr_l, pegfr_l and pxr_l (2 each), and 17 singletons including interest_. US_FRB22_var has 21 clusters: hqlfpr (18), eco_l (10), lww_l (4), trci (3), fpxrr_l and pxr_l (2 each), and 15 singletons. The shipped partitions are cross-checked against the shipped pair list, as a set of sets, by a licence test.

    Naming a cluster names one column: the app builds the members' first principal component from their unit-normalised stacked response paths and decomposes on that. So the naming budget counts clusters, not members.

    defaultNamed records the naming the builder validated. pickDefaultNamed scans every possible triple of clusters through the shipped solver over 20 deterministic sparse-truth seeds against a 1e-6 same-model-recovery criterion, and picks among the passers by maximising member coverage, then preferring a triple containing the interest_ cluster, then taking the first in cluster order. For US_FRB22 that is [hqlfpr, interest_, pcer_l], covering 19 of 54 shocks, with a worst measured recovery error of 2.53e-9. For US_FRB22_var it is [eco_l, interest_, ki_l], covering 12 of 54, at 1.32e-7 — passing, but only an order of magnitude inside the criterion.

    Remark 4 (Cluster members are chained, not mutually parallel). Collinearity is not transitive, so two members of one component can sit well below 0.95 against each other: they are linked through a chain of collinear neighbours, not pairwise near-parallel. The composite column is therefore a genuine first principal component of the member set, not a stand-in for an already-parallel bundle. Never describe a cluster as a set of mutually parallel shocks; the drawer does not, in any of the three places it explains them.

    Remark 5 (A full-rank Θ does not mean a naming is usable). Only 123 of the 1,771 possible cluster triples for US_FRB22, and 122 of the 1,330 for US_FRB22_var, pass the 1e-6 recovery criterion. Most of the rest are badly conditioned while still passing the rank test — the obvious triple of the three largest clusters is among the failures — which is why defaultNamed exists and why the drawer warns as soon as the user departs from it. Any other naming is exploratory, and nothing in this payload licenses it.

    13.5 <MODEL>.json — the per-model IRF file¶

    Every menu model, whether copied into census/ or indexed in place under irfs/, has the same shape: a two-level object, shock name → observable name → response array.

    irf[shock][observable][h + 1]  =  R_{shock,observable}(h),   h = 0 … 19

    where irf is the parsed file, shock one of the top-level keys, observable a model observable name, and h the response horizon in quarters. Every array is length 21. Index 0 is the pre-impact zero, so horizon h lives at index h+1 — this mirrors the benches' MATLAB s.obs(2:H+1) exactly, and an off-by-one here silently shifts every contribution by a quarter. The engine uses indices 1…12 (h = 0…11); the remaining eight are shipped but unused by Drivers.

    Every shock in a file carries the same observable key set, verified across all twelve shipped files, so the observable count is a property of the model rather than of the shock. Every file exposes the three common observables output, inflationq and interest; the rest are the model's own variables and observation equations, from 38 keys for CA_LS07 up to 454 for the FRB/US linearisations. Values are full double precision (Remark 1) and serialised with compact separators.

    The top-level key set is the model's full shock list, which is a superset of the index's shocks array: US_SW07/SW.json has eight keys and the index lists seven, the difference being the zero-response em recorded in dropped. A consumer should iterate index.models[M].shocks, not Object.keys(irf).

    Example 2 (Reading one response out of a shipped file). We read SW07's output response to its monetary-policy shock over the first five quarters, the way the engine does. interest_ is the MMB-injected monetary shock, output the common percent log-level column, and the leading 0 is the pre-impact entry we skip.

    python3 - <<'PY'
import json
irf = json.load(open('app/public/data/dsge/irfs/US_SW07/SW.json'))
print(irf['interest_']['output'][1:6])
# [-0.16580525975153695, -0.24963376942455795, -0.28143044022347269,
#  -0.28161868356000974, -0.26371718338798245]
PY

    A contractionary policy shock lowers output on impact and the trough arrives around the fourth quarter — the shape one expects, which is the cheapest sanity check that the file, the indexing convention and the sign convention are all as documented.

    Example 3 (Checking a shipped file against its index entry). Two claims the index makes about each file can be checked without running the app: the content hash and the usable-shock list. We verify both for every menu entry. The loop resolves meta.file under app/public/data/ by stripping the leading /data/, exactly as the loader does at runtime.

    python3 - <<'PY'
import json, hashlib
idx = json.load(open('app/public/data/dsge/census/index.json'))
for name, meta in idx['models'].items():
    path = 'app/public/data' + meta['file'].replace('/data', '', 1)
    got  = hashlib.sha256(open(path, 'rb').read()).hexdigest()
    irf  = json.load(open(path))
    assert got == meta['sha256'], name
    assert set(meta['shocks']) <= set(irf), name
    print(f"{name:14s} ok  {len(meta['shocks'])}/{len(irf)} shocks usable")
PY

    All twelve entries pass on the shipped tree, printing 7/8 for SW07 and 9/10 for CMR14 — the dropped zero-response columns — and n/n for everything else. The hash half of this check also runs inside the licence suite, so a file swapped without rebuilding the index turns the suite red.

    13.6 Provenance — where each file actually comes from¶

    Three distinct production paths feed this payload, and they are worth keeping apart because they differ in what a "shock" is.

    The injected MMB census (six models). EA_SW03, EA_SWW14, CA_LS07, HK_FP13, BRA_SAMBA08 and UK_SM11 are census runs of MMB models under the Taylor rule, carrying the MMB's injected generic shocks — interest_, fiscal_, markup_, demand_, wage_, inv_, flex_, pref_, tech_, of which each model supports the subset its equations admit (three to six). These are common shock slots imposed on heterogeneous models so that the same names mean the same thing across the menu; they are not the models' own estimated structural shocks. Their sourceNote is absent and their source is pipeline/census_irfs/<MODEL>/Taylor.json.

    The FRB/US export with native residual shocks (two models). US_FRB22 and US_FRB22_var are census runs of the same FRB/US linearisation — the second under VAR expectations rather than model-consistent ones — exposing 54 shocks: the two injected ones plus the model's own 52 _aerr equation residuals. These are native to FRB/US, one per stochastic equation, which is what makes the clustering of §13.4 necessary and the class layer rule-based. Their sourceNote is "MMB census run", and both are sourced from pipeline/census_irfs/ — note that US_FRB22's source directory is US_FRB22_mcap, since it is the same linearisation as the two-shock entry below, run differently.

    MMB rule files, indexed in place (four models). US_SW07, US_CMR14, US_FRB08 and US_FRB22_mcap are read from the irfs/ tree the app already ships, written by pipeline/compute_irfs_mmb.m, which drives the MMB CLI internals under MATLAB and Dynare 6 and requests IRFs by shock name. US_FRB08 and US_FRB22_mcap were produced with that script's default options.shocks = char('interest_', 'fiscal_') and therefore carry only those two, which is why US_FRB22_mcap is menuHidden: the 54-shock census entry supersedes it in the menu, but the index keeps it because the licence fixtures reference it. US_SW07 and US_CMR14 were regenerated by this feature with their full native shock sets — SW07's seven usable plus the zero-response em, CMR14's nine plus e_term — and the commit records that the interest_ and fiscal_ columns the policy-counterfactual panel reads are unchanged to ~5e-11, re-export rounding only.

    The hash discipline follows the split. For the eight census files the builder takes sha256 from pipeline/census_irfs/MANIFEST.json and refuses to ship a file whose bytes do not match the manifest; for the four rule-file entries it hashes the shipped file itself and records that in sha256Source. Either way the index states where its own hash came from.

    Remark 6 (pipeline/census_irfs/ is not on the deployed branch). The census tree, the 97-model IRF census that produced it, and the research memo on the failed model-free identification gate all live on explore/shock-benchmark under research hold. What ships is the copied output, the two validation benches, their transcripts and class_maps.json. In practical terms: node app/scripts/build_drivers_index.mjs cannot be run from the deploy branch — it fails on its first read of MANIFEST.json — and six of the eight rows of bench_simple_decomp.m, plus the FRB/US row of bench_class_recovery.m, need files that are not here either. The shipped census/<M>.json copies are byte-identical to their census sources by the hash gate, so the benches could be pointed at them, but both scripts hard-code the pipeline/census_irfs paths; that is a source edit, not a command-line option.

    13.7 Regenerating and validating the payload¶

    The index and the census copies are built by one script, run from anywhere:

    node app/scripts/build_drivers_index.mjs

    It reads pipeline/census_irfs/MANIFEST.json and each census model's <srcDir>/Taylor.json, pipeline/_shockbench/class_maps.json, and the four app/public/data/dsge/irfs/<M>/SW.json files; it writes app/public/data/dsge/census/index.json and copies each census Taylor.json to app/public/data/dsge/census/<name>.json. Everything in index.json — usable shocks, dropped shocks, collinear pairs, clusters, defaultNamed — is recomputed from the response files on each run, so amending class_maps.json or replacing an IRF file means rebuilding the index.

    The two validation benches print to stdout and write no files; the committed transcripts under docs/paper/ are captured output, so regenerating them means redirecting:

    matlab -batch "run('pipeline/bench_simple_decomp.m')"   > docs/paper/simple_decomp_results.txt
matlab -batch "run('pipeline/bench_class_recovery.m')"  > docs/paper/class_recovery_results.txt

    Example 4 (What a consumer should check after touching this payload). The index is built by hand and sits in neither npm test nor the deploy workflow, so its own build-time checks are not standing gates. The standing gates are in the licence suite, and they are what a reviewer should run.

    cd app && npm test          # 26 licence tests across drivers-decomp{,-v2,-v3}.test.ts

    Four of those assertions are provenance rather than mathematics, and they are the ones that catch a stale payload: index.shockClasses must equal pipeline/_shockbench/class_maps.json exactly; every shipped file must hash to the sha256 its index entry records; index.horizonQuarters must equal the engine's DRIVERS_H; and the shipped cluster partition must reproduce the connected components of the shipped pair list. A payload rebuilt without re-running them, or amended in the app instead of at the source, will pass tsc and fail here.

    Beyond the suite, three properties are worth confirming by hand on a new or replaced file, since they are assumptions the engine makes rather than things it checks: every shock carries the three common observables; every response array is length 21 with a zero at index 0; and the observable key set is identical across the shocks of one file.

    13.8 What this payload does not establish¶

    Stated plainly, because the contract is easy to over-read. The files describe responses and metadata; they license nothing on their own.

    • The claim is model-conditional. A different lens gives a different answer, and the lenses are not equally validated: bench_simple_decomp.m ran eight models — US_SW07, US_CMR14, EA_SW03, EA_SWW14, CA_LS07, HK_FP13, BRA_SAMBA08, UK_SM11 — and never ran any FRB/US lens. The FRB/US entries are backed only by the build-time recovery scan behind defaultNamed, which exists for the two clustered models and not for US_FRB08.
    • The validation is same-model recovery. It measures the estimator, not the model and not the world.
    • The class view is licensed at one configuration, on three coordinates (Remark 2). A class map in shockClasses is membership data, not a licence.
    • The clusters are empirical, not economic (Remark 4), and only the shipped default naming carries a recovery check (Remark 5).
    • Where a shock pair is flagged collinear, the split within the pair is not identified.
    • The seven-observable mode that the class licence requires is available on the US bloc only — it needs the BVAR spec columns CH, FNH, LXBC, JGDP and LANAGRA, and of the 52 shipped specs (§3) only US carries all five. Everywhere else the drawer runs at three observables, where no menu configuration licenses a class view.

    14. Out-of-sample evaluation contracts (the em-bayesian-gvar-eval harness)¶

    Scope note. The JSON contracts in §§1–13 are read by the deployed app. The three contracts below are read/written by the separate empirical-evaluation repository em-bayesian-gvar-eval (out-of-sample forecast horse-race + endogenous-US spillover analysis). They live in em-bayesian-gvar-eval/results/ and are not shipped in app/public/data/. The full design is em-bayesian-gvar-eval/docs/EMPIRICAL_PROTOCOL.md (§§0–2). Results are preliminary/forthcoming; the contracts here are stable.

    14.1 weights_asof_<startY>_<endY>.json — rolling as-of trade weights cache¶

    The horse-race is a recursive expanding-window scheme over origins t0 = 2010Q1 … 2024Q4 (2020 COVID origins dropped). A hard look-ahead invariant (EMPIRICAL_PROTOCOL.md §0 invariant #2, decision D11) forbids using the shipped 2021–2023 weights_24bloc.json/weights_full.json at a pre-2020 origin — that would inject future trade structure. Instead the driver resolves, per origin, a leak-free as-of weights file whose IMTS averaging window ends ≤ year(t0), built by matlab/weights/rolling_asof_weights.m (a thin wrapper on the main repo's pipeline/build_trade_weights_full.py — same IMTS pull, EA=G163, mirror fallback for embargoed reporters, <0.05% partner drop + renormalization). Files are cached under results/weights_cache/.

    Two modes (env OOS_WEIGHTS_MODE):

    • fixed (default) — a single pre-sample window (e.g. 2005-2009) used at every origin: provably leak-free (biased toward the past, never the future).
    • rolling — a 3-yr window ending the calendar year before year(t0) (strictly < year(t0), so even Q1 origins use no same-year trade); one IMTS pull per origin-year, cached. This is the rigor robustness variant.

    Schema — identical top-level shape to weights_24bloc.json (§10) but on the headline 6-bloc panel and with a window-specific window string:

    Field Type Shape Meaning
    source string provenance (IMF IMTS, SDMX 2.1 — same string as §10)
    indicators string[] [2] ["XG_FOB_USD","MG_CIF_USD"]
    euro_area_code string "G163"
    window string the as-of window for this file, e.g. "2016-2018 average" — distinguishes cache entries and is copied into each forecast JSON's meta.weightsWindow
    blocs string[] [6] headline panel ["US","EA","JP","UK","CA","CN"] (US first)
    bloc_codes object 6 keys code → metadata map
    note string records the row-normalization, US-as-closed-anchor, <0.05% drop, mirror fallback
    weights object 5 keys (fixed/late files) or 6 keys weights[receiver][partner] = w, zero diagonal, each row sums to 1 over its partners

    Receiver-row count is window-dependent — read defensively. The 2005-2009 (and other early/fixed) files carry 6 receiver rows including a US row (US endogenous, has its own RoW block); some windows (e.g. the 2021-2023 cache entry) carry 5 rows (US is the closed anchor / partner-only at that vintage, no US receiver row). Do not assume a US receiver row exists — resolve by iterating Object.keys(weights), exactly as the GVAR topology code does for weights_24bloc.json. The cached files are 6-sigfig per the IMTS builder; rows sum to 1 up to rounding (e.g. 0.999999).

    Example (weights_asof_2016_2018.json, abridged — note the 5-bloc weights map under a 6-bloc blocs list, because US is partner-only at this window):

    14.2 forecasts/<model>/<origin>.json — per-origin predictive draw clouds¶

    For each (model, origin) the driver (matlab/oos_driver.m → matlab/harvest_forecasts.m) writes one file holding the full predictive draw cloud (not just the mean) for the headline targets, sliced from the estimator's native Dforecast(H, n, nDraws−nBurn). Models are one directory each: emgvar_endo, emgvar_frozen, rw, rw_clim (climatology), arp, sbvar (single-country BVAR, ablation iii), cgvar_a (textbook OLS GVAR, iv-a), cgvar_b (single-pass Bayesian GVAR, iv-b), dfm.

    Field Type Shape Meaning
    model string one of the model tags above
    origin string origin quarter, "YYYY-Qn" (e.g. "2018-Q3")
    blocs object 6 keys per-bloc forecasts (headline panel US/EA/JP/UK/CA/CN)
    blocs[c] object 3 keys one entry per target: GROWTH, INFL, RATE
    blocs[c][t].draws number[][] [m][nh] the predictive cloud: m draws × nh requested horizons, in scored space (4·Δ for growth/inflation, level for rate). m is model-dependent: the Bayesian DK-smoother models (emgvar_endo/emgvar_frozen/cgvar_b/sbvar) keep the post-burn cloud m = nDraws−nBurn (≈100 at nDraws=200); the parametric/OLS/bootstrap benchmarks (rw/rw_clim/arp/cgvar_a/dfm) emit the full m = nDraws (200). Read m = draws.length, never assume it
    blocs[c][t].mean number[] [nh] predictive mean per horizon
    meta object run metadata (see below)

    meta fields (verified in the harvested files):

    meta key Type Meaning
    nDraws int requested NDRAWS (e.g. 200; the kept cloud size m is model-dependent — see the draws row above)
    lags int VAR lag order (3)
    emIters int EM star-loop iterations to convergence at this origin (1 for the MAXIT=1 single-pass ablations; 0 for the non-iterative benchmarks rw/arp/cgvar_a)
    covidInSample bool whether 2020Q2–Q4 ≤ t0 (so the COVID-as-missing mask applied in-sample)
    weightsWindow string the as-of weights window used (copied from §14.1's window)
    seed number per-origin RNG seed (reproducibility; cgl_bvarV5 calls rng default then offsets)
    usEndogenous bool whether the US joined the coupled loop with its own ROW*_US block at this origin (present on the EM-GVAR-family files; may be absent on the simple benchmarks)
    tol number star-convergence tolerance (0.05 sweep / 0.03 final)
    horizon int the estimator's full H (20)
    horizons int[] the scored horizons, in column order, e.g. [1,2,4,8]

    The draws/mean columns are packed DENSELY by REQUESTED horizon, not by a dense 1:H layout. Column j of every draws[k]/mean is horizon meta.horizons[j] — so column 0 = h=1, column 1 = h=2, column 2 = h=4, column 3 = h=8 (for horizons=[1,2,4,8]). Always index horizons through meta.horizons; never assume column j ⇒ h = j+1. (harvest_forecasts.m records this mapping precisely for that reason.)

    (top level) object 6 keys US/EA/JP/UK/CA/CN
    [c] object 3 keys GROWTH, INFL, RATE
    [c][t] object date → number "YYYY-Qn" → realized scalar in scored space

    External-forecast import + full-session files (client-side, not shipped data)¶

    Two user-facing JSON contracts (not part of public/data/), consumed and produced entirely in the browser. Documented here so a third party can generate them programmatically.

    External-forecast import (ControlPanel → External forecasts → Import forecasts)¶

    One source, one bloc. Values are in the chart's display units (q/q-annualised % for log growth/inflation vars, the level in % for lin rates, the index level for level-displayed vars).     GVAR propagation of an external forecast (compute note)¶

    An imported forecast on a linked (GVAR) bloc propagates cross-country. The two conditioning modes take different solve paths: - Exact pins (drag / trust 100%) — the cross-country transmission is linear, so it runs through the pre-built response kernels + the cached coupling inverse (I−M)⁻¹ (coupling_default.json.gz); the closed-form / one-hop-direct solvers apply. Fast and cacheable. - Soft pins (external forecast with uncertainty) — the per-cell measurement variance changes each bloc's smoother gain, which the exact-pin kernels don't represent. So runGVARSolve routes to the iterative solveGVAR (Gauss–Seidel: forecast each bloc, feed partners via the star channel, repeat to a fixed point), threading opts.condVarByCountry[bloc] into each per-bloc conditionalForecast. Exact but not cacheable, so it runs only on the full solve (Compute / Solve full GVAR), not the live preview.

    No external forecast ⇒ condVarByCountry undefined ⇒ the untouched closed-form/direct path (byte-identical; gvar-coupling-artifact / gvar-closed-form-* tests). Propagation + no-op locked by gvar-external-spillover.test.ts.
