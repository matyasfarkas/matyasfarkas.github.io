    Data Refresh — Quarterly-Shift / 2026Q1 Rebase Runbook (no re-estimation)¶

    Current guide: UPDATE_MANUAL.md (§6 is the quarterly data shift). This page is the detailed record of the 2026Q1 shift and the engines behind it; where it describes the panel as it was then (2026Q1 origin, 38 coupled blocs, Israel on its own calendar) it is history. Today (pack 2026Q2-reest-20261008b): 52 economies (35 coupled + 17 euro members), all through 2026Q2; Russia, Argentina and Israel are no longer shipped.

    4.0 (Oct 2026) — the dating steps below changed. There is no date constant any more: each history file carries its own firstQuarter, and the last quarter is always firstQuarter + rows − 1. Steps 11–15 below are the current chain: coverage manifest (asserted) → vintages → data pack (pack-build) → verification (verify_cutoffs + pack-verify --full with the calendar canary) → update packs. The complete, current procedure — including the model-update step that re-applies the shift after a re-estimation — is UPDATE_MANUAL.md. Other mentions of dates.ts/DEFAULT_LAST_HIST_DATE here are history.

    Status: the quarterly-shift procedure is ESTABLISHED and has shipped to production. The 2026 Q1 rebase went live on bvarscenario/main (US observed + cross-bloc nowcast for the rest, per-cell provenance, /monitor release-impact page). This file is the canonical operator runbook for moving the display origin forward one quarter. It complements the design in docs/data-refresh-2026q1-feasibility.md (read that first for the why); this file is the how to run it and the what to check before merge.

    Branch note (historical — effi-even-seasonal-dummies, the seasonal-v2 testing ground): when this runbook was first written that branch sat at the FRESH re-estimation vintage 2025 Q4 (dates.ts DEFAULT_LAST_HIST_DATE = '2025-10-01', shown AS-IS with no 2026 Q1 nowcast rebase) to evaluate the seasonal fix (evened EFFI + seasonal dummies). The shipped / current panel origin is now 2026 Q1 (DEFAULT_LAST_HIST_DATE = '2026-01-01'; coverage_manifest.json panelDefaultLastQuarter = 2026Q1). Running the shift chain below is exactly what promotes a 2025 Q4 branch to that 2026 Q1 origin.

    The method — estimate once, shift quarterly¶

    The companion is estimated once on the 2025 Q4 vintage and then frozen. Within the year the display origin is moved forward one quarter at a time with no re-estimation — the "quarterly data shift". For the 2026 Q1 rebase, 2026 Q1 becomes the LAST OBSERVATION, filled by

    • genuine real-time releases where a bloc is wired (has a live source map — today US, all cells incl. the 4-var fiscal block) or already carries the observed quarter (the new FSAP blocs HK / SG / RO / PE / PH pull current public data, so their 2026 Q1 is mostly observed); plus
    • a cross-bloc G-BVAR NOWCAST for every remaining ragged cell — one coupled GVAR solve conditions each bloc's DK smoother on its own observed cells and carries the wired leaders' 2026 Q1 through the star channel into the laggards' imputed cells. Older ragged blocs get more nowcast fill; the new blocs get little. Imputed cells are treated as data downstream but flagged model-implied per cell in public/data/nowcast_provenance.json — never WEO-extended, never held flat.

    2026 Q2 is then the first forecast quarter. Two seasonal-aware engines do the work:

    • app/scripts/refresh-quarter.mjs — per wired bloc, RE-SYNCS the prior shipped quarter's directly-sourced columns to realized values and THEN appends the genuine observed 2026 Q1 row (self-correcting, not append-only — the prior quarter's displayed q/q-growth row is recomputed against the re-synced levels so growth stays consistent; held GVAR-star aggregates and the fiscal-SFA residual are not re-synced), and RE-PROJECTS the FROZEN companion forward (mean via the DK smoother makeCountryModel/conditionalForecast; bands via the shipped per-draw companion_draws). The re-sync happens only under --accept-revisions (the mode the orchestrator runs). Seasonal-aware: it phases the quarter-of-year deterministic term from --asof itself (qoyNext = (asof.q % 4) + 1), NOT from dates.ts.
    • app/scripts/nowcast_complete.mjs — the cross-bloc completion: one coupled GVAR solve (completeRaggedPanel) fills every ragged 2026 Q1 cell across all blocs. Seasonal-aware via a per-bloc quarter-of-year ledger (qoyEndByCode).

    No estimation runs. cgl_bvarV5.m is never touched. companion_mean / companion_draws(.gz) / spec / transformations / coupling / weights stay frozen — so modelSig is unchanged and the shipped (I−M)⁻¹ coupling artifact stays valid (no 19-min rebuild). Per bloc the shift rewrites only: historical.json, historical_levels.json, baseline.json, baseline_levels.json, and (fiscal blocs only) fiscal_meta.json d0 — plus the single load-bearing date constant DEFAULT_LAST_HIST_DATE in app/src/lib/dates.ts (bumped to '2026-01-01'; IL keeps its own-calendar override).

    0. Who gets genuinely re-pulled vs nowcast-filled¶

    The shift no longer needs a source registry for every bloc. Two paths fill the new quarter:

    • Wired blocs — genuine observed data via refresh-quarter.mjs. The script only re-pulls a bloc that has a SOURCES[<CC>] entry (live source IDs + transform + window, honouring the R6 ID traps). Today only US is mapped (all cells incl. the 4-var fiscal block); extend SOURCES to wire more leaders. Run against an un-mapped bloc it is fail-closed: exit 4 ("NO SOURCE MAP — refusing to touch it"), writes nothing. CN / IN are fail-closed by design (exit 3, structural laggards — R5).
    • Everyone else — cross-bloc nowcast via nowcast_complete.mjs. Once the wired leaders have appended their observed 2026 Q1 rows, the coupled solve pads every other bloc's new quarter with model-implied cells (the star channel carries the leaders' observed values in). The new FSAP blocs HK/SG/RO/PE/PH already carry their own genuine 2026 Q1 (little to impute); the older ragged blocs get more fill. Even CN/IN advance this way — as an honest, flagged model-implied nowcast, never as fabricated observed data.

    So the shift is a single orchestrated command (auto_update.mjs --shift, §1). The per-wired-bloc refresh-quarter.mjs command in §1 is only what that orchestrator runs for each wired leader.

    Panel scope + holds¶

    The shift moves the whole coupled panel forward in one solve. On the seasonal-v2 branch that is 38 coupled GVAR blocs (US anchor + 37 RoW blocs, incl. the new HK/SG/RO/PE/PH) plus 17 euro-member standalones extended by member_extend.mjs — ~55 economies. (History — as of the 2026Q1 shift. The live panel is now 35 coupled blocs + 17 euro members = 52 economies, all ending 2026Q2.)

    HELD (never fabricated, R5): CN, IN — excluded from the wired pull (refresh-quarter exits 3); they take their new quarter from the cross-bloc nowcast like any laggard; do not re-pull them as if observed. (History: Israel used to sit on its own calendar with a date override; it is no longer shipped, and since 4.0 there is no date override of any kind — every history carries its own firstQuarter.)

    1. The shift chain (copy-paste)¶

    The whole shift is orchestrated by auto_update.mjs --shift. From app/:

    # 0) what's due? (probes the release calendar; exits 10 = data shift due, 11 = annual re-estimation due)
npm run data:check

# 1) DRY-RUN the whole shift (refresh gates run, NOTHING is written) — e.g. to 2026Q3
npm run data:shift -- --asof 2026Q3

# 2) COMMIT the shift (archives the current vintage, then runs the full publish chain)
npm run data:shift -- --asof 2026Q3 --commit

    FRED_API_KEY is optional: the scripts fall back to the repository's public key. (The 2026Q1 shift ran these as npx vite-node scripts/auto_update.mjs --check|--shift --asof 2026Q1 [--commit].)

    --shift --commit runs, in order (each step is a script you can also run by hand — §2):

    1. archive the current shipped vintage → pipeline/vintages/<lastQuarter>_shipped/ (idempotent);
    2. pre-release counterfactual — nowcast_complete.mjs --to 2026Q1 --write --baselines on the old data → pipeline/vintages/pre_2026Q1_counterfactual/ (the baseline /monitor diffs against);
    3. refresh-quarter.mjs for each WIRED bloc (WIRED = ['US'], --accept-revisions) — genuine observed 2026 Q1 rows. A gate failure leaves the bloc untouched (its new quarter is nowcast cross-block instead);
    4. realized_pins.mjs — harvest any published cells for the window as level pins (realized trumps imputation);
    5. nowcast_complete.mjs --to 2026Q1 [--realized …] --write --baselines — one coupled solve completes every ragged cell → staged in pipeline/nowcast_staging/;
    6. publish — copy staging → app/public/data/bvar/ + nowcast_provenance.json (a deliberate second step; the engine never writes public/data directly);
    7. member_extend.mjs --asof 2026Q1 — the 17 euro members follow the shift (one EA-channel-pinned row each);
    8. regen_gvar_bands.mjs — re-simulate predictive bands for all GVAR blocs from the new origin;
    9. build_coverage_manifest.mjs — rebuild public/data/coverage_manifest.json (drives the amber model-implied overlay);
    10. release_impact.mjs — regenerate the /monitor release-impact record (post − pre at the origin);
    11. build_coverage_manifest.mjs --panel-quarter <asof> — the dating comes from the data (every history now ends at the new quarter); the flag only asserts it. (Replaces the old dates.ts bump + manifest re-run.)
    12. vintages_publish.mjs — re-bake the /monitor vintage artifacts against the new live panel. A base counts as a "pure data shift" only if its recorded model fingerprint equals the live model's.
    13. pack-build.mjs — re-stamp the data pack (manifest.json: every file's SHA-256 + the dating the app reads), pack id <asof>-<yyyymmdd>.
    14. verification gate — verify_cutoffs.mjs (data calendars == coverage == pack manifest, every bloc on the new quarter, no null last-row cells, provenance converged) and pack-verify.mjs --full (every file re-hashed + the calendar canary against the estimation panels). The chain EXITS NON-ZERO on any violation.
    15. update packs — one per released app version recorded in pipeline/released_packs/ → packs/<id>_for_<version>.zip.

    The script then prints the post-run gate: npm test, npm run build (its prebuild re-verifies the pack), review /monitor + a few charts (amber dashed tails = model-implied nowcasts), and git add app/public/data pipeline/vintages && git commit — push/deploy only on a deliberate decision (prod = bvarscenario/main). Companion untouched ⇒ coupling_default.json.gz stays valid (no regen).

    Hiccup recovery (why the chain is safe to re-run)¶

    Every step is idempotent or additive: the vintage archive skips if present, refresh-quarter gates before writing, the completion stages to pipeline/nowcast_staging/ and publishing is an explicit copy, the manifest and bands regenerate from what is on disk, and the verification gate only reads. If a step crashes (power, API outage, OOM):

    1. Diagnose from the step's own log line — each step prints its name before running.
    2. Re-run the whole --shift --commit — completed work is skipped or harmlessly redone; or run the failed step's script by hand (each is listed above) and then steps 11–15 manually: npx vite-node scripts/build_coverage_manifest.mjs && npx vite-node scripts/vintages_publish.mjs && node scripts/pack-build.mjs --pack-id <asof>-<yyyymmdd> && npm run data:verify.
    3. Rollback = restore pipeline/vintages/<lastQuarter>_shipped/ over app/public/data/bvar/ (or git checkout the data paths). There is no date to revert: the restored histories carry their own calendar.
    4. Never hand-edit a shipped panel to "fix" a tail: the verify gate treats null tail cells as a failed completion, which is what they are.

    Deploy verification (two-hop chain — do not trust the first 200)¶

    Prod deploys are TWO hops: the tool repo's workflow builds and pushes the static export into the website repo (starter-hugo-academic), whose OWN Pages workflow then publishes — ~8–15 min end to end, plus a CDN quirk: GitHub Pages caches 404s for ~10 min, so a freshly-published file can 404 after the deploy finishes. Verify with a file that only the new vintage has (e.g. a new bloc's spec.json or a changed seasonalRows), NOT with coverage_manifest.json alone — the old vintage may serve a manifest with the same quarter label (the V3 deploy's false-confirm). Poll until the discriminating file serves 200 with the expected content.

    1b. The per-wired-bloc command (what step 3 runs)¶

    Gate-then-write for one wired leader, run from app/:

    npx vite-node scripts/refresh-quarter.mjs --bloc <CC> --asof <quarter>     # FRED_API_KEY optional

    Useful variants (use these while authoring a new registry):

    # gate ONLY — proves transform/window/source fidelity, never writes:
… scripts/refresh-quarter.mjs --bloc <CC> --asof 2026Q1 --gate-only
# gate + project + report, still no write (eyeball the seam/bands first):
… scripts/refresh-quarter.mjs --bloc <CC> --asof 2026Q1 --dry-run
# tighten the gate against a full-precision DataRaw_*_glob.json panel:
… --gate-tol 1e-9     # default is 5e-3 vs the 6-sig-fig shipped historical_levels
# accept source revisions (the mode the orchestrator runs): turns the gate into a revision DETECTOR, re-syncs
# the prior quarter, logs the revisions — only a GROSS (wrong-series/unit) error stays fatal:
… --accept-revisions
# tolerance before a revision-prone column (debt / IP / oil) counts as a flagged vintage revision:
… --revision-tol 0.5   # default 0.5 (100·log space ≈ 0.5% level)
# the dimension-aware GROSS ceiling for log columns (absolute, 100·log space):
… --gross-tol 20       # default 20 ≈ 22% q/q; volatile global price series use a fixed 50 (≈65%)

    Exit codes (what a non-zero means)¶

    code meaning action
    0 gate passed, wrote (or, with --gate-only/--dry-run, validated) proceed to verify
    1 GATE FAILED — transform/window/source fidelity not proven, or fatal fix the registry; nothing was written
    2 bad args (missing --bloc/--asof) fix invocation
    3 bloc is a HELD laggard (CN/IN) expected — leave held
    4 no source map for this bloc author SOURCES[<CC>] first, then re-run
    5 new quarter not fully published yet for this bloc wait for the data; do not partial-write
    6 fiscal: debt/GDP series missing at as-of fix the fiscal source id

    The gate (R1) is the binding safety check — but it has two modes. Before appending the new quarter it re-derives the existing last shipped row (the prior quarter) from the same live sources the same way and diffs it against the shipped panel. How a diff is treated depends on --accept-revisions:

    • Strict mode (no --accept-revisions) — the bare refresh-quarter.mjs default. STABLE columns must match byte-exact (within --gate-tol); revision-prone columns (debt/IP/cumulative) are allowed a documented --revision-tol. Any breach beyond tolerance writes nothing — there is no override. Use this while authoring a new registry, to prove transform/window/source fidelity.
    • Accept-revisions mode (--accept-revisions) — the mode the orchestrator runs (auto_update.mjs passes it, step 3). The gate stops being a must-match gate and becomes a revision DETECTOR: a diff above tolerance is no longer fatal — it is ACCEPTED and recorded as a source revision (and the prior quarter is re-synced to the realized value). Only a gross diff — the signature of a wrong series / wrong unit, not a plausible vintage revision — remains fatal (exit 1, writes nothing). The gross ceiling is dimension-aware: log columns use an absolute ceiling in 100·log space = --gross-tol (default 20 ≈ 22% q/q); volatile global price series (GLB_OIL / GLB_USEQ / GSNE) get a wider VOLATILE_GROSS = 50 (≈ 65% q/q); lin ratios/rates (fiscal shares, policy & market rates) use a RELATIVE ceiling of 50% of the column's own level (floored). So on the normal orchestrated path a column does NOT have to match the shipped value — only stay within the gross ceiling.

    2. Running the chain by hand (step by step)¶

    Prefer the orchestrator (auto_update.mjs --shift --commit, §1) — it passes the right flags and archives the vintage first. These are the exact commands it issues, for when you need to run or debug one step (or re-run after a fix). All from app/:

    FK=${FRED_API_KEY:-}     # optional; the scripts fall back to the repository's public FRED key

# 3. genuine observed rows for the wired leaders (US today) — gate-then-write, revisions accepted
FRED_API_KEY=$FK npx vite-node scripts/refresh-quarter.mjs --bloc US --asof 2026Q1 --accept-revisions

# 4. realized-data level pins for the (gap → 2026Q1] window (EU HICP/GDP mirrors, ECB rate, global commons)
FRED_API_KEY=$FK npx vite-node scripts/realized_pins.mjs --asof 2026Q1 --out ../pipeline/realized_pins_2026Q1.json

# 5. cross-block nowcast completion → STAGES to pipeline/nowcast_staging (report-only first, no --write,
#    to eyeball the per-bloc imputed-cell counts, then re-run with --write)
npx vite-node scripts/nowcast_complete.mjs --to 2026Q1 --realized ../pipeline/realized_pins_2026Q1.json --write --baselines

# 6. publish the staged panel into public/data (review the diff first)
cp -r ../pipeline/nowcast_staging/*/ public/data/bvar/                       # per-bloc historical*/baseline*
cp ../pipeline/nowcast_staging/nowcast_provenance.json public/data/

# 7. euro members follow the shift (one EA-channel-pinned row each)
npx vite-node scripts/member_extend.mjs --asof 2026Q1 --realized ../pipeline/realized_pins_2026Q1.json

# 8. re-simulate predictive bands for all GVAR blocs from the new origin
npx vite-node scripts/regen_gvar_bands.mjs

# 9. rebuild the coverage manifest
npx vite-node scripts/build_coverage_manifest.mjs

# 11–15. dating is in the data since 4.0 — nothing to edit. Assert it, re-bake /monitor, re-stamp, verify:
npx vite-node scripts/build_coverage_manifest.mjs --panel-quarter 2026Q1
npx vite-node scripts/vintages_publish.mjs
node scripts/pack-build.mjs --pack-id 2026Q1-<yyyymmdd>   # re-stamp manifest.json under a NEW id
npm run data:verify                         # verify_cutoffs + pack-verify --full

    Notes: - nowcast_complete stages, never publishes. It writes pipeline/nowcast_staging/ (or --out <dir>); copying into public/data/bvar is the deliberate review step. It refuses to stage if the coupled solve did not converge — raise --max-sweeps (default 120) or investigate. - --to 2026Q1 extends EVERY bloc's grid to 2026 Q1 (null rows appended, then imputed). After the wired refresh the leaders already carry the observed row, so only their laggard partners are imputed. - Both engines are seasonal-aware: they phase the quarter-of-year deterministic term from the target quarter. (Before 4.0 this mattered because dates.ts was bumped only at the end of the chain; since 4.0 the dating comes from each history's firstQuarter, and setPanelDates cross-checks the declared qoyNext in the manifest.)

    Wiring a NEW leader (optional — to turn a bloc's imputed cells into observed data)¶

    A bloc only needs a SOURCES[<CC>] registry if you want its 2026 Q1 to be genuine observed rather than cross-bloc nowcast. To add one:

    1. Author SOURCES[<CC>] in refresh-quarter.mjs (live FRED/Eurostat IDs + transform + window). Honour the R6 traps: discontinued OECD-on-FRED CPI mirrors; FREV/FPEXP are internal names, not FRED IDs; stale Eurostat HICP → use CP0000EZ19M086NEST for EA HICP. EA members get the shared-EA exogenous rate/corp handling baked into the spec (do not re-source those endogenously).
    2. Gate with --gate-only until it passes on the STABLE columns. If it can't pass, the registry is wrong — fix the IDs/transform/window, never loosen the tolerance to force it (--accept-revisions only RECORDS known vintage revisions; it does not silence a wrong series).
    3. Dry-run (--dry-run) and eyeball the reported seam + bands (see the Seam continuity check in §3 — a continuous level with a noisy annualized q/q step is fine; a true level discontinuity is not).
    4. Add the bloc to WIRED in auto_update.mjs; it is then re-pulled genuinely on every shift.

    3. Verify checklist (before merge)¶

    Run all of these green after a shift (the production 2026 Q1 shift passed every item).

    • [ ] tsc clean: cd app && npx tsc --noEmit → exit 0.
    • [ ] cgl_bvarV5.m 0-diff: git diff --stat BVAR/MFBVAR/cgl_bvarV5.m empty. Production estimator untouched.
    • [ ] Companion + coupling frozen: git status --porcelain app/public/data/bvar/ shows per bloc ONLY historical.json, historical_levels.json, baseline.json, baseline_levels.json, and (fiscal) fiscal_meta.json modified. companion_mean / companion_draws(.gz) / spec / transformations / gvar/coupling_default.json.gz / weights_*.json MUST NOT appear (frozen companion ⇒ modelSig unchanged ⇒ no coupling regen).
    • [ ] fiscal_meta = d0 only (fiscal blocs): git diff …/fiscal_meta.json changes only d0; sfaDefault and idx frozen.
    • [ ] History extends one quarter: every coupled bloc's historical*.json row count +1, last row dated on the new quarter.
    • [ ] R1 gate PASS (wired blocs): on the orchestrated --accept-revisions path, PASS means no column breached the GROSS wrong-series/unit ceiling (accepted revisions are expected, not failures). The re-synced columns + accepted revisions are logged to <bloc>/refresh_revisions.json — an APPENDED log, { log: [ { stampedAt, asof, priorQuarter, note, resynced:[…], gateFlagged:[…] } ] }, never clobbered (resynced = columns actually overwritten, |diff| > gate-tol; gateFlagged = the subset large enough to count as a genuine vintage revision).
    • [ ] Nowcast converged + staged: nowcast_complete reports converged=true; per-bloc imputed-cell counts look sane (new FSAP blocs HK/SG/RO/PE/PH near-zero; laggards more).
    • [ ] Provenance travels: public/data/nowcast_provenance.json regenerated; imputed cells flagged model-implied; the coverage manifest's lastObs/imputedThrough drive the amber chart overlay.
    • [ ] Members followed: all 17 euro members extended one row (member_extend); no member left a quarter short of the EA origin (the common-ECB self-check).
    • [ ] Bands sane: baseline_levels.json mean+bands all finite, q05 ≤ q16 ≤ q84 ≤ q95 everywhere.
    • [ ] Re-anchor (split-brain healed): the engine's re-projected baseline (from the refreshed history) equals baseline_levels.json mean to ~0. The grey fan and the engine sit on the SAME vintage.
    • [ ] δc = 0 == baseline (R7): an all-unconditional solve reproduces the baseline (no spurious shift).
    • [ ] Dates plot: node scripts/stamp_calendar.mjs --check passes and manifest.json panel.lastHistQuarter is the new quarter; in the app, x=−1 is the new last obs and x=0 the first forecast. No off-by-one on the x-axis. (Before 4.0 this item checked DEFAULT_LAST_HIST_DATE.)
    • [ ] Seam continuity: the level across the 2025Q4→2026Q1 join is continuous. A large annualized q/q number on a genuinely volatile quarter (e.g. WTI) is annualization, not a discontinuity — confirm against the underlying level before flagging.
    • [ ] CN/IN honest (R5): CN/IN advanced by cross-bloc nowcast ONLY (flagged model-implied in the provenance), never re-pulled as fabricated observed data.
    • [ ] Old vintage archived: pipeline/vintages/<lastQuarter>_shipped/ exists (the shift is reversible).

    4. Guardrails (do not violate)¶

    • No auto-deploy. The chain writes public/data (+ pipeline/vintages, the realized pins), but the commit + push to bvarscenario/main happens only on explicit user confirm (prod = bvarscenario/main; origin is dead).
    • No re-estimation within the year. Reuse kalman.ts / bvarForecastDraw / the shipped companion verbatim; never touch companion_mean/companion_draws. Re-estimation is the annual Q1 step (auto_update.mjs --q1-prep, MATLAB), not a shift.
    • The nowcast STAGES, never publishes. nowcast_complete writes pipeline/nowcast_staging/; the copy into public/data/bvar is a deliberate reviewed step (the orchestrator does it after the solve converges).
    • Never git add -A. Stage git add app/public/data pipeline/vintages pipeline/realized_pins_<q>.json (+ this doc / any wired registry change) — not the whole tree.
    • Fail-closed is a feature. A wired bloc exiting 4/5/6, or refresh-quarter gate-failing, leaves it untouched — its new quarter is then nowcast cross-block. Never force a write.
    • Never loosen the gate to make it pass. A failing gate means the source/transform/window is wrong; --accept-revisions only records known vintage revisions, it does not silence a wrong series.
    • Never fabricate a laggard as observed (R5). CN/IN (and any un-wired bloc) advance only as flagged model-implied nowcasts.

    5. Files¶

    Engines + orchestrator (all under app/scripts/): - auto_update.mjs — the shift orchestrator (--check / --shift --asof … [--commit] / --q1-prep). - refresh-quarter.mjs — per-wired-bloc observed refresh (gate + re-project + bands writer). - nowcast_complete.mjs — cross-block nowcast completion (completeRaggedPanel); stages to pipeline/nowcast_staging/. - realized_pins.mjs — harvest published cells as level pins (realized trumps imputation). - member_extend.mjs — extend the 17 euro members one row to the shifted origin. - regen_gvar_bands.mjs — re-simulate predictive bands panel-wide from the new origin. - build_coverage_manifest.mjs — rebuild public/data/coverage_manifest.json. - release_impact.mjs — the legacy single-pair /monitor record (post − pre); the vintage comparison (§7) supersedes it. - vintages_publish.mjs — the /monitor vintage comparison. - pack-build.mjs / pack-verify.mjs — re-stamp and verify the data pack (public/data/manifest.json).

    Data + state: - app/public/data/manifest.json — the data pack: every file's SHA-256 and size, and each bloc's dating (no date constant in the code since 4.0). - app/public/data/bvar/<CC>/{historical,historical_levels,baseline,baseline_levels,fiscal_meta}.json — the regenerated per-bloc display/state files. - app/public/data/{nowcast_provenance.json, coverage_manifest.json} — per-cell model-implied flags + panel vintage. - pipeline/vintages/<lastQuarter>_shipped/ — the archived pre-shift vintage (reversible); pipeline/nowcast_staging/ — the review-before-publish stage. - docs/data-refresh-2026q1-feasibility.md — the design and the R1–R8 risk register.

    6. Monthly data-check action — the automated reminder¶

    The shift above is run by hand, on purpose (it ships data, so a human reviews it first). But remembering to look every month is easy to forget. A GitHub Action now does the looking for us: .github/workflows/data-check.yml.

    What it does — and what it does NOT do. It runs npm run data:check (auto_update.mjs --check) on a schedule, reads the result, and reports it. It is check + alert only: it never writes, shifts, nowcasts, re-estimates, or ships anything. When an update is due it tells a person, who then runs the shift chain in §1 (or the re-estimation runbook) by hand. No data is ever touched by the action.

    When it runs. cron: '0 9 5 * *' — 09:00 UTC on the 5th of each month. That is a few days after month-end, so the quarterly QNA / GFS releases that the panel depends on have landed. You can also run it any time from the Actions tab (Run workflow, the workflow_dispatch trigger).

    What the three outcomes mean (the probe's exit code, surfaced in the run's job summary):

    Exit Meaning What a person does next
    0 Up to date — no new full-coverage quarter yet. Nothing.
    10 Within-year data shift available — a new quarter is published for every macro sentinel. Companion stays frozen, no re-estimation. Run npm run data:shift -- --asof <YYYYQn>, review, push (all human-gated — §1).
    11 Annual re-estimation due — a full final calendar year exists beyond the estimation vintage. Launch the MATLAB re-estimation; prep with npm run data:q1prep -- --year <YYYY>.

    How the alert reaches you (zero secrets). When the outcome is 10, 11, or a probe error, the job fails on purpose. GitHub automatically emails a failed scheduled run — no SMTP server, no API key, no stored secret. (GitHub's rule: the notification for a scheduled-workflow failure goes to the user who last edited the cron in the workflow file — i.e. whoever commits this file, here matyasfarkas — following that account's notification settings. So enable the setting below once.) The job summary (Actions → the run → Summary) carries the full detail: the sentinel table, which quarter is available, and the exact command to run. When the outcome is "up to date" the job passes quietly and you hear nothing.

    Forwarding the alert to gmapsmodel@gmail.com / matyi.farkas@gmail.com. The built-in email goes to the GitHub account that owns the repo (matyasfarkas), following that account's notification settings — there is no code change to make. To route it onward: - GitHub → Settings → Notifications → Actions: enable "Send notifications for failed workflows only" and point GitHub notifications at the address you want (GitHub → Settings → Emails lets you add gmapsmodel@gmail.com / matyi.farkas@gmail.com as verified addresses and choose which receives notifications), or - add a filter/forwarding rule in the receiving mailbox.

    If you later want a direct email to those two addresses (instead of relying on GitHub's own notification), the upgrade path is documented but not built: add a final step using dawidd6/action-send-mail@v3 with a Gmail App Password stored as a repo secret (e.g. MAIL_PASSWORD), sending to both addresses only when steps.probe.outputs.exit_code is 10 or 11. That introduces one secret, which is why the zero-secret built-in notification is the default.

    Two things to know about scheduled Actions: - A schedule: workflow fires in every repo the file is pushed to. This repo is mirrored (bvarscenario and gmapsmodel), so the job is pinned with if: github.repository == 'matyasfarkas/BVARScenarioTool' — it runs on the canonical repo only, once. - GitHub auto-disables a scheduled workflow after ~60 days of no repository activity. Any push, or a manual Run workflow, re-arms it.

    A caveat the probe inherits (flagged, not a defect of the action). The probe marks a sentinel UNREACHABLE on a network blip and drops it from the coverage test. In the rare case where the only laggards (today KR, CN) go unreachable while the rest are already beyond the panel, the probe can report "shift available" one cycle early. Because the action only alerts — a human verifies full coverage before running the actual shift (§1 gates fail-closed) — this is safe: at worst it prompts a look that finds nothing to do.

    7. Vintage-comparison monitor (/monitor)¶

    The /monitor page compares the live published panel against a prior vintage you choose, and shows the revision on a graph (not just a single scalar). It answers "what did this data update change, versus the time point I pick?"

    How it works. app/scripts/vintages_publish.mjs bakes, under app/public/data/vintages/: - index.json — the registry of base vintages (what fills the "Compare against" selector), each tagged pureDataShift: true (model/companion frozen — a true data-release impact) or false (the comparison also spans a re-estimation — "model + data"). - <vintageId>/<bloc>.json — per-economy, the calendar-aligned forward revision (live − base) for every comparable variable, plus each variable's origin-quarter revision. Lazy-loaded one economy at a time.

    Alignment is done by the unit-tested app/src/lib/monitor/vintageAlign.ts on two axes — variable id AND calendar quarter — never by raw array index (a 2025Q4 re-estimation has 41 vars vs the live 40, and a different origin; pairing by index would compare the wrong variable in the wrong quarter). Variables whose transformation changed, or that were dropped/added between vintages, are listed and excluded as non-comparable.

    Regenerate it: npm run data:vintages. It also runs automatically in two places: late in a --shift --commit (the §1 chain step after the final coverage-manifest rebuild, so it re-bakes against the shifted live panel), and in app/package.json prebuild — i.e. on every next build — as a freshness guard so the baked public/data/vintages/* artifacts can never go stale versus the live panel (the same safeguard class as the companion-draws .gz). The artifacts have no .gz sibling, so the deploy's prune step keeps them (verified in the export).

    Bases available today (honest scope). Since the October 2026 re-estimation every archived vintage was made with an earlier model, so all three bases offered now (2025Q4_shipped, 2025Q4_shipped_mb902f2385a, pre_2026Q1_counterfactual_mb902f2385a) are labelled "model + data"; the first pure-data-shift base will be the one written by the next data shift. The paragraph below is the state before the re-estimation: only ONE genuine pure-data-shift base existed — pre_2026Q1_counterfactual_mb902f2385a (same 2026Q1 origin as live, same model; 35 economies, 0 dropped), which the page opens on by default. (An older pre_2026Q1_counterfactual, last built on 26 Aug 2026 with an earlier model and wrongly labelled "model frozen", was removed in Oct 2026.) The picker also offers 2025Q4_shipped, an across-re-estimation base (origin 2025Q4, 47 economies, 5 dropped ids + 28 transform-mismatches excluded) clearly labelled "model + data". The picker grows one pure-data-shift entry each monthly shift (auto_update writes a vintage_meta.json into each new pre_<asof>_counterfactual so the publish script discovers it with no code edit).
