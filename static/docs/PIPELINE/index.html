    Data & Estimation Pipeline¶

    This page documents the offline pipeline that turns raw public data into the static JSON the web app serves: build → estimate → check → port → couple → complete & stamp the data pack → test → deploy. Everything here runs on the researcher's machine (MATLAB + Python + Node); the deployed browser app only ever reads the resulting data pack (app/public/data + its manifest.json). Since 4.0.0 the pack is separate from the tool: a new pack (a quarterly data shift or a re-estimated model) reaches users without a new app version — see UPDATE_MANUAL.md.

    Scope / where to look next. This page is the mechanism reference — the script inventory, the raw-data precedence chain, the GVAR-EM loop internals, the prior/coherence tagging sweeps, and the port/coupling steps. For the decision tree ("what kind of update is this, and what does it re-estimate?") and the operational runbooks (exact copy-paste sequences with the green gate) see MAINTAINER_OPERATIONS.md, REESTIMATING_MODELS.md and ADDING_A_COUNTRY.md; for the live compute architecture see ARCHITECTURE_FOR_AI.md; for the fiscal block see fiscal-block-methodology.md. The per-economy variable table (transformation · prior · financial-tag, all 1048 ported variable rows audited coherent) lives in the user manual (docs/GMAPS_User_Manual.tex, Appendix B — generated from the shipped specs by docs/generate_manual_tables.py). The out-of-sample forecast horse-race + endogenous-US spillover evaluation lives in a separate repo — see §11 and its docs/EMPIRICAL_PROTOCOL.md. This page does not repeat those — it complements them.

    The currently-deployed platform (data pack 2026Q2-reest-20261008b, Oct 2026) is 52 economies: 35 coupled GVAR (global vector-autoregression) blocs (the US, endogenous, + 34 partners, with the euro area as one aggregate EA bloc; HK, SG, RO, PE and PH joined in 2026; AR, IL and RU were dropped) + the 17 euro-area members, each with its own model estimated outside the coupled GVAR. Every panel was rebuilt from its publishers with no fills of any kind (pipeline/sources/, §3.0): each series runs to its latest published quarter (2026Q2 where published), and every gap — leading, interior or at the ragged end — is missing data that the sampler draws. Coupling: dim 2180, ρ(M) = 0.971875. AE (United Arab Emirates) was evaluated and dropped earlier: it publishes only annual real GDP, and the viability test for a GVAR bloc is quarterly real GDP existing (§3.1.1).

    Older numbers on this page. Several sections were written for the 33-bloc deployment of mid-2026 (coupling dim 2060, ρ ≈ 0.92–0.945, a common 2025Q4 estimation endpoint with WEO-Denton-extended tails). Where they remain they are labelled as history. The authoritative record of the deployed run is docs/reest-2026/ (PLAN.md decisions, REVIEW.md, and the exact scripts in runs/).

It is documented in §3.6 and is independent of §4–§7 in both directions.

    3. Script reference¶

    3.0 Source registries — how the deployed panels are built (Oct 2026)¶

    Since the genuine-data re-estimation, every estimation panel is rebuilt from a machine-readable source registry, one file per economy, by one builder:

    python3 -B pipeline/sources/build_panel.py --bloc NZ [--end 2026-Q2] [--out DIR] [--refresh] [--dry-run]
python3 -B pipeline/sources/compare.py --bloc NZ      # new panel vs the previous one, column by column
python3 -B pipeline/sources/scaffold.py --bloc NZ     # registry skeleton from an existing panel
    • pipeline/sources/registry/<CC>.json (52 economies) + _globals.json (the four GLB_* columns): for each variable, in the model's variable order, the provider, its exact key, how monthly/daily data become quarters (complete quarters only), any documented unit conversion or sample cut, and labels for proxies. Format and conventions (incl. "every exchange rate: rise = appreciation"): pipeline/sources/registry/README.md.
    • Providers (providers*.py): FRED, BIS, IMF, OECD, Eurostat, ECB, DBnomics, StatCan, Bundesbank, …; staged marks a series already in the repo (e.g. pipeline/sources/staged/) — not a live fetch, and each one is a to-do for a live adapter.
    • Derived columns (derived*.py): the 4-variable fiscal block (fiscal4: revenue and primary expenditure as % of GDP, EFFI direct or trailing-4-quarter, SFA as the exact debt-identity residual) and its fiscal_meta (d0 at the last published debt quarter, sfaDefault).
    • Rule: no fills of any kind. Every cell is a published value (after a declared conversion) or NaN. The output DataRaw_<CC>_glob.json has the estimator's usual schema, plus a .provenance.json (per column: provider, key, fetch vintage, first/last genuine quarter, notes, decision reference).
    • The source decisions behind the registries (D1a–D13: re-sourced rates, BIS effective exchange rates, Costa Rica from OECD accounts, India's new base, a GDP deflator for every fiscal economy, …) are in docs/reest-2026/PLAN.md §5.

    The builders in §3.1 are the earlier route (how the panels were assembled up to Sep 2026). They are kept for reference and for the satellite files they produced (e.g. the trade weights and NFA anchors the deployed pack still uses); do not use them to rebuild a deployed panel.

    3.1.1 Auto data-pull sourcing scripts (public APIs, no fabrication)¶

    Every builder below pulls from a public API and stores the genuine observation only — ragged edges kept, no interpolation / back-fill / extrapolation. The first block is the standing macro/credit/ fiscal sourcing; the second block (under pipeline/fsap_expansion_staging/) is the FSAP-expansion sourcing that assembles the 5 new blocs and the time-varying / external satellites. This table maps each data type → script → public API → what it pulls; the assembler scripts that turn the staged series into a DataRaw_<CC> panel follow.

    Data type Script Public API What it pulls
    Macro (US) build_us_auto.py FRED all US quarterly macro + the 3 fiscal drivers, COVID handled
    Macro (EU/EFTA + EA) build_oecd_eurostat.py, build_ea_eurostat.py Eurostat SDMX (namq_10_gdp real GDP, prc_hicp HICP) quarterly real national accounts + prices for the EU/EFTA members and the EA aggregate
    Macro (FRED core) build_country_data.py FRED quarterly macro + financial block for the FRED-based economies

    Fiscal build_fiscal22_*.py (incl. build_fiscal22_columns.py) national / OECD / IMF fiscal sources the EFFI/SFA/FREV/FPEXP fiscal columns — build_fiscal22_columns.py is the assembler (carries the even-coupon EVEN_INTEREST EFFI, §5.2)
    Time-varying trade weights fsap_expansion_staging/weights/build_weights_timevarying.py IMF IMTS via api.imf.org SDMX 2.1 — flow IMF.STA:IMTS(1.0.0), indicators XG_FOB_USD+MG_CIF_USD, key COUNTRY.INDICATOR.COUNTERPART_COUNTRY.A, EA = G163 ANNUAL bilateral goods X+M, 1995–2024, 39 reporters (38 blocs + AE candidate); per-year row-normalized (zero diagonal, partners < 0.05% dropped, RU/TW mirror fallback, reporter-years with no data omitted not imputed) → weights_timevarying.json (+ weights_latest.json for 2024 + weights_validation.json)

    Assembling a staged bloc into a panel. Two assemblers turn the staged per-role series above into the DataRaw_<CC> layers of §4:

    • build_newbloc_panel.py [CC …] — assembles DataRaw_<CC>_2025q4.json from the staged newblocs/+neer/+trade/ series via a per-bloc MANIFEST (variable roles GDP/CONS/INV/GOV/EXP/IMP/CPI/HP/NEER/EQ/CREDIT/RATE/YIELD10; a ROLE dict fixes transformation + isFinancial per role, matching the deployed PL/EM template). Grid runs from max(GDP first obs, 2000Q1 EM-peer floor) to the 2025Q4 vintage (later 2026Q1/Q2 obs feed the separate rebase, §6/§10); raw values stored as-is, ragged edges kept, absent cells written null (leading NaN back-filled, the DK smoother imputes interior holes). A rate-less bloc (SG) is fine. Default runs all 5.
    • build_globals_new_blocs.py [CC …] — already in §3.1; injects the 4 GLB_* commons (dropping any legacy _US block, forcing the 4 globals isFinancial:1 per §3.4) → DataRaw_<CC>_glob.json. The same script that converts the euro standalones is reused for the FSAP new blocs via its CLI subset.

    A bloc becomes GVAR-coupled purely by data: a row in the static weights file (weights_full_38.json = the 2021–23 average of the TV panel over the 38-bloc set — added as a row and as a partner everywhere, renormalized), block:'row' vars in its spec.json, and a {code,name,group} entry in app/src/lib/data/countries.ts (HK/SG/RO/PE/PH already present). See ADDING_A_COUNTRY.md for the full new-bloc runbook.

    3.3 The fiscal stationary ("WN") prior — tag_fiscal_wn.py¶

    §3.3–§3.5 describe one-off tagging sweeps of the earlier route. In the source route (§3.0) each registry entry carries its variable's prior, transformation and isFinancial directly, so the panels come out already tagged; the sweeps below are not part of the deployed chain. (In the deployed growth-rate model the estimator additionally tags the differenced GDP/price/deflator columns WN.)

    The GLP/Minnesota prior in BVAR/MFBVAR/GLPreplicationWeb/bvarGLPmf.m builds the prior coefficient matrix b with a unit own-first-lag mean by default (a random walk: diagb=ones(n,1)). Any column listed in the pos vector gets its own-first-lag prior mean zeroed, turning that variable into a mean-reverting white-noise (WN) process under the prior:

    % BVAR/MFBVAR/GLPreplicationWeb/bvarGLPmf.m, lines 192–195
b=zeros(k,n);
diagb=ones(n,1);
diagb(pos)=0;          % zero the own-first-lag prior mean for the 'pos' columns -> stationary/WN
b(2:n+1,:)=diag(diagb);

    pos is the 3rd positional argument of the COVID-as-missing sampler cgl_bvarV5 (which renames it pos=stationary; and forwards it as 'pos' to bvarGLPmf):

    % BVAR/MFBVAR/cgl_bvarV5.m
function [Xcond,storeP,BETA,SU,X_interp0,Dforecast] = cgl_bvarV5(x,p,stationary,nDraws,...)
pos=stationary;
... r = bvarGLPmf(..., 'pos', pos);

    Why this matters. Before this change every call passed [] for stationary, so every variable in every bloc was a prior random walk. The fiscal GDP ratios — FREV_GDP (revenue/GDP), FPEXP_GDP (primary expenditure/GDP), and SFA (the stock-flow adjustment) — are economically stationary: they fluctuate around a long-run share, they do not drift. Under the RW prior the projected ratios stayed pinned near their last observation at the long horizon (US revenue stuck near ~19%). The WN prior lets them mean-revert to their in-sample means — US FREV_GDP → ~17.9% (sample mean 17.91, last obs 18.77; commit e38673a) instead of drifting. The effective interest rate EFFI is genuinely persistent and stays RW.

    How the tag is consumed. Each estimator reads the per-variable prior field out of the raw JSON via a priorsfrom helper and builds the WN column-index vector, passed as cgl_bvarV5's 3rd arg:

    % export_bvar_gvar24_loop.m — on the kept domestic block, indices into x=[dom | stars]
statCols = find(Spec.Prior(keep)=="WN")';   % empty for the 44 non-fiscal blocs
[Xcond,~,B,S,~,Dfc] = cgl_bvarV5(x, lags, Dc.statCols, nDraws, nBurn, ...);

% export_bvar_euro_fsap.m
statCols = find(Prior=="WN")';
[~,storeP,BETA,SU,~,Dforecast] = cgl_bvarV5(x, lags, statCols, nDraws, nBurn, ...);

    Because the stars (ROW*) are appended after the domestic columns, the WN indices (which point into the domestic block) are unchanged by the star append — and they remain on the domestic ratios only; stars are always RW. statCols is empty for the 44 non-fiscal blocs, where pos=zeros(1,0) behaves exactly like the old [] — so the WN change is a byte-identical no-op for every bloc that carries no fiscal ratio.

    priorsfrom and the cell-array trap. tag_fiscal_wn.py writes prior on every variable object (not just the 3 WN ones) so the field set stays homogeneous: MATLAB's jsondecode returns J.variables as a struct array only when all objects share the same fields; a partial prior tag makes it a cell array and breaks the estimators' arrayfun(@(v)v.id, J.variables) calls. priorsfrom (present in both estimators) is written to be robust to either shape. The Python tagger is format-preserving (a targeted text splice — only the inserted/updated prior bytes change; the data array is untouched) and idempotent (re-running once tags are present is a no-op). It edits the globals-augmented file the GVAR loop actually reads, preferring _glob → _2025q4 → plain.

    python3 pipeline/tag_fiscal_wn.py
# DataRaw_US_glob.json: 0 field(s) changed this run; WN = ['FPEXP_GDP', 'FREV_GDP', 'SFA']; RW count = 35
# ... (idempotent: 0 changes once tagged)

    The exported spec.json carries the real prior per variable (WN/RW), so the contract and the per-economy coherence table reflect it. Committed in 6f0161a (plumbing) and 22250be/e38673a (the refit). See the fiscal recursion in fiscal-block-methodology.md.

    3.4 Global-commons financial coherence — tag_global_financial.py¶

    The COVID-as-missing masking in the estimator NaN's the 2020Q2–Q4 window only for the slow national-accounts macro variables (isFinancial:0), so the Durbin–Koopman smoother imputes them; fast-moving market prices (isFinancial:1) are kept observed through COVID and condition that imputation (§5.1, step 3). An audit found two of the four US-determined global commons mis-tagged: GLB_USEQ (US equity index) was isFinancial:false in every non-US bloc, and GLB_OIL (oil price) was isFinancial:false in every bloc — so they were being NaN-imputed across COVID like a GDP series, which is incoherent for a daily-quoted market price.     3.6 The DSGE lens payload — the IRF census and build_drivers_index.mjs¶

    Everything above builds the BVAR side. The app also ships a DSGE impulse-response payload, used by two features that read a scenario through a structural model: the policy counterfactual, which shifts a scenario path by the impulse response to a change in the policy rule, and the experimental Drivers panel, which reads a scenario path back into the structural shocks of one chosen model over the first twelve forecast quarters (the method, its licence and its limits are in drivers-decomposition.md). This payload is produced by one Node script and involves no DataRaw, no estimation, no port and no coupling. A re-estimation ships it unchanged, and a change to it re-estimates nothing.

    Where the impulse responses come from. Every lens on the Drivers menu is a model of the Macroeconomic Model Base (MMB), and the responses ship with one of two provenances, recorded per model in the index:

    • Census models (eight). Exported by an MMB census run under the model's Taylor rule and staged as pipeline/census_irfs/<model>/Taylor.json, with pipeline/census_irfs/MANIFEST.json carrying one sha256 per file. These are copied into the served tree. They are EA_SW03, EA_SWW14, CA_LS07, HK_FP13, BRA_SAMBA08, UK_SM11, and the two 54-shock FRB/US linearisations US_FRB22 (source directory US_FRB22_mcap) and US_FRB22_var.
    • Models already in the app's IRF tree (four). US_SW07, US_CMR14, US_FRB08 and US_FRB22_mcap are read in place from app/public/data/dsge/irfs/<model>/SW.json and are indexed, not copied; the two FRB/US entries carry the sourceNote "MMB rule file". US_SW07 and US_CMR14 were regenerated with their full native shock sets when Drivers shipped, which is why they are much larger than before (215 KB and 1.79 MB); the interest_ and fiscal_ columns the policy counterfactual reads moved by ~5e-11, re-export rounding only.

    The build step. One script produces the whole payload:

    node app/scripts/build_drivers_index.mjs

    It takes no arguments and resolves the repository root from its own location, so it runs from anywhere. It reads pipeline/census_irfs/MANIFEST.json, the eight pipeline/census_irfs/<srcDir>/Taylor.json files, pipeline/_shockbench/class_maps.json, and the four app/public/data/dsge/irfs/<model>/SW.json files. It writes app/public/data/dsge/census/index.json (36 KB) and the eight app/public/data/dsge/census/<model>.json copies (1.0 MB for the six small models, 10.75 MB and 10.57 MB for the two FRB/US lenses). A census file whose sha256 does not match the manifest is a hard error: the script refuses to ship it rather than warning.

    Every field in the index is derived from the response arrays, not curated by hand. For each model the script records the usable shocks — a shock is usable iff it carries all three common observables output, inflationq and interest and its stacked three-observable, twelve-quarter response path has Euclidean norm at least 1e-9 — and names anything it drops together with the reason (zero-response, missing-observable). It records the collinear pairs, |cos| > 0.95 between unit-normalised stacked response paths, computed exactly as pipeline/bench_simple_decomp.m computes it. For the two 54-shock FRB/US lenses it additionally records the clusters — connected components of that collinearity graph, each labelled by its largest member's equation name, ordered by size — and a validated default naming, the one cluster triple its own build-time recovery scan selects among those that recover a known shock sequence to 1e-6. Finally it embeds pipeline/_shockbench/class_maps.json verbatim as index.shockClasses, so the browser never fetches anything under pipeline/ at runtime.

    Remark 1 (Clusters are connected components, not bundles of parallel columns). A cluster is a connected component of the |cos| > 0.95 graph, so its members are chained through collinear links rather than mutually parallel: collinearity is not transitive, and two members of one component can sit well below 0.95 against each other. The single column the app names for a cluster is the first principal component of the member set, not a stand-in for an already-parallel bundle. Do not describe cluster membership as pairwise near-parallel, in the docs or in the interface.

    Remark 2 (The census sources are not on the deploy branch). pipeline/census_irfs/ lives on explore/shock-benchmark, together with the rest of the research provenance for this feature. On the deploy branch build_drivers_index.mjs fails at its first read, MANIFEST.json, so regenerating the payload means checking that tree out first. Nothing is lost by not having it day to day: the shipped copies are byte-identical to their census sources by the sha gate, and the tests re-verify that hash on every run.

    Example 1 (Re-shipping the payload after a class map changes). We amend a model's shock-class membership and re-ship the payload that carries it. Class membership has exactly one source of truth, pipeline/_shockbench/class_maps.json; the copy inside index.json is a build product, so editing it there would be overwritten on the next build and would fail the provenance test in the meantime. We proceed in steps. First we edit the class map. Then we rebuild the index, which copies the amended map into it verbatim and re-derives every other field. Then we re-run the class-recovery bench, because a changed class map changes what that bench measured and therefore what the class view is licensed at — the criteria, and what to do when a bench stops passing, are in MAINTAINER_OPERATIONS.md §H. Finally the fast test suite, which re-hashes every shipped file against the index and asserts the embedded map equals the source. The commands are as follows:

    # from the repo root, with pipeline/census_irfs/ checked out (Remark 2)
$EDITOR pipeline/_shockbench/class_maps.json                        # the single source of truth
node app/scripts/build_drivers_index.mjs                            # -> census/index.json + the 8 copies
matlab -batch "run('pipeline/bench_class_recovery.m')" | tee docs/paper/class_recovery_results.txt
cd app && npm test                                                  # includes the 26 Drivers licence tests

    The payload's weight in the static export, and how much of it a user actually downloads, are in BUILD_AND_CI.md. What the class view is licensed at, and the rule for a bench that stops passing, are in MAINTAINER_OPERATIONS.md §H.

    5. The GVAR-EM loop (export_bvar_gvar24_loop.m)¶

    The loop is an EM- (expectation–maximisation-) style fixed-point over the cross-country foreign components. It interleaves a Gibbs/DK imputation step (estimate each bloc, fill the COVID + foreign-star holes) with a trade-weighting step (rebuild every bloc's RoW stars from partners' completed panels), and iterates until the foreign components stop moving.

    5.1 Per-iteration internals¶

    1. Bootstrap the US (closed anchor). Estimate the US once with no stars (cgl_bvarV5(xUS, …)) over the COVID-masked domestic block, take the posterior-mean DK-completed series XcUS = mean(Xcond,3) and form its [realGDP, price, rate] panel. This seeds iteration-1's stars. With US_ENDOGENOUS=1 the US is then folded into the loop and re-estimated with its own ROW*_US stars (the no-stars fit is discarded — a warm start, not exported).
    2. Build stars (buildstars). For each bloc, ROWDEM/ROWINF/ROWFIN = trade-weighted averages of partners' real-GDP growth / inflation / short rate, renormalised over the partners present each quarter (unbalanced panel). Stars are 4·Δ(100·log) (annualised %), not 400·. Per-component availability: a rate-less partner (today only SG) still feeds DEM/INF; hyperinflation partners (AR, while in the roster) are dropped from INF/FIN but kept in DEM. Without GVAR_NOFILL, leading NaN is back-filled; under GVAR_NOFILL=1 (deployed run) a quarter with no reporting partner stays missing and is drawn by the sampler like any gap; internal COVID NaN is left for the smoother. Weights are the static row by default, or the per-quarter time-varying IMTS rows when GVAR_TV_WEIGHTS is active (§5.2) — so the shifting trade structure enters the star history.
    3. Estimate each bloc (parfor). x = [domestic | ROWDEM ROWINF ROWFIN]; over 2020Q2–Q4 NaN only the macro columns (domestic isFinancial==false + ROWDEM + ROWINF); keep all financial columns + ROWFIN observed. The financial set kept observed now includes all four global commons GLB_OIL/GLB_USLR/GLB_USBAA/GLB_USEQ (after the §3.4 coherence fix), matching the domestic market prices. The WN/stationary columns (fiscal ratios; under BVAR_DIFF_GP=1 also the differenced real GDP, price and deflator) enter as the 3rd positional statCols arg (§3.3). Under GVAR_NOFILL=1 every other gap in the panel is missing data too: a seed fill only starts the chain, and the cells the sampler drew are exported in estimation_mask.json. cgl_bvarV5(..., statCols, ..., 'sur',0,'noc',1,'Ndraws',1000, 'Ndrawsdiscard',500) then imputes the macro holes via the Durbin–Koopman smoother conditioned on the observed financials. The completed panel is the posterior mean mean(Xcond,3).
    4. Converge. Compute max|Δstar| across blocs (excluding the COVID-NaN'd macro-star cells, which are MC noise; ROWFIN stays in the metric). Stop when it>1 && max|Δstar| < TOL.

    This is a Jacobi sweep: all stars are built from the frozen start-of-iteration state, then all non-US blocs (or all blocs when US_ENDOGENOUS) are estimated independently in parallel — same fixed point as Gauss–Seidel, ~Ncores faster.

    Algorithm (EM-style fixed point over the foreign components).

    Input:  per-bloc panels {X_c}, trade weights W, COVID window 2020Q2..Q4, TOL, MAXIT
Output: per-bloc completed panels {X̃_c} + posterior draws (the 8-file contract)

  ── E-step seed ───────────────────────────────────────────────
  Estimate US with NO stars (cgl_bvarV5, COVID-macro-masked) → X̃_US⁰ = mean(Xcond,3)
  Seed each bloc's foreign stars S_c⁰ from the iteration-0 completed panels.

  ── EM loop (Jacobi) ──────────────────────────────────────────
  for it = 1 .. MAXIT:
    M-step / star build:   for every bloc c:               # frozen start-of-iter state
        S_c = buildstars(W, {X̃_p}_{p≠c})                   # ROWDEM/ROWINF/ROWFIN, 4·Δ(100·log),
                                                            #   per-quarter renormalised over present partners
    E-step / re-estimate:  parfor every bloc c:
        x_c = [domestic_c | S_c]                            # WN cols = statCols (3rd arg)
        NaN the 2020Q2..Q4 MACRO cells (isFinancial==false + ROWDEM + ROWINF) only;
            keep all financials + ROWFIN (incl. GLB_*) observed
        [Xcond, β_c, Σ_c, ...] = cgl_bvarV5(x_c, lags=3, statCols, nDraws, nBurn, 1, H, ...)
        X̃_c = mean(Xcond,3)                                 # DK-smoother posterior-mean completion
    convergence:  Δ = max_c |S_c^{it} − S_c^{it−1}|         # exclude COVID-NaN'd macro-star cells
    if it>1 and Δ < TOL: break                              # MC noise floor ≈ 0.13

  save /tmp/gvar24_workspace.mat   then   exportbloc(c) → /tmp/gvar24_export/<c>/ (8 files)

    The E-step is the Durbin–Koopman data-augmentation completion of the foreign blocs under COVID-macro-masked / financials-observed missingness; the M-step is the Bayesian (GLP) re-estimation plus the trade-weighted star rebuild. Iterating to a fixed point in the completed stars is what couples the blocs at estimation time (distinct from the solve-time coupling x=Mx+d in §7).

    7. Coupling (precompute_gvar_coupling.mjs) — the pre-shipped inverse¶

    The browser solves the cross-country fixed point x = (I−M)⁻¹ d from a pre-shipped coupling artifact. The in-browser M build (DK-smoother probes) is ~19 min at 24 blocs and worse at the augmented endogenous dimension, so pre-shipping is mandatory, not an optimisation.

    app/scripts/precompute_gvar_coupling.mjs (run via npx vite-node):

    1. assembles the deployed bloc bundle exactly like the loader (a non-US bloc qualifies iff its spec.json has block:'row' vars; US is always included), self-configures the topology, and computes modelSig;
    2. builds M in JS (buildGVARCouplingM / buildGVARCouplingMEndo when US_ENDOGENOUS);
    3. inverts (I−M) via MATLAB BLAS (app/scripts/invert_coupling.m; the NumPy invert_coupling.py is the no-MATLAB fallback);
    4. writes the gzipped app/public/data/bvar/gvar/coupling_default.json.gz ({ modelSig, pinStructure:'', dim, rhoSpectral, M, invImM }, 6-sig-fig). The plain .json is removed; the app reads only the .gz (through the data pack, hash-checked, decompressed in-browser via DecompressionStream). In the deployed pack (35 blocs, dim 2180) the artifact is 35,646,004 B gzipped; the raw JSON would exceed GitHub's 100 MB per-file limit, so gzip is mandatory. The coupled dimension is nB·60 + 80 (each bloc's star block + the US-global augmentation), so it grows with the bloc count: 33·60 + 80 = 2060 (mid-2026) → 35·60 + 80 = 2180 (deployed).

    After writing the artifact, re-stamp the pack (pack-build.mjs): the manifest records the coupling's hash and the weights it was built from (gvar.coupling.inputs.weightsSha256), and pack-verify checks that they match the shipped weights.

    cd app
npx vite-node scripts/precompute_gvar_coupling.mjs

    Keyed to the data by modelSig. The artifact MUST be regenerated whenever any deployed bloc changes — a stale modelSig is rejected and the app falls back to the slow path. The script prints ρ(M) but does not stop on ρ ≥ 1: check it yourself.

    The augmented operator's spectral radius grows with the bloc count (it must stay < 1 for a stable fixed point):

    Topology dim ρ(M)
    6-bloc — 0.59
    24-bloc (frozen anchor) — 0.726
    33-bloc (endogenous US, mid-2026) 2060 ~0.92–0.945 (artifacts of Jun–Sep 2026)
    35-bloc (endogenous US, Sep 2026 model) 2180 0.957724
    35-bloc (endogenous US, deployed Oct 2026 genuine-data re-estimation) 2180 0.971875 (LIVE coupling_default.json.gz) — must stay < 1 (the fixed-companion E-step keeps it contractive; GVAR_POLISH_EXACT would push it > 1, §5.2)

    rhoSpectral moves with each refit; what matters is that it stays < 1. The deployed value is higher than before, so shocks spread a little further and last a little longer (docs/reest-2026/REVIEW.md §2). The artifact's modelSig (per-bloc n_lags_H_<betahat-fingerprint>) keys it to the exact data; the deployed one reads US:40_4_20_… (US n = 40, lags = 4).

    10. Targeted single-bloc re-estimation¶

    Two distinct "re-estimate one bloc" patterns exist; picking the wrong one is the most common maintenance mistake. The rule is set by whether the bloc is in the coupled GVAR. See the decision tree in MAINTAINER_OPERATIONS.md §0; this is the mechanism behind it.

    The bloc is… Pattern Re-estimates Coupling regen?
    a euro-area member (AT BE DE EE ES FI FR GR IE IT LT LU LV NL PT SI SK) truly single-bloc — it is not in the coupled system (no weights row, no trade-weighted stars) only that bloc no
    a coupled GVAR bloc (US/EA/any RoW) full GVAR re-estimate — its stars feed every other bloc, so the fixed point moves for everyone all 35 yes

    Either way, re-stamp the data pack afterwards under a new id (pack-build.mjs --pack-id …, then pack-verify.mjs --full).

    10.1 The euro member — genuinely isolated¶

    A euro member has its own model (domestic + fiscal block + euro-area external columns + two rest-of-euro-area aggregates), estimated by export_bvar_euro_redesign.m, one member per run. It carries no coupling, so re-estimating it touches nothing else:

    (The earlier export_bvar_euro_fsap.m route — domestic + exogenous US block + 4 globals — is no longer what the deployed members use.)

    10.2 The coupled bloc — there is no "just one bloc" path¶

    Because each coupled bloc's ROW* stars are trade-weighted aggregates of every partner's completed panel, changing one coupled bloc's data perturbs the EM fixed point for all of them. The honest path is the full loop. But you can iterate fast on a subset using BVAR_GVAR_BLOCS (US first), which is the validate-then-commit pattern: confirm a data/coherence fix is correct on a 2–3-bloc smoke run before launching the multi-hour full refit. This is exactly how the §3.5 CA-IP fix and the §3.3/§3.4 tags were landed:

    # (a) FAST validation subset (separated, no coupling) — confirm the fix is sane
BVAR_GVAR_BLOCS="US CA" NDRAWS=200 MAXIT=1 US_ENDOGENOUS=1 \
  matlab -batch "run('pipeline/export_bvar_gvar24_loop.m')"
GVAR_PORT_BLOCS="US CA" python3 pipeline/port_gvar_exports.py   # inspect /tmp/gvar24_export first

# (b) once happy, the FULL coupled refit (the only deploy-grade path for a coupled change)
US_ENDOGENOUS=1 matlab -batch "run('pipeline/export_bvar_gvar24_loop.m')"
python3 pipeline/port_gvar_exports.py
cd app && npx vite-node scripts/precompute_gvar_coupling.mjs    # MANDATORY: stars changed for everyone

    The intermediate commits 6f0161a (WN plumbing) → 9839a46 (CA-only targeted re-estimate, the validate step) → 22250be → e38673a (the self-consistent full 33-bloc refit folding in all three fixes) are this pattern in the git history. A MAXIT=1 subset run is not deploy-grade for a coupled bloc — it freezes the stars at their historical (uncoupled) values; only the full loop, run to convergence (the deployed run: MAXIT=30, converged at sweep 6), reaches the cross-country fixed point. After any coupled change you must regenerate coupling_default.json.gz (§7) — a stale modelSig is rejected and the app silently falls back to the slow path. See MAINTAINER_OPERATIONS.md §C–§D for the per-bloc checks (n == spec == companion, convergence vs the MC floor, fiscal closure) and §E for the green gate.

    11. Empirical evaluation (out-of-sample horse-race + spillover)¶

    A separate repo — em-bayesian-gvar-eval (docs/EMPIRICAL_PROTOCOL.md) — evaluates the platform's forecasts against benchmarks. It consumes the same estimator and conventions documented here; this section is the cross-link, not a duplicate.

    Design (final). Two cores:

    1. Out-of-sample forecast horse-race. Recursive expanding-window, origins 2010Q1–2024Q4 (drop the 2020 COVID origins for the headline), targets {real GDP growth, inflation, short rate} for US/EA/JP/UK/CA/CN (full-panel = all 33 blocs in the appendix), horizons h ∈ {1, 2, 4, 8}.
    2. Proposed: the EM-Bayesian GVAR — endogenous-US (emgvar_endo, US_ENDOGENOUS=1) and the legacy frozen-anchor (emgvar_frozen).
    3. Benchmarks: Random Walk (driftless + a sample-mean "climatology" anchor), AR(p) (AIC-selected, iterated + direct), single-country Bayesian VAR (the coupling ablation = strip the ROW* columns, MAXIT=1), textbook OLS Pesaran–Schuermann–Weiner / Dees GVAR (cgvar_a), single-pass Bayesian GVAR (cgvar_b, MAXIT=1 — the EM ablation), and a Bayesian DFM.
    4. Leak-free by construction. Panels truncated ≤ t0 before transformData and before any star is built; rolling as-of-t0 trade weights (IMTS bilateral trade with endPeriod ≤ year(t0)) — the shipped 2021–2023 weights_full.json is forbidden in the sweep (it would inject future trade structure). COVID-as-missing is reapplied in-sample at every origin where 2020Q2–Q4 ≤ t0.

    5. Scoring: CRPS (primary density metric) + parametric log-score + PIT/coverage, scored from the per-draw predictive cloud Dforecast(1:8,:,:). Significance via Giacomini–White (headline — valid under nesting and correct for the expanding scheme), Clark–West (nested point), Diebold–Mariano (non-nested), with Romano–Wolf + the Model Confidence Set for multiplicity.

    6. Endogenous-US spillover analysis. The contribution the endogenous-US GVAR enables and the frozen-anchor cannot: a US shock that propagates abroad and feeds back into the US. Tier A (directly solver-computable conditional scenario propagation via solveGVARClosedFormEndo / solveGVARLinear in app/src/lib/compute/gvarSolve.ts) ships first; Tier B (GIRF/FEVD/connectedness) is a new module built from the exported companion_mean.json (betahat=Γ, sigmahat=Σ) + the coupling M — not a call into the current solver (which computes conditional-mean deltas, not GIRFs).

    Headline result (first full pass — results/tables.{txt,json}, 56 origins, 9 models; DESIGN final). AR(p)/DFM have the lowest point CRPS, but the 90% Model Confidence Set carries the value-add: emgvar_endo is in the inflation MCS at all horizons and the short-rate MCS at h=1,2,4 (out of the growth MCS at h=1 & h=8), emgvar_endo ⪰ emgvar_frozen, and it decisively beats the textbook OLS classical GVAR (cgvar_a removed from most sets). Best inflation h=1 = emgvar_endo (relRMSE 0.799). Honest caveats: the draw-based densities are over-confident (PIT cov90 ~0.73–0.83 vs 0.90) and the parametric log-score column is numerically broken (CRPS + MCS are the robust primaries). The Tier-A US +100 bp result shows non-trivial endogenous-only feedback the frozen anchor omits, but the magnitudes are large/sign-flipping and it is a multi-period conditional projection, NOT a causal IRF — validate before headlining. Do not cite the log-score numbers.

    See em-bayesian-gvar-eval/docs/EMPIRICAL_PROTOCOL.md for the full leak-free driver design (oos_driver.m), the per-origin forecast JSON schema, the compute plan, and the look-ahead invariants.
