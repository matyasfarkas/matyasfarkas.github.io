    Build, Test & Deploy¶

    How the EM-Bayesian Global VAR platform goes from a working tree to the two live sites — the /bvar-scenario path of the academic website (GitHub Pages) and gmapsmodel.com (Netlify) — and to the desktop installer. This page documents the green gate (the local checks that must pass before any deploy), the data-pack check every build runs, the test taxonomy (which suites guard an invariant versus a feature), and the deploy chain (two builds of the same commit).

    Since 4.0.0 the data and the estimated model live in a data pack (app/public/data + manifest.json), separate from the tool: the build ships whatever pack is in the tree, and desktop users can update the pack without a new installer (UPDATE_MANUAL.md).

    For the higher-level architecture and the data-refresh / re-estimation runbook, see ARCHITECTURE_FOR_AI.md and REESTIMATING_MODELS.md. This page does not repeat those.

    The green gate¶

    Everything runs from the app/ directory. The commands below are the full pre-deploy contract — types clean, tests green (fast suite + the heavy solver canaries), static export succeeds — before any push to the deploy remote.

    cd app
npx tsc --noEmit                       # 1. types: must report 0 errors
npm test                               # 2. fast suite (excludes the heavy solver canaries)
npm run test:heavy                     # 3. heavy solver/perf canaries (serialised, 1 fork)
BASE_PATH=/bvar-scenario npm run build # 4. static export with the deploy base path
    Step Command What it proves
    Types npx tsc --noEmit TypeScript compiles with no errors (no emit; type-check only).
    Fast tests npm test The fast compute suite in app/src/__tests__/compute/, minus the heavy solver canaries (see the split below), including the cheap canaries.
    Heavy tests npm run test:heavy The expensive full-panel solver / affine-kernel / band-solve canaries, run serialised (--poolOptions.forks.maxForks=1) so the multi-second US-endogenous solves do not contend for cores.
    Build npm run build prebuild first: gzip_companion_draws.mjs (gzips every local plain companion_draws.json into its .gz; in a fresh checkout there is none — the plain files are not in git — and the committed .gz is used), vintages_publish.mjs (re-bakes the /monitor vintage files), pack-verify.mjs --full (every file matches manifest.json; dating, weights↔coupling and app-version checks). Then next build writes the static export (output: 'export') to app/out/, and prune-redundant-json.mjs web drops plain .json files that have a .gz twin.

    Green gate = tsc 0 errors and npm test green and npm run test:heavy green and the build succeeds. Only then is a deploy allowed. The gate is manual: neither deploy (GitHub Action, Netlify) runs tsc or the tests. What they do run is npm run build, so a pack that fails pack-verify --full cannot deploy. npx vitest run (= npm run test:all) runs everything in one pass — use it for a full sweep, but note it runs the heavy suites with default parallelism (slower, can over-subscribe).

    The fast/heavy split is real, and it is in package.json — read it, don't assume. npm test is not vitest run: it is vitest run with a list of --exclude globs. The excluded (heavy) patterns are gvar-us-endogenous, gvar-direct-channel, gvar-band-solve, gvar-band-solve-levelunits, gvar-nowcast-completion, gvar-closed-form-*, affine-blockernels-parity, gvar-kernel-affine-independence, gvar-external-spillover, gvar-anderson. npm run test:heavy runs exactly those (matched by vitest run <name…>), one fork at a time. A change that only npm test covers leaves the full-panel solver paths (dim 2180 in the deployed pack) unverified — both halves are mandatory before deploy. (npm run test:watch is vitest — the interactive watcher, never a CI gate.)

    A few notes that are easy to get wrong:

    • The build is a static export: next.config.mjs sets output: 'export', images.unoptimized: true, and routes the deploy prefix through basePath/assetPrefix/NEXT_PUBLIC_BASE_PATH, all driven by the BASE_PATH env var (see BASE_PATH below).
    • This is not stock Next.js — see app/AGENTS.md. Read the bundled docs under node_modules/next/dist/docs/ before changing build config.

    Test taxonomy¶

    Most tests live in app/src/__tests__/compute/; checks on the shipped data files (e.g. meta-column-indices.test.ts) are in app/src/__tests__/data/. They fall into three roles:

    • CANARY — guards a load-bearing invariant or a deployed artifact. A red canary means the shipped model data, the scaling convention, or the cross-country solver identity is broken; it must block the deploy, not be skipped.
    • FEATURE — proves a specific user-facing capability (a Taylor rule, optimal policy, the fiscal debt recursion, US-endogenous coupling, the entropic long-run tilt, GVAR globals/topology, …).
    • REGRESSION — pins a previously-fixed bug so it cannot silently return (scaling differencing, WYSIWYG conditioning, counterfactual recovery, …).

    Fast (npm test) vs heavy (npm run test:heavy) — which is which¶

    npm test excludes ten heavy patterns; npm run test:heavy runs exactly those, serialised to one fork. The three deploy-blocking canaries (scenario-scale-convention, gvar-convergence, gvar-coupling-artifact) are all in the fast suite. The heavy suite is the multi-second full-panel solver and the affine-kernel/coupling perf-parity gates:

    --exclude glob (from package.json) currently-present files what it covers
    gvar-us-endogenous gvar-us-endogenous.test.ts augmented endogenous fixed point (full panel)
    gvar-direct-channel gvar-direct-channel.test.ts the one-hop preview on the live US-endogenous panel
    gvar-band-solve gvar-band-solve.test.ts per-draw conditional GVAR re-solve (the experimental cloud)
    gvar-closed-form-* gvar-closed-form-routing.test.ts (I−M)⁻¹d ≡ iterative + cache correctness on the endogenous fixture
    gvar-band-solve-levelunits gvar-band-solve-levelunits.test.ts the band solve in level units
    gvar-nowcast-completion gvar-nowcast-completion.test.ts the coupled nowcast of the ragged edge (needs up to 120 sweeps on the deployed model)
    affine-blockernels-parity affine-blockernels-parity.test.ts one full filter+smoother probe-loop reference (slow by design)
    gvar-kernel-affine-independence gvar-kernel-affine-independence.test.ts the kernel-cache RANK-1 affine-independence gate
    gvar-external-spillover gvar-external-spillover.test.ts external-forecast propagation through the coupled solve
    gvar-anderson gvar-anderson.test.ts the Anderson-accelerated soft (external-forecast) solve reaches the same fixed point (≈5 min alone)

    The fast/heavy split is keyed on glob patterns, not a fixed file list: npm test --excludes the ten patterns above and npm run test:heavy selects gvar-us-endogenous gvar-direct-channel gvar-band-solve gvar-closed-form affine-blockernels gvar-kernel-affine gvar-nowcast-completion gvar-external-spillover gvar-anderson (app/package.json is authoritative) — so a new gvar-closed-form-* file is auto-routed to the heavy half. Everything else in app/src/__tests__/ runs under npm test. Both halves are part of the gate — a heavy suite that only test:heavy runs still blocks a release if red. (Under heavy machine load some vitest workers time out; such a file is re-run on its own before it counts as a failure.)

    Canary suites (block deploy)¶

    Test file Guards
    scenario-scale-convention.test.ts The conditional-display scaling convention: response paths for log vars are shown as 4·(Δlevel_t − Δlevel_{t−1}) (q/q-annualized rate deviation), not 4·levelGap_t (cumulative price-level gap). Pins the corrected convention against the MATLAB conforekf ground truth for the canonical Baa +100bp / 8q shock; a break would re-introduce the ~23× far-horizon overstatement.
    gvar-convergence.test.ts Gauss-Seidel ≡ closed-form: for the same US scenario the iterative solveGVAR (Gauss-Seidel sweeps, US frozen) and the linear solveGVARLinear (build M by unit-RoW probes, then (I−M)⁻¹ d / Smith doubling) must agree to ~machine precision per RoW country. This is the proof that the N-bloc linear-solver generalization is correct; also reports empirical and power-iteration ρ(M).
    gvar-coupling-artifact.test.ts The pre-shipped coupling artifact (public/data/bvar/gvar/coupling_default.json.gz) is FRESH: its modelSig matches the deployed models, the augmented empty-pin-structure dim is self-consistent with the live US-endogenous build, ρ ∈ (0,1), and an artifact-hydrated solve equals the live-built closed-form solve (≤1e-3, the 6-sig-fig rounding bound). Also asserts the route REFUSES the empty-structure artifact for a non-empty (e.g. US-pinned) request. Skips loudly if the .gz is missing rather than failing.

    These three must stop a release if red — they cover the two things a static deploy cannot self-correct: the shipped artifacts (coupling_default.json.gz, the per-bloc model JSON) and the display/solver conventions the UI renders on top of them. Two data-file guards belong with them: fiscal-meta-indices.test.ts (every fiscal bloc's debt path stays bounded — stale positional indices explode it) and data/meta-column-indices.test.ts (every fiscal_meta/external_meta index points at the right variable family; external_meta.idx equals its recorded idxIds). The data pack itself is checked by pack-verify --full in every build (above).

    Regression suites¶

    Test file Bug it pins
    conditioning-wysiwyg.test.ts A directly-conditioned variable must display exactly the dragged path (WYSIWYG), including sparse/partial per-quarter conditioning — the scaling-differencing fix must apply only to RESPONSE vars.
    counterfactual-irf.test.ts A counterfactual recovers the impulse response function (IRF) when the rate adjustment equals the IRF.
    counterfactual-recovers-scenario.test.ts A counterfactual with a vanishing policy adjustment must recover the scenario (policy effect measured against the right baseline).
    fiscal-backcast.test.ts The budget-identity recursion in fiscalAccounting.ts reproduces the observed US federal debt/GDP back-cast from observed drivers (Step-1 gating).
    matrix.test.ts Core linear algebra (Cholesky/solve/inverse, ~1e-15 singularity threshold) in matrix.ts.
    affine-blockernels-parity.test.ts The affineBlocKernels perf path reproduces the old full filter+smoother probe loop to <1e-9 (baseline mean Sc and every per-period kernel) and is >=3× faster, on the real US-endogenous bloc — the optimization must stay a numerical no-op. (heavy)
    gvar-kernel-affine-independence.test.ts The affine-independence claim underlying the per-bloc kernel cache-key change (RANK-1 gate). (heavy)
    fiscal-meta-indices.test.ts Pins the STALE-POSITIONAL-INDEX bug (§ below): re-resolves every fiscal bloc's fiscal_meta.json indices by variable id from the deployed spec.json and asserts each bloc's derived debt path stays bounded — the regression that caught EA's effRate landing on the equity index (col ~537) so debt/GDP exploded. Also pins the level-display drag conversion (oil → $100 must not over-shoot to ~$190).

    The perf-fix parity suites (affine-blockernels-parity, gvar-kernel-affine-independence) are regression gates in spirit — they prove an optimization is numerically a no-op — but because they protect the production GVAR solve path, treat a red result there with the same severity as a canary.

    The STALE-POSITIONAL-INDEX gotcha (porter must regen). fiscal_meta.json stores the fiscal-driver column indices positionally, but the porter (pipeline/port_gvar_exports.py) does not regenerate them. Any variable-order change (the 33-bloc GVAR-EM refit inserted vars ahead of the fiscal block in every spec except US) silently re-points the indices at the wrong columns — the cause of the recent EA/UK/CA/JP/CN debt explosion. The fix is to run node pipeline/fix_fiscal_meta_indices.mjs (re-resolves the six indices by variable id from the deployed spec.json, preserves d0/sfaDefault, idempotent) after porting and before the gate; fiscal-meta-indices.test.ts is the canary-grade guard that blocks a deploy with stale indices. See REESTIMATING_MODELS.md and the DATA_SCHEMA fiscal-meta section.

    The file list above is enumerated from app/src/__tests__/compute/. When you add a test, slot it into the right row here and confirm it actually runs under vitest run.

    Drivers licence suites (the experimental DSGE decomposition)¶

    The Drivers panel reads a scenario path through a chosen DSGE model and reports which sequence of that model's structural shocks reproduces it. The claim is model-conditional and its validation is same-model recovery, so what the suites below guard is not a user-facing capability but a licence: the configurations in which the shipped estimator is allowed to present a result, and the provenance of the data it reads. Three files carry them, 26 tests in total, and none of them is in the --exclude list — they all run under npm test.

    Test file Tests Guards
    drivers-decomp.test.ts 4 The engine mirrors pipeline/bench_simple_decomp.m: exact same-model recovery on the identified fixtures, the budget rule (naming more shocks than observables watched throws), and the measured unit conversions (inflationq/pinfobs = interest/robs = 4.000).
    drivers-decomp-v2.test.ts 7 Display-unit additivity (contributions + residual reproduce the scenario line to 1e-8), the CMR14 extended-observable unit mapping, and the FRB/US cluster licence.
    drivers-decomp-v3.test.ts 15 The column-normalised solver, class aggregation at the licensed configuration, the three-coordinate class-view predicate, the FRB/US cluster partition and its validated default naming, shipped-payload provenance (sha256 of every shipped file, class_maps.json embedded verbatim, index horizon = engine horizon), the BVAR-panel-to-observable seam, and the rank arithmetic behind the excluded duplicate observables.

    Remark 1 (These are artifact gates, not unit tests). Each file reads the shipped payload off disk — app/public/data/dsge/census/index.json, the census copies, and the US_SW07/US_CMR14 files in the IRF tree — rather than a fixture. Test v3-5 hashes every shipped file and compares against the sha256 the index records for it, so a payload regenerated without rebuilding the index, or an index committed without its files, turns red. Treat that the way you treat gvar-coupling-artifact: it is telling you the shipped data and the shipped metadata have come apart. The suite therefore also does real I/O, including the 10.75 MB US_FRB22.json that the cluster tests load.

    Remark 2 (Do not widen a licence constant to make a test pass). Test v3-3 asserts the class-view observable set and shock set against the literal bench coordinates, not against the constants the app exports, and it carries a negative case for each of the seven droppable shocks. Widening either constant to admit a configuration the bench never ran is exactly what the test exists to catch. The correct response to a red licence test is to narrow what the interface offers; see MAINTAINER_OPERATIONS.md §H4.

    Deploy chain¶

    The source repo is matyasfarkas/BVAR-Policy-Calibration-Tool (the origin remote). There are two deploy targets, built from the same commit of main — push it to both:

    Remote Repo Builds Serves
    bvarscenario matyasfarkas/BVARScenarioTool GitHub Action deploy-to-website.yml (below) matyasfarkas.github.io/bvar-scenario (GitHub Pages, via starter-hugo-academic)
    gmapsmodel gmapsmodel/GMAPS Netlify, per netlify.toml (below) gmapsmodel.com (domain root)

    Both deploys run npm ci && npm run build, so both run prebuild (pack-verify --full); neither runs the tests. The desktop installer is a third, local build (below).

    The GitHub Pages chain: the bvarscenario Action builds the export and republishes it into the matyasfarkas/starter-hugo-academic website repo, a Hugo Academic site published to GitHub Pages. This workflow contains no Hugo step: it only copies app/out/* into the website repo, and the Hugo build downstream then rebuilds and serves it.

    push -> bvarscenario main
   │   (paths: app/** or netlify.toml)
   ▼
.github/workflows/deploy-to-website.yml   (runner: ubuntu-latest, Node 22)
   │  npm ci
   │  BASE_PATH=/bvar-scenario npm run build      → app/out/
   │  checkout matyasfarkas/starter-hugo-academic
   │  rm -rf website/static/bvar-scenario/*
   │  cp -r app/out/* website/static/bvar-scenario/
   │  commit + push to the website repo
   ▼
Hugo rebuilds the Hugo Academic site from the website repo
   ▼
served at the /bvar-scenario path of the academic site (GitHub Pages)

    Workflow facts, verified against .github/workflows/deploy-to-website.yml:

    • Triggers: push to main with changed paths under app/** or netlify.toml, plus manual workflow_dispatch.
    • Runner / toolchain: ubuntu-latest, actions/setup-node@v4 with node-version: 22 and npm cache keyed on app/package-lock.json.
    • Build step runs in working-directory: app: npm ci then npm run build, with BASE_PATH: /bvar-scenario in the environment.
    • Publish step checks out matyasfarkas/starter-hugo-academic (via secrets.WEBSITE_DEPLOY_TOKEN), clears website/static/bvar-scenario/, copies app/out/* in, and commits/pushes (a no-op git diff --cached --quiet short-circuits when nothing changed).

    The Hugo build that assembles the final academic site is not in this workflow file — it runs as part of the website repo's downstream build that publishes to GitHub Pages, and any Hugo version pin lives in the starter-hugo-academic repo, not here (see below).

    gmapsmodel.com (Netlify)¶

    netlify.toml (repo root): base = "app", command = "npm ci && npm run build", publish = "out", NODE_VERSION = "22", and DOCS_URL pointing the Docs button at the hosted MkDocs site (this host serves the app at the domain root, with no sibling /docs/). No BASE_PATH is set, so the app is built for the root.

    The ignore rule skips a push that changes neither app/ nor netlify.toml (to save metered build minutes):

    ignore = "git diff --quiet $CACHED_COMMIT_REF $COMMIT_REF -- :/app :/netlify.toml"

    Netlify runs this command inside the base directory (app/), so the paths must be repo-root pathspecs (:/…). The first version (git diff --quiet HEAD^ HEAD -- app netlify.toml, added 2026-08-05) matched nothing from app/, always exited 0, and cancelled every build — manual "Trigger deploy" included — until it was fixed in 298dfd8d (2026-10-08). $CACHED_COMMIT_REF (the last commit Netlify built) also covers a merge whose first parent already had the changes, which HEAD^ missed. After every push, check the site really changed: curl https://gmapsmodel.com/data/manifest.json should show the new packId.

    The desktop installer (Tauri)¶

    Built locally, not in CI: npm run build:tauri (= next build with TAURI_BUILD=1 and an empty BASE_PATH, then prune-redundant-json.mjs desktop), then npx tauri build (Windows cross-build steps in app/src-tauri/README.md). build:tauri has no prebuild, so run npm run data:verify (verify_cutoffs + pack-verify --full) first. The installer carries the data pack that was in the tree as its built-in pack; record it with npm run pack:record-release -- --version <x.y.z> so later update packs can be cut against it. Full steps: UPDATE_MANUAL.md §8.

    BASE_PATH¶

    The site is served from the /bvar-scenario sub-path of the academic site (GitHub Pages), so the static export must be built with that prefix. next.config.mjs:

    const nextConfig = {
  output: 'export',
  basePath: process.env.BASE_PATH || '',
  assetPrefix: process.env.BASE_PATH || '',
  images: { unoptimized: true },
  env: { NEXT_PUBLIC_BASE_PATH: process.env.BASE_PATH || '' },
};
    Build BASE_PATH Asset/link prefix
    Local dev / preview unset → '' root-relative (/…)
    Deploy (GitHub Action) /bvar-scenario /bvar-scenario/…
    Deploy (Netlify, gmapsmodel.com) unset → '' root-relative (/…)
    Desktop (build:tauri) '' root-relative

    The GitHub Action always sets BASE_PATH=/bvar-scenario. Reproduce that deploy artifact locally with BASE_PATH=/bvar-scenario npm run build. Data files are fetched only through app/src/lib/data/dataManifest.ts, which builds its URLs from process.env.NEXT_PUBLIC_BASE_PATH + /data.

    Hugo version pin (0.122.0)¶

    The website repo's build is pinned to Hugo 0.122.0. The pin is enforced in the website pipeline (.github/workflows/updater-wip.yml). Rationale: Hugo 0.123+ removed the getCSV / getCSS data helpers that the wowchemy (academic) theme depends on; later versions break the site build. Do not bump the pin without first migrating the theme off those removed helpers. (Documented in README.md and ARCHITECTURE_FOR_AI.md.)

    The Drivers payload in the static export¶

    next build copies app/public/ into app/out/ verbatim, so the DSGE impulse-response payload the Drivers panel reads ships with every deploy. The directory it added, app/public/data/dsge/census/, is 22.4 MB over nine files, and two of them are almost all of it: the FRB/US census lenses US_FRB22.json at 10.75 MB and US_FRB22_var.json at 10.57 MB, each carrying the responses of 54 shocks. The index and the six small census models come to 1.07 MB together. Regenerating the US_SW07 and US_CMR14 IRF files with their full native shock sets added a further 1.6 MB under app/public/data/dsge/irfs/. That was about 24 MB against an app/public/data/ tree of ~757 MB (Aug 2026), so nothing in the deploy chain has to change to carry it and no file comes near GitHub's 100 MB limit.

    None of it is fetched eagerly. The drawer requests census/index.json (36 KB) the first time a user opens it, once per session, and the selected model's response file only when that model is selected, cached per model for the rest of the session. The default lens is US_SW07, whose 215 KB file is already in the IRF tree, so the ordinary path costs 251 KB. The two ~10.7 MB FRB/US files are downloaded only if the user picks an FRB/US lens — the drawer records a fetch failure per model and offers a retry, which is there because a file that size can fail on a slow link. Unlike companion_draws and the coupling artifact these files are not gzipped in the repo, and the loader that fetches them does no client-side decompression; whatever compression happens on the wire is the host's doing and is not configured here.

    Remark 3 (The desktop prune does not touch them). npm run build:tauri runs scripts/prune-redundant-json.mjs desktop, which deletes a plain X.json from out/data/ only when a sibling X.json.gz exists. The census files have no .gz sibling, so the full 22.4 MB travels into the Tauri bundle. If the installer size becomes the binding constraint, the lever is to gzip the two FRB/US files at build time and give the Drivers loader the .gz path the coupling artifact already uses — a code change on both sides, not a build flag.

    What to commit (and what not to)¶

    • Commit only deploy-relevant files (app/**, docs, config).
    • Commit app/public/data/ together with its manifest.json: every data change needs a re-stamp (pack-build.mjs --pack-id <new id>), or prebuild's pack-verify --full fails the deploy. Never re-use a pack id for different content.
    • The plain companion_draws.json files are local by-products (not in git, not in the pack); only the .gz is committed.
    • Leave pipeline/ scratch — diagnostics, staging dirs, raw CSVs, _verify/ — untracked.
    • Never commit app/.env.local or any FRED_API_KEY.
    • Commit app/public/data/dsge/census/index.json together with the payload files it hashes. The index records a sha256 per shipped file and drivers-decomp-v3.test.ts re-computes every one of them, so a half-staged payload is a red test rather than a silent mismatch.

    Quick reference¶

cd app
npx tsc --noEmit
npm test                # fast suite (excludes the heavy solver canaries)
npm run test:heavy      # heavy solver / perf-parity canaries (1 fork)
BASE_PATH=/bvar-scenario npm run build   # prebuild runs pack-verify --full

npm run data:verify                 # verify_cutoffs + pack-verify --full
npm run pack:build -- --pack-id <id> # re-stamp manifest.json after a data change (new id)

git push bvarscenario main && git push gmapsmodel main
curl -s https://gmapsmodel.com/data/manifest.json | head -c 300   # confirm Netlify really rebuilt

npm run test:all        # = vitest run

node scripts/build_drivers_index.mjs

If a Drivers licence test goes red, the shipped payload and the index that hashes it have come apart, or a licence constant has been widened past what the benches ran — regenerate the payload, or narrow the interface; never widen the constant (§H4 of MAINTAINER_OPERATIONS.md).
